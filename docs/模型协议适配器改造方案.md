# 模型协议适配器改造方案（新增 Claude：`anthropic_messages`）

> 状态：**已确认并实施**（2026-10-09）。第 18 节 7 项均按推荐确认；第 3 项按保守做法落地（Bedrock 两种主机都默认关闭结构化输出）。实施与本稿的差异见第 19 节。
> 范围：新增第三种连接协议 `anthropic_messages`，与 OpenAI 兼容（Chat Completions）、OpenAI Responses 并列，对评分、起草、归类、结构识别提供同一套接口。

## 1. 背景与目标

现在只有两种协议：`openai_compatible`（`OpenAICompatibleChatScorer`）和 `openai_responses`（`OpenAIResponsesScorer`）。2026-10-09 起改用 AWS Bedrock，而 Bedrock 上的 Claude 走 Anthropic Messages 协议，不走 OpenAI 兼容协议。现有两个适配器都接不上。

目标：

1. 新增 `AnthropicMessagesScorer`，实现上层用到的全部方法（第 5.7 节），接入用量计量、调用日志、429/额度识别、截止时间、限流重试、熔断和连接并发。
2. 同一个适配器既能接 Bedrock（`bedrock-runtime` / `bedrock-mantle` 的 `/anthropic/v1/messages`），也能直连 `api.anthropic.com`。
3. 迁移 0034 放宽 `ck_ai_connections_provider_type`；平台模型配置同步支持。
4. 协议识别、测试连接和账户页、运维页的协议下拉都能选 Claude。
5. 三个适配器跑**同一套合同测试**。

## 3. 不做的事

- **不新增 `LLM_PROVIDER=anthropic` 环境变量路径**。Claude 只能通过 BYOK 连接或平台模型配置使用（与 D-028 一致：受保护部署里环境变量不是模型来源）。
- **不用流式**。评分、起草都是短 JSON，超时上限 300 秒，非流式够用；与另两个适配器保持一致。
- **不开提示词缓存（`cache_control`）**。Bedrock 不支持顶层自动缓存；要缓存得先把视图拆成「共享前缀块 + 规则块」，改了提示词构造就得升版本，且写缓存比普通输入贵 25%，收益要靠真实调用实测。放到后续阶段。
- **不用服务端 `fallbacks`（拒答自动换模型）**。换模型会让实际出分的模型与复现身份里记的模型不一致；Bedrock 也不支持。拒答按失败处理，转人工复核。
- **不支持 SigV4 签名**。只支持 API Key（`x-api-key`）。
- 不改现有两个适配器发出的提示词和请求体（第 13 节）。

## 4. 总体结构

```

  ├─ openai_responses   → OpenAIResponsesScorer       ┐
  ├─ openai_compatible  → OpenAICompatibleChatScorer   ├─ llm/transport.py: post_with_retry()
  └─ anthropic_messages → AnthropicMessagesScorer  新  ┘    (截止时间 / 429 额度 / 重试 / 熔断槽位 /
                                                             UsageMeter / call_log / observation)
```

新文件 `backend/app/services/llm/anthropic_messages_adapter.py`。`factory.get_llm_scorer` 增加一个分支，设置 `_ai_connection_snapshot`、`_ai_connection_organization_id`、`max_concurrency`，做法与另两种一致。

## 5. `AnthropicMessagesScorer`

### 5.1 请求形状

```json
POST {base_url}/messages
x-api-key: <key>
anthropic-version: 2023-06-01
content-type: application/json

{
  "model": "<连接里的模型名>",
  "max_tokens": 4096,
  "system": "<指令文本>",
  "messages": [{"role": "user", "content": "<JSON 视图文本>"}],
  // 以下字段只在连接显式配置时出现
  "temperature": 0.2,            // 或 top_p，二者至多其一
  "thinking": {"type": "adaptive"},
  "output_config": {
    "effort": "low",
    "format": {"type": "json_schema", "schema": {…清理后…}}   // 仅结构化模式
  }
}
```

`system` 与 `user` 的文本**与 Chat 适配器逐字相同**：旧路径用 Chat 适配器的 `_instructions` / `_envelope_instructions` / `_input_payload`，Core 路径用 `core_view` 生成的 `request.system` / `request.user`。所以这次不产生新的提示词文本（第 13 节）。

为了不让 Claude 适配器去 import 另一个适配器的私有函数，这几个旧路径提示词函数移到中立模块 `llm/legacy_prompts.py`，原模块重新导出。移动不改字符，用测试锁定文本哈希。

### 5.2 参数策略与默认值

| 参数 | 默认 | 连接可覆盖 | 说明 |
|---|---|---|---|
| `temperature` / `top_p` | **不发** | 可设其一，同时设置在保存时拒绝 | 新模型传了就 400，所以「不发」是唯一对所有现行模型都安全的默认 |
| `thinking` | **不发**（由模型默认决定） | `adaptive` / `disabled` | 不提供 `between_tools`、`budget_tokens`（模型专属，配错就 400） |
| `output_config.effort` | **不发**（模型默认：Opus 5.5 为 `medium`） | `low`/`medium`/`high`/`xhigh`/`max` | 新增连接选项 `effort`。是否默认设为 `low` 见第 18 节第 5 条 |
| `max_tokens` | `ANTHROPIC_MAX_TOKENS=4096` | `max_tokens`（1–100000） | 思考 token 也占这个预算；1200 在思考恒开的模型上容易截断 |
| 超时 | `ANTHROPIC_TIMEOUT_SECONDS=120` | `timeout_seconds`（1–300） | |
| 重试 | `ANTHROPIC_MAX_RETRIES=2` | — | 与 OpenAI 两个适配器同义 |

新增三个环境变量只作默认值，不包含 Key、地址或模型。

### 5.3 结构化输出的两种模式

新增连接选项 `structured_output`：`json_schema` | `off`；不设置时按地址自动决定，并在适配器初始化时确定下来：

| 主机 | 自动结果 | 依据 |
|---|---|---|
| `api.anthropic.com` | `json_schema` | 官方 API，GA |
| `bedrock-runtime.*.amazonaws.com` | `off`（实施时由 `json_schema` 改为 `off`） | 用户核实可用，但 Claude 文档说 Opus 4.7 及以后的模型由 mantle 设施承载（第 18 节第 3 条）；需要时在高级设置里改为「开启」 |
| `bedrock-mantle.*.api.aws` | `off` | 文档写明不支持，用户实测 400 |
| 其它（DeepSeek / Kimi / 智谱等的 Anthropic 兼容端点） | `off` | 没核实过，宁可走提示词约束 |

- **`json_schema` 模式**：`output_config.format` 带上**清理后**的 schema。清理只**删**不支持的关键字（`minimum`、`maximum`、`exclusiveMinimum`、`exclusiveMaximum`、`multipleOf`、`minLength`、`maxLength`、`maxItems`、`uniqueItems`、取值大于 1 的 `minItems`、`pattern`），不改结构，也不把约束改写进描述（改描述等于改提示词）。`pattern` 文档说部分支持，但 `^[0-9a-f]{64}$` 这类定长量词是否算「简单情形」没把握，删掉更稳；Core 路径的 `evidence_unit_id` 本来就用 `enum` 约束。
- **`off` 模式**：不带 `format`，只靠指令文本约束（与 Chat 适配器的 `json_object`/`none` 模式一样）。现有指令都写明了字段（起草指令里写有完整 JSON 形状，Core 视图指令列出了每个字段），不用追加 schema 文本。
- 两种模式下，**本地校验都不变**：`decode_core_response`、`decode_core_group_response`、起草层的 `_positive_points` 等仍然逐项校验。实施时要逐个核对：清理删掉的每个约束都有本地校验覆盖（重点是起草 schema 里的 `minimum`/`maximum`/`maxLength`/`maxItems`/`uniqueItems`）。没有覆盖的先补本地校验，再放开清理。

### 5.4 响应解析

1. 按顺序拼接 `content` 里所有 `type=text` 块，跳过 `thinking` / `redacted_thinking`，去掉 Markdown 代码围栏，然后 `json.loads`。
2. `stop_reason` 的处理：
   - `end_turn` / `stop_sequence`：正常解析；解析失败报 `invalid_json`。
   - `max_tokens`：一律报 `output_truncated`（与 Responses 适配器的 `_raise_if_incomplete` 一样严格，不赌「刚好写完」）。
   - `refusal`：报新原因 `refused`。不重试，评分转人工复核；起草、归类按「输出无效」处理并提示原因。
   - `pause_turn` / `tool_use` / 其它：报 `incomplete_output`。
   - 有 thinking 块而没有文本：`max_tokens` 时报 `output_truncated`，否则报 `empty_content`。
3. 异常类型 `MessagesJSONOutputError` 继承新的公共基类 `ProviderJSONOutputError(ValueError)`（放在 `llm/errors.py`，带 `.reason`）。`ChatJSONOutputError`、`ResponsesJSONOutputError` 也改为继承它，类名和消息都不变。目前按具体类名捕获的调用方改成捕获基类：
   - `extraction/llm_structure.py`：`except (ResponsesJSONOutputError, ChatJSONOutputError)` 改为捕获基类；
   - `ai_rule_drafter.py`：`except ChatJSONOutputError` 改为捕获基类。**行为变化**：Responses 适配器的截断以前在这里走通用失败分支，改后会得到准确的「输出达到长度上限」提示；
   - `ai_rule_drafter.py` 的 `isinstance(scorer, (OpenAICompatibleChatScorer, OpenAIResponsesScorer))` 加入 `AnthropicMessagesScorer`；
   - `classification/llm_classifier.py` 的原因白名单加入 `refused`。

### 5.5 用量

`usage` 换算进现有三字段：

- `prompt_tokens = input_tokens + cache_creation_input_tokens + cache_read_input_tokens`（总输入，文档给的算法；目前没开缓存，后两项为 0）；
- `completion_tokens = output_tokens`（包含思考 token，按输出计费）；
- `total_tokens = 两者之和`。

成功调用写入 `UsageMeter.record_success`，HTTP 失败或传输失败写入 `record_failure`，由共享传输层统一处理。

### 5.6 复现身份（provider contract）

需要改两处：`core_adapter.core_runtime_provider_contract`（V3/V4，Profile 冻结用）和 `base._provider_contract`（V1 旧路径）。都按 `provider == "anthropic"` 加分支，并且**从适配器实例读实际发出的值**，不读全局 settings：

| 字段 | 取值 |
|---|---|
| `name` | `anthropic`（Bedrock 和直连同名；缓存隔离靠连接快照） |
| `model` | 连接里的模型名 |
| `model_version` | `messages-2023-06-01`；设置了 effort 时为 `messages-2023-06-01;effort=low` |
| `sampling.temperature` / `top_p` | 发了就记实际值；没发就记 `"1"` / `"1"`（API 名义默认值；Responses 适配器省略 `top_p=1` 时也这样记） |
| `sampling.seed` | `null` |
| `sampling.max_tokens` | 实际值 |
| `thinking` | 发出的值：不发记 `{enabled:false, type:null}`；发 `adaptive` 记 `{true,"adaptive"}`；发 `disabled` 记 `{false,"disabled"}` |
| `response_format` | `json_schema` 或 `none`（第 5.3 节的结果） |

effort 放进 `model_version`，是因为 PromptEnvelope V1/V3/V4 的 `provider` 是封闭结构，新增字段要改三个契约版本。`model_version` 本来就表示「这个模型以什么方式被调用」，所有 envelope 都会逐字比较它。代价：`model_version` 不再只是协议名。

身份记录的是**发出的请求**，不是模型的实际行为。比如不发 `thinking` 时，Opus 5.5 实际是在思考的。这与 Chat 适配器的现行约定一致（不发即 `null`）。

## 6. 共享传输层（`llm/transport.py`）

现有两个适配器的 `_post_with_retry` 基本逐行相同，约 150 行：截止时间、429 额外重试、额度不重试、熔断槽位、observation、call_log、UsageMeter。PR #13 改截止时间时就得两处同步改。第三份拷贝会让漂移风险翻倍，所以**抽成一个函数**：

```python
def post_with_retry(*, client, url, headers, payload, provider_label, model_name,
                    base_url, connection_snapshot, usage_meter, usage_of,
                    operation, model_parameters, base_attempts,
                    attempts_limit=None, timeout_seconds=None,
                    rate_limit_retries=None, deadline=None,
                    default_timeout=None, extra_output=None) -> httpx.Response
```

- 三个适配器的 `_post_with_retry` 都变成薄包装，只提供 URL、请求头、`usage_of`、`operation`（`chat` / `responses` / `messages`）和 observation 参数。
- **行为保持不变**：现有测试（`test_connection_concurrency_and_rate_limits.py`、`test_core_llm_adapters.py`、`test_p4_provider_circuit.py`、`test_p0_llm_observability.py`）一行不改，必须全过；合同测试再从三个适配器的角度覆盖一遍。
- 不改为异步，不改 HTTP 客户端（仍用 `httpx`）。

其它改动：

- `_REQUEST_ID_HEADERS` 加 `x-amzn-requestid`（`request-id` 已有）。
- `_RATE_LIMIT_HEADER_NAMES` 加 12 个 `anthropic-ratelimit-*` 头。
- Bedrock 错误体没有 `error.type` 时，用 `x-amzn-errortype` 头（取冒号前的部分，如 `ThrottlingException`）作为 `provider_error_type`，只用于诊断，不参与分类。

- **不识别**的情形：Bedrock 的「每日 token 配额」类 429（AWS 文档未给出稳定错误码），仍按可重试的限流处理，受 `rate_limit_retries` 和截止时间约束。

## 8. 协议识别与测试连接

### 8.1 识别（`ai_connection_protocol.py`）

新常量 `MESSAGES = "anthropic_messages"`，`PROTOCOLS` 扩为三个。识别顺序在现有四步上扩展：

1. 手动选择优先（不变）。
2. 地址后缀：新增 `/messages`，按 `/v1/messages` 优先截掉后识别为 `MESSAGES`。
3. **路径规则（新增，排在已知主机表之前）**：路径里有 `/anthropic` 段的识别为 `MESSAGES`。这能覆盖两种 Bedrock 主机，以及 DeepSeek（`api.deepseek.com/anthropic`）、Kimi、智谱等的 Anthropic 兼容端点。它们的主机在已知主机表里映射到 Chat，所以路径规则必须先于主机表判断。
4. 已知主机：加 `api.anthropic.com → MESSAGES`。Bedrock 主机**不进**主机表：同一主机下还有 OpenAI 兼容端点（`/openai/v1`、mantle 的 `/v1`），只看主机会判错。
5. 探测：候选顺序变为 Chat → Responses → **Messages**。只有 404/405 才换下一个（不变）。这意味着未知主机在保存或测试时，最多会多发一次探测请求。

**地址规范化**（只对 `MESSAGES`）：保存的 `base_url` 统一以 `/v1` 结尾，请求发到 `{base_url}/messages`。
- `https://api.anthropic.com` → `https://api.anthropic.com/v1`
- `…/anthropic` → `…/anthropic/v1`
- `…/anthropic/v1/messages` → `…/anthropic/v1`

改完的 `ProtocolNotDetected` 文案改为「Chat Completions、Responses 或 Anthropic Messages」。

### 8.2 测试连接（`ai_connections.verify_connection_runtime`）

新增 `anthropic_messages` 分支：

```json
POST {base_url}/messages   (x-api-key, anthropic-version)
{"model": m, "max_tokens": 32,
 "messages": [{"role":"user","content":"Reply with {\"ok\":true}."}],

```

- 探测请求**带上与真实评分相同的参数形状**。这样「Opus 5.5 配了 temperature」或「mantle 配了结构化输出」这类组合会在测试时就失败，而不是等评分时才 400。

### 12.1 三适配器合同测试（新文件 `test_llm_adapter_contract.py`）

每个协议提供一个「协议夹具」：端点路径、鉴权头断言、成功响应构造（给定 JSON 和用量）、错误响应构造（给定状态、错误类型和头）。下面每条用例对三个适配器参数化执行：

1. `complete_json` 返回解析结果；用量三字段与 `request_count` 正确；带 `response_schema` 时只尝试一次。
2. `score_core_envelope` / `score_core_group`：模型返回同样的 JSON 时，三个适配器解码出的结果**完全相同**；身份不匹配时在发请求之前就拒绝；幻觉引文被拒绝。
3. `score_criterion` / `score_envelope` 输出带 `provider`、`provider_response_id`、`usage`。
4. 429 带 `retry-after`：按 `rate_limit_retries` 重试；`attempts_limit=1` 时超时不重试。
5. 额度耗尽**不重试**，即使还有 `rate_limit_retries` 预算。各协议用自己的信号：OpenAI `insufficient_quota`、智谱 `1113`、Claude `enforced_spend_limit_reached`、402 `billing_error`、自设消费上限 400。
6. 截止时间：已过期就不发请求；单次超时不超过剩余时间；等待会吃光预算时放弃重试。
7. 熔断：401/403 永久打开；连续 5xx/529 达到阈值后打开，冷却后半开探测。
8. `max_concurrency` 从连接带到适配器，且不进快照。
9. 截断：统一抛 `ProviderJSONOutputError(reason="output_truncated")`。
10. 错误投影不含响应正文和 Key；请求 ID 能取到。

## 13. 提示词与缓存版本

- 本方案**不改任何现有提示词文本**，也不给 Claude 新写指令（第 5.1 节）。按「改 prompt/输入构造要升 PROMPT_VERSION」的约定，**不需要升版本**。
- 理由：Claude 的缓存条目靠复现身份（`name=anthropic`、`model_version`、`response_format` 等）与现有条目隔离，不会误复用。升 `PROMPT_VERSION` 反而会让现有 L0 缓存和 0033 的规则决策账本**全部失效**，已评过的论文重评要重新付费。
- 如果实施中确实需要改共享的指令文本（比如发现 Claude 在 `off` 模式下需要额外的格式提示），就升版本，并在 DECISIONS 里记下原因。
- 换成 Claude 后评分质量会变。按 §15 用 QWK 留出集重新锚定基线需要**真实调用**，必须先取得你的授权和预算，不包含在本次交付里。

## 16. 放弃了什么

| 放弃 | 原因 |
|---|---|
| **官方 Anthropic Python SDK** | 官方技能默认推荐用 SDK。不用的原因：①现有重试、截止时间、熔断槽位、错误投影、观测都建立在 `httpx.Response` / `httpx.HTTPStatusError` 上，SDK 1.x 底层是 `httpx2`，异常和响应对象都对不上，得再写一层转换；②SDK 自带重试，要关掉并改用 `with_raw_response` 才能拿到头；③现有测试用 `httpx.MockTransport` 注入，SDK 要换另一套注入方式，合同测试就做不到「同一套夹具」；④Vercel 函数包会多一个依赖。代价：要自己维护请求体和错误类型的对应关系，SDK 的自动约束清理、类型化异常也用不上，需要靠第 5.3、7 节和测试补齐 |
| 第三份 `_post_with_retry` 拷贝 | 风险最低，但截止时间、额度这类修复以后要改三处 |
| 只支持结构化输出 | Bedrock mantle（Opus 4.7 及以后模型的主要入口）不支持 |
| 把被删的 schema 约束改写进字段描述（SDK 的做法） | 等于改了提示词，要升版本，导致现有缓存失效 |
| 默认发 `temperature: 0` 追求确定性 | 新模型直接 400；而且 temperature 为 0 本来也不保证输出一致 |
| 改 PromptEnvelope 契约新增 `effort` 字段 | 要同时升 V1/V3/V4 三个封闭契约，范围过大 |
| 服务端 `fallbacks` 拒答换模型 | 实际出分的模型与身份不一致；Bedrock 也不支持 |
| 提示词缓存、流式、SigV4 | 第 3 节 |
| Bedrock 主机直接按主机名判 Claude | 同一主机下还有 OpenAI 兼容端点 |

## 17. 风险与顺带发现

- **SQLite 重建表**：`batch_alter_table` 重建 `ai_connections` 可能丢掉部分唯一索引或 CHECK。迁移测试逐项断言；Postgres 由 CI 的逐版本迁移覆盖。
- **思考恒开的模型**：Opus 5.5 不能关思考，单条规则的输出 token 会比 GLM 高出一截，成本随之上升。是否默认 `effort=low`，见第 18 节第 5 条。
- **共享传输层抽取**会动两个正在生产使用的适配器。对策：第 1 个提交只做抽取，现有测试一行不改全部通过之后才继续。
- **顺带发现（未修，建议另开任务）**：旧版 v2 路径的 `base._provider_contract` 对非 OpenAI 的 provider 一律读全局 `OPENAI_COMPATIBLE_*`，而不是连接自己的选项。于是 BYOK Chat 连接在这条路径上：①连接设的 `max_tokens`/`temperature`/`response_format_json` 不生效；②会发 `thinking: {"type": "disabled"}`（settings 默认值），这与 factory 里「BYOK 只在连接显式开启时才发 thinking」的注释相矛盾。修它会改变 Chat 连接的缓存身份，所以不并入本方案；Claude 分支从一开始就读适配器实例的值。

## 18. 待确认事项

1. **HTTP 实现**：用 `httpx` 直连（推荐，理由见第 16 节），还是改用官方 SDK？
2. **共享传输层**：本次一起抽出（推荐），还是先复制第三份、以后再合并？
3. **Bedrock 上的结构化输出**：你核实的是 `bedrock-runtime` 上可用。但 Claude 文档说，Opus 4.7 及以后的模型即使从 bedrock-runtime 调用，也由 “Claude in Amazon Bedrock”（mantle）的基础设施承载，而它不支持结构化输出。**你核实时用的是哪个模型？** 打算用 4.7 及以后的模型的话，`bedrock-runtime` 的自动判定建议也改成 `off`。无论哪种判定，测试连接都会带着同样的参数去试，配错会在测试时暴露。
4. **自设消费上限的识别**：它是 HTTP 400，没有错误码，只能按文档给出的消息前缀判断为额度耗尽。现有规则是「只按错误类型和错误码精确匹配」。是否为这一条破例（限定 400 + `invalid_request_error` + 两条文档原文前缀）？推荐破例：否则用户会看到「请求无效」，而真正的原因是钱用完了。
5. **思考强度与结构化输出要不要放进界面**：方案 A（推荐）是在账户页和运维页的「高级设置」里加两个下拉（「思考强度：模型默认/低/中/高」「结构化输出：自动/开启/关闭」），只在协议为 Claude 时显示，默认值都是「模型默认」「自动」。方案 B 是只加协议选项，其余参数只能通过 API 设置。另外，评分时 effort 默认是否设为 `low`？推荐**不设**：质量和成本的取舍需要你授权做真实对比之后再定。
6. **不升 `PROMPT_VERSION`**（第 13 节）是否同意？
7. **迁移编号**：本方案用 0034，异步任务化方案顺延为 0035，是否同意？
