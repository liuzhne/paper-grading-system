## 1. 结论与不可变决策

修复前的主要差异来自第一步有三套呈现：首次上传是旧表单，未确认的临时会话使用新双栏组件，确认后的评分标准又回到旧的评分项侧栏与单项表单。本轮已将初始选择、临时会话、正式标准及只读状态接入同一个 `RubricImportWorkspace`，确认后返回第一步仍显示文件、评分项表和基本信息。规则侧栏放在第二步，完整校验问题放在第三步。

本轮已按原型的内容层级、卡片顺序和逐步操作重组第一步，并补齐后端读取来源的接口。仍遵守以下已确认合同：

- 评分标准没有适用类型选择器；「课程报告评分标准」是用户填写的名称。截图中的课程报告/学位论文/编程作业按钮不进入实现。
- 第一步默认不调用 LLM。先确定评分项、分值和来源；内容归属、扣分规则、AI 建议与规则确认放在第二步。
- 上传、确定性解析与草稿编辑只写数据库临时导入会话；用户确认评分项后才创建正式 Rubric。
- 分值使用正整数；导入小数按十进制 `ROUND_HALF_UP` 换算，展示原值、结果和对应评分项，合计与满分不符时不能继续。
- 原文查看及编辑沿用现有组织可见性和角色权限；审核中、已发布标准只读，不能通过文件卡片绕过锁定。
- 重新上传先预览差异、再确认替换；未变化项保留人工成果，变化项失效重确认，移除项保留历史，新增项需补规则，不能覆盖已发布版本。

下表描述修复前代码事实。文件名指向源代码，后续行号可能随实现变动。

| 对照点 | Design 与用户预期 | 修复前差异及证据 | 本轮处理 |
|---|---|---|---|
| 第一步布局连续性 | 始终是左侧 Word、Excel、评分项表，右侧基本信息、确认提示、下一步 | `RubricsView.vue` 只有 `store.activeImportSession` 为真时渲染 `RubricImportWorkspace`；正式标准的 `step === 1` 使用 `editor-layout`、`criteria-nav` 和单评分项表单 | 同一组件覆盖选择文件、解析草稿、已确认标准和只读标准；第二步再使用评分项导航 |

| 标题与状态 | 标题、版本和状态属于正在操作的标准 | 页面标题取 `current?.name`，而新导入会话另存于 `activeImportSession`；此前选中的标准可能仍影响页头 | 以当前工作对象派生标题、状态及页头动作；临时会话不展示旧标准的审核/发布动作 |
| 规则错误出现时机 | 第一步核对评分项；第二步处理规则；第三步检查发布资格 | `activeIssues`、`blocking` 的红色告警位于步骤判断之外；第一步显示缺少规则、执行校验阻断 | 第一步只展示结构/分值/来源问题；规则不足进入第二步，完整校验与发布清单进入第三步 |
| 步骤门禁 | 每一步只要求完成当前用户能处理的任务 | `goStep()` 对所有后续步骤使用 `stepOneGate(parseState)`，未认领的疑似规则也让用户停在第一步 | 区分评分项结构核对与规则归属；进入第二步允许补规则，未处理规则仍不得提交审核或发布 |
| 文件卡片 | 已上传显示文件名、真实元数据、预览及重新上传；空卡片可选择/拖放 | 新组件只有文件名，文字直接写「解析成功」；正式标准第一步没有相同文件卡片；「拖入」文案没有对应 drop 处理 | 状态来自真实数据；实现拖放、点击选择、处理失败与重试；无法恢复的历史文件信息明确标注缺失 |
| 来源读取 | 返回第一步或重新打开标准仍能查看原文件与评分项出处 | 已有会话 `source-preview`；正式标准读取接口未提供统一的文件/评分项来源工作区投影 | 新增只读 `GET /rubrics/{id}/source-workspace`，从已有会话、活动 compilation 和来源记录投影；不新增持久化字段 |
| 评分项表 | 一屏对比编号、名称、满分、文档出处与解析状态 | 正式标准只能通过左侧逐项选择查看；临时组件直接展示 `source_refs[0].locator` 或 `sheet_name`，不能完整解释结构化定位 | 已统一表格，来源转换为可读文本，文件卡片可展开原文与定位信息；来源不足返回 `unknown` 并显示待补充，未实现逐行出处点击跳转 |
| 问题可操作性 | 点击问题能定位到评分项并处理 | 小数换算提示渲染成 `issue-link` 按钮却无点击事件；部分来源/合计问题只有文字 | 告警绑定评分项；定位、聚焦/高亮后可编辑，无法绑定单项的总分错误定位满分与合计 |
| 重新上传 | 在原文件卡片操作，先看到保留/变化影响，再明确确认 | 临时会话与正式标准使用两种不同重传 UI；正式标准另有原生输入表单 | 共用卡片和差异呈现，内部仍调用各自会话/正式标准 API；取消或失败保持原结果 |
| 主操作与后退 | 第一步「确认评分项，下一步」，第二步可返回核对原材料 | 新组件只为会话提供此主操作；正式标准第一步依赖页头保存/步骤切换 | 当前步骤保留一个清晰的前进主操作；已确认标准修改保存成功后进入第二步，后退保持内容 |
| 临时评分项实际编辑 | 编辑、新增、删除都应提交会话草稿 | 真实 E2E 编辑后没有发出 PATCH：`structuredClone` 直接接收 Pinia 响应式数组，抛出 `DataCloneError` | 编辑/新增/删除统一先 `toRaw()` 再复制，不把 Vue 代理交给原生克隆；最终综合 E2E 已验证真实 PATCH 与增删操作 |
| 确认响应丢失后的重试 | 服务端已确认时再次点击应恢复同一评分标准 | 每次点击生成新随机幂等键，确认 POST 已成功但响应丢失后重试会返回 409 | 同一会话固定使用 `confirm:<session_id>`；重试复用同一收据，后端仍校验确认状态及幂等，不另创建 Rubric |
| 视觉验收 | 原型重心在材料和表格，右侧摘要紧凑；窄屏仍可完成操作 | 单元测试通过不能证明初始/确认后两种页面的布局一致；旧侧栏占用表格宽度 | 同视口核对空状态、已解析、返回第一步、只读态；检验卡片比例、间距、信息顺序及窄屏可操作性 |

## 3. 按用户操作推进

### 3.1 第一步：基本信息与评分项

1. 从「导入评分模板」进入空工作区，按实际材料选择 Word、Excel 或两者，至少一份。基本信息位于右侧，名称可编辑，版本和说明作为补充信息，不出现类型选择。
2. 执行确定性解析。处理期间显示正在解析，防止重复提交；失败显示具体原因并保留已选文件及输入。尚未返回解析结果前，不显示「解析成功」。
3. 成功后在原卡片显示文件信息，表格显示评分项、整数分值、可读来源、解析状态和项数/合计。此时数据库只有临时会话，模板库不应新增正式评分标准。
4. 用户逐项核对，可查看出处、修改名称/分值/说明、按草稿能力新增/删除；右侧提示小数换算、来源冲突及合计问题。合并或选用某一来源必须有显式操作。
5. 用户重新上传其中一份文件时，先查看新增、变化、移除、未变化及规则继承影响。取消不替换；确认后重新核对。另一份未替换文件沿用，不要求用户重复选择。
6. 只有结构、分值、来源冲突满足条件才启用「确认评分项，下一步」。点击后原子创建正式 Rubric；失败留在当前步骤并保留编辑，成功进入第二步。
7. 从第二步返回或从模板库重开标准，第一步仍显示同样的两张文件卡片、评分项表和基本信息。正式草稿的修改经现有保存/重编译路径产生后继执行草稿；未经保存不得悄悄切换并丢失输入。审核中/已发布标准可读来源，不能编辑或重传。

第一步不要求用户解决「缺少扣分细则」或执行规则校验问题；这些问题必须在第二步有对应编辑入口，并继续受第三步的发布门禁约束。

### 3.2 第二步：评分规则

按已确认评分项导航，查看原文规则、未归属的疑似规则、模板对应关系和扣分细则。用户先核对来源，再人工补充或主动生成 AI 建议；AI 结果须逐项确认，不因切换步骤自动执行。完成当前评分项后可继续下一项，也可返回第一步核对材料。规则内容变化使受影响的旧确认/旧校验失效，保持原有服务端规则。

### 3.3 第三步：校验与发布

集中展示条款确认、来源/模板映射、未处理规则、最新草稿校验和发布权限。问题链接回能够处理它的步骤及评分项；保存修改后重新校验。提交审核与发布是两个独立动作，审核中需要退回草稿才能编辑，已发布需要复制新版本，不新增绕过生命周期的入口。

## 4. 前后端对应与修改范围

接口表省略统一 `/api` 前缀。`source-workspace` 已实现并纳入 OpenAPI/schema；其余会话、保存及发布动作复用既有接口。

| 用户动作/页面数据 | 前端职责 | 后端对应 | 边界 |
|---|---|---|---|
| 选择材料并解析 | 初始态卡片、文件校验、名称与版本、loading/error | `POST /rubrics/import-sessions` | 至少一份文件，`scorer=None`，只建会话 |
| 编辑/核对导入结果 | 保留本地输入，更新评分项和基本信息 | `PATCH /rubrics/import-sessions/{id}` | `expected_state_version` 并发保护 |
| 临时原文查看 | 显示可读来源并定位对应条目 | `GET /rubrics/import-sessions/{id}/source-preview?document=word\|excel` | 沿用会话可见性；只读 |
| 选择 Excel/Word 处理冲突 | 呈现双方值及确认结果 | `POST /rubrics/import-sessions/{id}/conflicts/{id}/resolve` | 显式决策、版本校验 |
| 临时重新上传 | 共用卡片选择与差异确认 | `POST /rubrics/import-sessions/{id}/reupload-preview`、`reupload-confirm` | 指纹一致才替换；取消无写入 |
| 确认评分项 | 防重复、失败保留、成功进入第二步 | `POST /rubrics/import-sessions/{id}/confirm` | 幂等创建 Rubric，不自动审核/发布 |
| 重开正式标准第一步 | `RubricsView.refreshDetail()` 直接 `api.get` 读取投影，再构造相同文件卡片、来源、解析提示和评分项表 | `GET /rubrics/{id}/source-workspace` | 投影已有数据、只读、组织隔离，响应 `private, no-store`；无表/列变更，迁移 head 仍为 0031 |
| 正式草稿保存 | 将表格和基本信息交给现有保存流程 | `POST /rubrics/{id}/recompile` 等既有保存入口 | 最新活动 compilation 和内容校验；后继草稿重新确认 |
| 正式草稿重新上传 | 同一差异组件显示保留与失效数量 | `POST /rubrics/{id}/reupload-preview`、`reupload-confirm` | 仅 draft 可写；review/published 拒绝 |
| 规则核对与 AI 建议 | 第二步按评分项组织；主动触发 AI | 既有 `rule-coverage`、`review-workspace`、`parse-coverage`、规则确认/补充接口 | 不改评分算法和 prompt，不放宽规则完整度门禁 |
| 检查、提交审核与发布 | 第三步按状态逐步开放操作 | 既有 `execution-draft`、`submit-review`、`publish` 等接口 | 最新校验、角色、组织、不可变版本边界不变 |
