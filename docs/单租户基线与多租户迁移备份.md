# 单租户基线与多租户迁移备份

> 发布基线：`v0.2.0` / `release/2026-08-21-v0.2.0` / 2026-08-21（Asia/Shanghai）。
>
> 本文记录当前实现的真实隔离边界，供未来多租户改造前核对和备份；它不是多租户功能的承诺，也不能把现有 `owner_id` 误认为已经实现了租户隔离。

## 当前模型：一个部署、一个可信租户

生产部署可通过 `AUTH_ENABLED=true` 启用一套共享用户名和密码。认证成功后签发 HMAC 会话 token；它只用作访问门禁，不代表独立用户、角色或租户。未启用认证时，本地和 CLI 使用无需登录的开发模式。

数据写入时，Web/CLI 的 `current_user_id` 均使用同一个 `DEFAULT_DEV_USER_ID`。`users` 与部分资源上已存在 `owner_id` / `created_by` / `reviewer_id` 等字段，评分批次到论文再到评分运行也会传递 `owner_id`；这些字段目前用于归属、审计和未来迁移锚点，**没有按请求身份过滤资源，也没有 tenant 级访问控制**。

因此，当前系统的正确运行前提是：同一部署中的登录者均属于同一受信任组织、可以看到彼此的数据。不要将它用于需要班级、院系、学校或客户之间数据隔离的场景。

## 边界与风险清单

| 范围 | 当前行为 | 多租户前必须补齐 |
| --- | --- | --- |
| 身份 | 单一共享凭据；token 仅携带用户名与过期时间 | 独立身份提供方/用户表、密码或 SSO 生命周期、会话撤销 |
| 授权 | 数据端点只验证是否已登录 | 每个请求解析 tenant 与主体，并执行资源级授权 |
| 数据归属 | `owner_id` 多数写为固定开发用户 ID | 明确 `tenant_id`，为所有业务、审计、缓存和异步任务回填并强制非空 |
| 查询隔离 | 没有 tenant 条件 | Repository/服务层默认作用域、数据库约束与跨租户访问测试 |
| 文件与报告 | 同一 storage 根/桶保存对象 | tenant 前缀、对象授权、迁移校验与跨租户不可枚举测试 |
| 缓存与任务 | LLM 缓存、批任务和观测数据按现有业务身份组织 | 缓存键、任务租约、导出和监控指标都纳入 tenant identity |
| 管理能力 | 没有 RBAC | tenant 管理员/评分者/审核者等最小权限模型与审计日志 |

公开的 `/api/auth/*` 与 `/api/system/*` 为登录和部署自检保留；在多租户设计中也必须逐项审查响应内容，避免暴露其他租户的运行、配置或计数信息。

## 迁移前冻结与备份要求

多租户改造开始前，先从本 release 分支或标签构建可复现工件，并执行以下不可逆变更前的备份。备份不得提交到仓库，且不得包含密钥。

1. 记录部署的 Git revision、`v0.2.0` 标签、Alembic head、运行时配置的**键名/非敏感值**和已批准的发布清单。
2. 使用 `python -m backend.app.scripts.ops_backup create` 同时备份 PostgreSQL 与 storage；在隔离的恢复库、空 storage 目标上先执行 `ops_backup verify`，再演练恢复。
3. 导出每个现有资源的稳定 ID、现有 `owner_id`、创建/更新时间、关联关系及 storage object key；保留映射清单和 SHA-256，不把论文原文、成绩或 token 写入代码库。
4. 冻结已发布 `RubricVersion`、评分运行、DocumentSnapshot、报告与评估门禁的不可变身份。迁移只能新增 tenant 归属或映射，不能重写历史内容 hash、评分证据或审核事件。
5. 对生产库先做只读盘点：空 `owner_id`、多个 `owner_id`、孤儿 storage 对象、跨批次引用、未完成批任务和未过期租约。任何无法归属的记录必须人工裁决，不得默认分配到新租户。

## 推荐的改造顺序

1. 先定义 tenant、用户、成员关系和角色的不可变合同，并明确系统级运维主体是否属于任一 tenant。
2. 新建迁移，为每张业务表、异步任务、审计记录和 storage 元数据增加 `tenant_id`；先允许仅为迁移回填的临时空值，回填、校验和索引完成后再改为 `NOT NULL`。
3. 将认证从共享凭据改为可验证主体；请求上下文必须同时提供 `tenant_id` 与 subject，禁止客户端直接指定任意 tenant。
4. 在服务、查询、导出、评分、缓存和 storage 入口统一强制 tenant scope；数据库层增加必要的复合唯一约束、外键或 Row Level Security（若采用）。
5. 增加跨租户读、写、导出、对象访问、缓存命中和任务恢复的负向测试；先在隔离副本演练回填与回滚，再按租户分批发布。
6. 保持本 release 可恢复，直到迁移后的备份恢复、数据对账、权限回归和人工验收全部通过。

## 不能作为迁移依据的事项

- `owner_id` 存在不表示该记录已经隔离，也不表示其值一定是最终 tenant。
- 共享登录用户名、`DEFAULT_DEV_USER_ID`、文件路径前缀和数据库连接信息都不是 tenant identity。
- 不得为追求“多租户兼容”而修改已发布评分标准、评分运行、证据、内容 hash 或历史审核记录。
- 任何租户数据、学生论文、成绩、密码、token、服务角色密钥和完整连接串均不得加入 Git。
