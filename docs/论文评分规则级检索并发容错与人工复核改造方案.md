因此，本次候选版本的发布目的，是修复超长请求和整篇失败扩散，并建立人工兜底；不是开启 Core 默认切换，也不是宣告全部目标架构完成。

本方案解决论文 Core 评分链中的四个相互关联的问题：

1. 当前每个语义原子规则都会携带整篇论文的全部 `evidence_units`，导致单次 Prompt 远超模型上下文限制。
2. 当前批处理只在论文之间并发，同一篇论文内的规则仍串行；若直接增加规则级并发，会同时放大超长请求和 Provider 限流风险。
3. Groq HTTP 异常会从单个语义规则向上传播并终止整篇论文，缺少规则级检查点、延迟重试、连接熔断和部分成功持久化。
4. 当前已经具备 `blocked`、空总分、`pending_review`、`resolve_block` 和 `ReviewLog`，但 Provider 请求在生成可持久化 Outcome 之前失败，无法进入正式人工复核闭环。

目标架构是：

```text
文档解析一次
    ↓
结构化事实 + 原文证据块 + 章节层次索引
    ↓
每个原子规则生成独立的证据检索请求
    ↓
章节过滤 + BM25 + 语义检索 + 重排 + 邻接扩展
    ↓
Token Budget 预检，仅选择受控 Top-K 原文证据
    ↓
无状态 RuleScoringTask 按依赖 DAG 有界并发调用 LLM
    ↓
规则级检查点、缓存、重试、熔断、失败隔离
    ↓
代码按冻结规则确定性聚合
    ↓
必要规则失败：空总分 + pending_review + 人工复核任务
    ↓
全部阻塞项解决后生成正式总分和等级
```

实施顺序必须是：

1. 先建立错误分类、Token Budget 和评分项专属证据检索，解决当前 400。
2. 再建立规则级持久化、部分成功和人工复核闭环。
3. 最后开启按依赖图的有界并发，避免嵌套并发和 Provider 错误风暴。

本方案不授权切换默认 Core、不绕过 GATE-03、不使用本地论文作为仓库 fixture，也不把外部论文或其正文提交到 Git。

## 1. 现状与事故事实

### 1.1 已确认的直接故障

生产任务使用：

- Provider：`openai_compatible`
- 平台：Groq
- 模型：`openai/gpt-oss-120b`
- 端点：`/openai/v1/chat/completions`

三篇论文均已成功完成上传、对象存储读取和文档解析，请求到达 Groq 后返回 HTTP 400。模型本身有效，认证也没有返回 401/403。

使用相同生产解析链对三份本地对应 DOCX 做只读核算，得到以下聚合指标。原始文件没有复制、上传或加入仓库：

| 样本 | 原文字符数 | Evidence Units | Evidence + Extension 字符数 | 粗略 Token 区间 |
|---|---:|---:|---:|---:|
| A | 54,653 | 938 | 535,773 | 160k–237k |
| B | 46,088 | 746 | 435,265 | 137k–208k |
| C | 37,284 | 632 | 358,782 | 108k–161k |

`openai/gpt-oss-120b` 的单请求上下文窗口为 131,072 tokens，且输入与输出共享上下文。因此两份样本在保守估算下已超限，第三份在加上系统指令、评分规则和输出预算后也处于高风险区。

### 1.2 代码根因

当前 Core Prompt 组装存在以下行为：

1. `LegacyPaperAdapter` 将每个段落扩展为带内容哈希、证据 ID、章节路径、序号、定位器等字段的 evidence unit。
2. `scoring/core/engine.py::_prompt_envelope()` 将 `document["evidence_units"]` 全量放入每个原子规则的 PromptEnvelope。
3. `openai_compatible_adapter.py::score_core_envelope()` 将整个 Envelope 序列化为一个 user message。
4. 每个语义规则重复发送同一篇论文的大量无关内容和重复身份字段。
5. 调用前没有 Provider-aware token 预检，错误只能由 Groq 返回。

因此，直接原因是单请求超过 Groq 上下文限制；系统根因是缺少评分项专属检索、证据选择合同和 Token Budget。

### 1.3 当前并发与失败边界

当前批任务通过 `ThreadPoolExecutor` 并发不同论文，`max_workers` 为 1–16。单篇论文内部：

- AtomicRule 已有 `depends_on_rule_codes`，执行计划具备 DAG 数据基础。
- `execute_rule_plan()` 仍按拓扑顺序同步 `for` 循环执行。
- HTTP 异常在 `llm_runtime.score()` 处直接向上传播。
- 批任务能够隔离不同论文，但不能隔离同一论文中的不同规则。

结果是：

```text
单规则 Groq 失败
    → 当前论文剩余规则不再执行
    → 论文级 BatchScoringItem 失败
    → 其他论文继续
```

### 1.4 当前人工复核基础与断点

系统已经具备：

- `ScoreItem.auto_score_status = calculated | invalid | blocked`
- `ScoringOutcome.status = completed | review_required | blocked`
- `blocked` Outcome 的 `final_total` 和 `grade` 必须为空
- `ScoringRun.need_manual_review`
- Submission/Paper 的 `pending_review`
- 教师/组织管理员执行 `resolve_validation`、`resolve_block`
- `ReviewLog` 保存处理前后分数、理由、复核人和 policy hash
- 未解决的 invalid/blocked 项禁止提交最终复核

当前断点是 Provider 异常发生在 Outcome 持久化之前，因此不会产生可处理的 blocked ScoreItem，也不会生成正式的人工复核待办。

## 2. 目标与非目标

### 2.1 目标

1. 所有模型请求在发出前满足明确、可审计的 Token Budget。
2. 每个语义规则只接收与该规则相关、数量受控且可回溯的原文证据。
3. 确定性规则不调用 LLM；语义规则只负责受限判定，不负责最终算分。
4. 无依赖规则可有界并发，有依赖规则按 DAG 分层执行。
5. 并发额度按 AI connection 全局控制，而不是按论文嵌套放大。
6. Provider 失败隔离到单个规则，并支持规则级缓存、重试、恢复和定向重试。
7. 自动重试耗尽且阻塞总分的规则进入正式人工复核队列。
8. 任何必需项未解决时，正式总分和等级保持为空。
9. 所有检索、Prompt、模型、错误、人工处理和聚合身份可审计、可回放。
10. 保留现有 V3 历史回放，不修改已发布合同的含义。
11. 使用 OpenTelemetry 标准埋点和自托管 Langfuse 观测评分 Trace，且不将观测平台变成评分事实来源。

### 2.2 非目标

- 不引入可以自由行动、调用任意工具或互相对话的通用 Agent 框架。
- 不把每个评分项做成长会话、有记忆的 subagent。
- 不通过切换更长上下文模型掩盖 Prompt 膨胀问题。
- 不允许模型直接决定授权外扣分、总分或等级。
- 不使用检索失败证明全文不存在某内容。
- 不静默切换 Provider 或模型。
- 不在本阶段改变默认 `SCORING_ENGINE_MODE`。
- 不将本地论文、正文片段、真实学生材料或 API Key 写入仓库、日志或测试 fixture。
- 不在代码中硬编码生产并发数、Top-K、人工复核 SLA 或发布阈值。
- 不把 Langfuse Trace 当作权威评分结果、证据、任务状态或人工复核记录的唯一存储。
- 不默认向 Langfuse 发送完整 Prompt、完整论文正文、API Key、Authorization 或隐藏思维链。

## 3. 稳定设计原则

### 3.1 确定性优先

以下任务优先由代码处理：

- 必需章节、字数、引用数量、图表编号、格式事实。
- 已发布规则的分值、封顶、互斥、依赖、档位分数和最终聚合。
- 原文 quote 与 evidence unit 的逐字匹配。
- 全文级“是否缺失”的可穷举检查。

LLM 只处理需要语义判断的原子规则，并只返回：

- `triggered | not_triggered | not_applicable | insufficient_evidence`
- 已发布 `level_code`
- 已授权 finding code
- 原文 evidence ID 和逐字 quote
- 可选的简短理由、置信度和人工复核建议

### 3.2 评分项专属上下文

一次 Provider 调用只判断一个原子规则。模型看到：

1. 不可变安全指令。
2. 当前 criterion 和 atomic rule。
3. 必要的论文级短上下文。
4. 与当前规则相关的受控 Top-K 原文证据。
5. 少量已批准校准锚点。
6. 严格输出 Schema。

哈希、完整 locator、数据库 ID 和重复身份字段留在服务端；模型只接收短证据 ID、章节、位置和原文。

### 3.3 无状态 Rule Worker，而非通用 Subagent

每个评分任务是一个无状态、可重放的 `RuleScoringTask`：

```text
输入 = 冻结规则 + 冻结证据选择 + 冻结 Runtime Identity
输出 = 受验证的 SemanticRuleResponse
```

任务不能：

- 改写评分标准。
- 访问其他论文。
- 自由选择工具。
- 保存会话记忆。
- 计算最终总分。
- 与其他 Rule Worker 自由协商。

### 3.4 Fail-closed

- Provider 失败不能解释为学生得 0 分。
- Provider 失败不能解释为不扣分或满分。
- 必需规则失败时不生成正式总分。
- 只有全部阻塞规则自动成功或经授权人工解决后才能聚合正式成绩。

### 3.5 不可变身份与版本化演进

当前 `PromptEnvelopeV3` 是已发布合同，不应增加隐式字段或改变“授权证据集合”的历史含义。推荐新增 `PromptEnvelopeV4`，显式加入证据选择身份；V3 继续用于历史回放和兼容路径。

## 4. 目标组件设计

### 4.1 文档证据索引

解析阶段一次性生成：

1. 原文 Evidence Unit：最终引用和证据验证的权威来源。
2. 结构化 Section Map：章节标题、层级、顺序、证据 ID 范围。
3. 检索 Chunk：按结构切分的若干连续 evidence units。
4. Context Header：约 50–100 tokens 的章节/片段背景，仅用于检索和模型理解。
5. 章节结构化摘要：用于全文一致性和跨章节导航，不能作为最终扣分证据。

建议初始参数仅作为评估起点，不作为生产硬编码：

- Chunk：约 400–800 tokens，优先尊重段落和章节边界。
- 重叠：约 10%–15%。
- 初始召回：30–100 个候选。
- 重排后：8–20 个证据块。
- 邻接扩展：命中块前后 0–1 个块，受 Token Budget 约束。

所有参数由 Profile 或经授权配置提供，进入版本身份和审计记录。

### 4.2 评分项证据检索

新增 Profile-neutral 检索端口：

```text
EvidenceRetriever.select(
    document_snapshot,
    criterion_snapshot,
    atomic_rule_snapshot,
    retrieval_policy,
    token_budget,
) -> EvidenceSelectionSnapshot
```

检索顺序：

1. 章节路由：依据 Profile、criterion、evidence hints 和规则类型过滤候选章节。
2. 确定性匹配：章节名、关键词、表格、图号、引用、代码或术语。
3. BM25：准确词法召回。
4. 向量召回：语义相似内容。
5. Rank Fusion：合并并去重。
6. Reranker：按当前规则重排。
7. 多样性控制：避免 Top-K 全部来自同一段落或重复表述。
8. 邻接扩展：补充局部上下文。
9. Token Budget 裁剪：保留最高价值、可验证证据。

`EvidenceSelectionSnapshot` 至少包含：

```json
{
  "schema_version": "evidence-selection-snapshot@1",
  "selector_version": "...",
  "criterion_code": "...",
  "rule_code": "...",
  "query_projection": {},
  "selected_evidence_unit_ids": [],
  "section_coverage": [],
  "coverage_mode": "top_k | exhaustive | hierarchical",
  "token_budget": {},
  "selection_hash": "..."
}
```

不得把检索相似度分数直接发送给判分模型，避免形成额外评分偏置；分数保留在检索审计中。

### 4.3 三类证据覆盖模式

#### Top-K 局部语义判断

适用于：

- 是否描述某种技术方法。
- 实验设计质量。
- 结果分析深度。
- 创新点是否具体。

#### Exhaustive 全文覆盖

适用于：

- 必需章节是否存在。
- 全文是否完全缺少某类明确元素。
- 图表、引用、关键词和格式事实。

优先使用确定性代码；若必须语义判断，则按所有相关章节 map，再由代码聚合，不能用普通 Top-K 的“未命中”作为缺失证明。

#### Hierarchical 跨章节判断

适用于：

- 研究目标与结论一致性。
- 方法、实验和结论是否闭环。
- 摘要与正文是否矛盾。
- 创新点是否贯穿全文。

流程：章节结构化摘要导航 → 选取相关章节 → 回查原文证据 → 跨章节规则判定。最终证据仍必须引用原文 Evidence Unit。

### 4.4 PromptEnvelopeV4

V4 在 V3 基础上新增：

- `evidence_selection_identity`
- `token_budget_identity`
- `coverage_mode`
- 只包含选中的短 Evidence Projection
- 可选的章节级短上下文，但不能替代原文证据

Evidence Projection 建议：

```json
{
  "evidence_id": "E01",
  "section_path": ["5 实验", "5.2 结果分析"],
  "location": "paragraph:18",
  "normalized_text": "..."
}
```

服务端维护：

```text
E01 → evidence_unit_id → unit_text_hash → authoritative locator
```

V4 响应继续复用或版本化现有 `SemanticRuleResponseV2`；若新增 `insufficient_evidence`、`confidence` 或 `review_reason`，必须显式发布新响应版本，不能扩展已冻结 Schema。

### 4.5 Provider-aware Token Budget

新增模型能力注册表：

```text
provider
model
context_window
max_output_tokens
tokenizer/estimator
recommended_input_budget
service_tier constraints
```

预算公式：

```text
available_input
= context_window
 - system_and_rule_tokens
 - reserved_output_tokens
 - safety_margin_tokens
```

要求：

1. Prompt 构建后、本地调用前再次计算最终 token。
2. 超预算时按重排顺序移除最低价值证据，不截断 JSON 或 quote。
3. 仍超预算则返回稳定内部错误 `TOKEN_BUDGET_UNSATISFIABLE`，不得调用 Provider。
4. 记录 estimator version、估算 token、实际 Provider usage 和偏差。
5. Provider 没有可用 tokenizer 时使用保守估算，并通过生产 usage 持续校正。

### 4.7 DAG 分层执行

从 `depends_on_rule_codes` 构建拓扑层：

```text
Layer 0：所有无依赖规则
Layer 1：依赖 Layer 0 的规则
Layer N：依赖已完成前置规则的规则
```

执行原则：

- 确定性规则可优先完成并立即持久化。
- 同一 Layer 的语义规则可以并发。
- 下游规则仅在依赖结果满足规则语义时进入 pending。
- 依赖失败不影响无关分支。
- blocking rule 失败只阻塞其 criterion 和依赖分支，不终止整个论文执行器。
- 所有独立任务完成后再聚合 CriterionOutcome 和 ScoringOutcome。

不在每篇论文内部创建独立线程池；所有任务进入同一个按 AI connection 管理的调度器。

### 4.8 AI Connection 全局并发与流量控制

每个 AI connection 共享：

- 并发 Semaphore。
- RPM token bucket。
- TPM/ITPM/OTPM 预算。
- Provider 响应头快照。
- Retry-After 调度。
- Circuit Breaker。

安全并发由账户实际限制、平均 Prompt tokens 和平均延迟计算。生产默认值必须来自经授权配置，不能根据 Groq 公共套餐表自动假定。

避免：

```text
paper_concurrency × rule_concurrency_per_paper
```

形成不可控的嵌套乘法。

推荐调度策略：

- 每个组织和 connection 保证公平队列。
- 大 Prompt 请求按估算 token 预约额度。
- 429 根据 `Retry-After` 进入 `retry_wait`。
- Worker 不使用长时间 `sleep`；设置 `next_attempt_at` 后释放执行槽。
- 批次取消时取消未领取任务，已完成任务保留。

### 4.9 错误分类和处理矩阵

| HTTP/错误 | 分类 | 默认处理 |
|---|---|---|
| 400 `context_length_exceeded` | request_reducible | 缩小证据后最多重建一次 Envelope |
| 其他 400 | request_permanent | 不盲目重试，记录脱敏错误并阻塞规则 |
| 401/403 | connection_permanent | 立即打开连接熔断器，任务 deferred，要求重新认证 |
| 404 | connection_config | 暂停连接，等待修正模型或 URL |
| 408/409 | transient | 有界指数退避 |
| 413 | request_reducible | 缩小请求后重试一次 |
| 422 | response_or_semantic | 严格 Schema 修正重试一次，仍失败则阻塞 |
| 429 | rate_limited | 遵守 Retry-After，降低动态并发 |
| 498 | flex_capacity | 抖动退避；经授权可切同模型 on-demand/auto |
| 499 | canceled | 不重试 |
| 500/502/503/504 | provider_transient | 有界指数退避和 jitter |
| timeout/transport | network_transient | 有界重试 |
| 响应 JSON 无效 | response_invalid | 修正重试一次 |
| quote/证据验证失败 | evidence_invalid | 修正重试一次，仍失败则人工复核 |

保存经过白名单过滤的 Provider 错误信息：

- HTTP status
- `error.type`
- `error.code`
- 脱敏 `error.message`
- Provider request ID
- Retry-After 和 rate-limit headers

禁止记录：Authorization、API Key、完整 Prompt、完整论文正文或未脱敏 Provider body。

#### 4.9.1 OpenTelemetry + Langfuse 可观测性

选型决策：使用 OpenTelemetry 作为与平台无关的埋点和上下文传播标准，使用自托管 Langfuse 作为 LLM Trace、输入输出诊断、Token/延迟分析和后续评估界面。业务数据库仍是评分、证据、规则任务、人工复核和发布状态的唯一权威来源；Langfuse 不参与计分和业务状态转换，Langfuse 暂时不可用也不得使评分请求失败。

部署边界：Langfuse 作为独立的持久化服务部署，不嵌入 Vercel Serverless 评分进程。应用只通过环境变量获取 Langfuse/OTLP endpoint 和密钥，仓库不保存生产凭据。Langfuse 版本、健康检查、备份、保留和升级回退纳入上线清单，但它的备份不替代业务数据库备份。

稳定 Trace 层级：

```text
batch_scoring
└─ scoring_run
   ├─ document_parse
   ├─ rule_scoring_task
   │  ├─ evidence_retrieval
   │  ├─ token_preflight
   │  ├─ llm_generation
   │  ├─ response_validation
   │  └─ retry_attempt
   └─ score_aggregation
```

所有 Span 使用稳定名称，并根据边界附加：

- `organization_id`、`batch_job_id`、`scoring_run_id`；P2 引入规则任务后再附加 `rule_scoring_task_id`。
- Profile、criterion code、atomic rule code 和 coverage mode。
- document/rubric/policy/prompt/evidence selection/token policy 的版本或 hash。
- Provider、connection ID、请求模型、实际响应模型和 service tier。
- 估算/实际 input/output token、预留输出空间、上下文使用率、延迟、重试次数和结束原因。
- ProviderError code、HTTP status、Provider request ID、Retry-After 和白名单限流响应头。
- 选中的 Evidence Unit ID、section path、裁剪标记、Schema/引用校验结果。

内容采集采用“指标全量、内容受控”的双通道策略：

1. Langfuse 常规 Trace 默认只保存身份 hash、证据 ID、章节路径、Token、延迟、模型参数、错误分类和校验结果。
2. 需要观察文本时，在应用内完成脱敏和长度限制后再导出；脱敏处理发生在 OTLP/Langfuse 网络发送之前。
3. 完整 Prompt/响应如确有事故调查需要，仅进入系统内部的加密审计存储，应用 RBAC、访问日志和短保留周期，不直接复制到观测平台。
4. 错误、人工复核和发布观察 Trace 100% 采集；普通成功 Trace 按经授权的比例采样。
5. 采样、脱敏、保留周期和内容查看权限是生产策略，必须配置化并进入发布审核。

禁止记录隐藏思维链。只记录结构化评分决定、证据引用、简短理由、置信度和校验结果。

### 4.10 Circuit Breaker

每个 AI connection 独立状态：

```text
closed → open → half_open → closed/open
```

建议策略必须配置化并通过测试：

- 401/403：立即 open，直到连接重新认证或管理员恢复。
- 连续 transient 错误或滚动窗口失败率超过阈值：短期开启。
- open 状态新任务进入 `deferred_provider`，不制造错误风暴。
- 冷却后 half-open 只放行一个小请求。
- 成功关闭，失败重新打开。

连接级事故不得立即为每篇论文创建大量人工任务；先创建一个 Provider Incident。超过业务 SLA 或确认无法恢复后，再把仍阻塞的必需规则转人工。

### 4.11 人工复核任务

在现有 `ScoreItem`、`ReviewLog` 和 review service 基础上新增 `ManualReviewTask`，用于待办、领取、SLA 和去重：

```text
id
organization_id
scoring_run_id
rule_scoring_task_id
score_item_id
criterion_code/rule_code
trigger_code/trigger_message
blocking_final_total
status
priority
assigned_reviewer_id
claimed_at/due_at/resolved_at
resolution_type
version
created_at
```

状态：

```text
open → claimed → resolved
             ↘ canceled/superseded
```

触发条件：

1. 必需规则自动重试耗尽。
2. 永久请求错误无法自动修正。
3. 多次返回不合法 Schema 或无效证据。
4. 文档解析或证据覆盖不足，无法形成合法自动结果。
5. Provider Incident 超过已批准 SLA，且阻塞正式总分。

人工操作：

- 仅重试当前失败规则。
- 人工评分/选档，必须给出理由和原文证据。
- 在规则允许时标记 not applicable。
- 退回材料，标记 `resubmission_required`。

正式总分条件：

```text
blocking_manual_review_task_count == 0
AND 所有必需 CriterionOutcome 均可聚合
AND final_total_score IS NOT NULL
AND grade IS NOT NULL
```

人工评分不能覆盖不可变 RuleDecision；必须作为独立 human resolution/contribution 持久化，并继续写 ReviewLog。

### 4.12 人工复核权限与并发控制

- 沿用 `teacher`、`org_admin` 处理权限。
- 任务领取后使用乐观锁 `version` 防止重复提交。
- 提交时验证组织可见性、分数范围、resolution capability 和证据来源。
- 可配置双人复核：零分/满分、大幅覆盖、规则本身疑似错误或大面积 Provider 事故。
- ReviewTask、ReviewLog 和最终导出明确区分自动结果、人工解决阻塞、普通人工调整和重新自动评分。

## 7. 分阶段执行计划

### 阶段 P0：冻结基线与事故可观测性

目标：在不改变评分结果的前提下，让 Provider 错误可分类、可度量，并能在 Langfuse 中按论文、规则和 Provider 请求还原执行链路。

工作：

1. 定义稳定的 `ProviderError` 分类和错误码。
2. 保存脱敏 Groq error body、request ID、Retry-After 和 rate-limit headers。
3. 为所有 Provider 增加相同的错误投影合同。
4. 增加 Prompt 字符数、估算 token、实际 usage 和模型上下文指标。
5. UI 用可操作错误替代裸 `httpx.HTTPStatusError`。
6. 定义稳定的 OpenTelemetry Trace/Span 命名、关联 ID 和 GenAI 属性映射。
7. 接入自托管 Langfuse；SDK/Exporter 失败时 fail-open，不影响评分主链。
8. 在应用端实现 Langfuse/OTel Span 脱敏、内容长度限制和采样策略。
9. P0 执行期间先以最终会原样持久化到 `ScoringRun.idempotency_key` 的 `scoring_request_id` + criterion/rule identity 打通业务审计记录与 Langfuse Trace；落库后即可由 ScoringRun 反查同一请求身份。P2 引入规则任务后再增加 `scoring_run_id` 与 `rule_scoring_task_id`。业务侧只保存平台无关的 Trace ID，不保存绑定 Langfuse 部署域名的 URL，也不在 Langfuse 中保存权威任务状态。
10. 建立基础看板：ProviderError 率、上下文使用率、Token、p50/p95 延迟、重试率、Schema/证据校验失败率。

测试：

- 400 context、401、413、422、429、498、5xx、timeout fixture。
- 确认 Key、Authorization、完整 Prompt 和正文不进入日志。
- 确认错误码可稳定持久化和展示。
- 确认一次评分的 Parse/Retrieval/Token/LLM/Validation Span 共享同一 Trace，规则级可单独过滤。
- 确认学生姓名、学号、API Key、完整原文和未脱敏 Provider body 在导出前被拒绝或替换。
- 确认 Langfuse 不可达、超时或 Exporter 队列满时，评分和权威审计持久化仍正常。
- 确认错误/人工复核 Trace 全量采集，成功 Trace 采样决策在 Trace 级保持一致。

验收：

- 生产同类错误能够区分 context、auth、rate limit、capacity 和 provider outage。
- 维护者可从业务页面的 `scoring_run_id` 取得其持久化 `idempotency_key`，再以同值的 `scoring_request_id` 定位 Langfuse Trace，并看到规则级输入身份、Token、延迟、重试、错误和校验结果；P2 后可直接按 run/task ID 定位。
- Langfuse 中不存在未经批准的完整论文/Prompt，且观测失效不影响评分正确性和可恢复性。
- 不改变现有分数或执行顺序。

回滚：先关闭 Langfuse Exporter，保留应用内 ProviderError 分类、Trace ID 和原异常链；不回滚业务审计数据。

### 阶段 P1：Token Budget 与评分项证据选择

目标：解决当前 Groq 400，确保每个请求受控且与当前评分项相关。

工作：

1. 定义 `EvidenceRetriever` 和 `EvidenceSelectionSnapshot`。
2. 先以章节过滤 + 现有 chunk/BM25 或等价轻量检索实现可解释基线。
3. 增加向量召回、Rank Fusion、reranker 和邻接扩展。
4. 实现 local token preflight 和安全裁剪。
5. 发布 PromptEnvelopeV4；V3 保持只读回放。
6. Prompt/缓存版本升级，selection hash 进入缓存和运行身份。
7. 对缺失证明和跨章节规则分别实现 exhaustive/hierarchical 路由。

测试：

- 三类长论文合成 fixture，不使用真实学生正文。
- 每个请求都低于配置预算。
- quote 仍能映射到完整权威 Evidence Unit。
- Top-K 未命中不能被解释为全文缺失。
- V3 fixture 回放不变。
- 改检索/Prompt 后重新跑 QWK 留出集并保存新基线。

验收：

- 长文档不再产生 Provider context-length 拒绝。
- Prompt token 显著低于上下文上限且保留必要输出空间。
- 检索 Recall@K、证据正确率和 QWK 达到维护者批准的门槛。

回滚：Feature Flag 切回 V3/all-evidence，仅限安全长度材料；超长材料保持 fail-closed，不能重新放开无预算请求。

### 阶段 P2：规则级检查点与部分成功持久化

目标：单规则失败不再终止整篇论文。

工作：

1. 增加 `RuleScoringTask` 迁移、模型和服务。
2. 执行计划展开时创建规则任务和依赖关系。
3. 确定性规则、语义规则分别持久化结果。
4. Provider 异常转换为规则状态，不直接终止 ScoringRun。
5. 无关规则继续执行；依赖分支精确 skip/defer。
6. 所有任务终态后构造部分或完整 Outcome。
7. 增加“只重试失败规则”和应用级幂等。

测试：

- 中间规则失败后其他独立规则成功。
- 下游依赖准确跳过，不影响旁支。
- 进程中断、租约过期、重复领取和重复回调。
- 同一 Envelope 不产生两个权威结果。
- 取消、恢复、失败项重试和代际隔离。

验收：

- 单规则失败不会丢失已成功规则。
- 重试失败项不会重复调用成功项。
- 批任务与论文进度能精确到规则。

回滚：保留新表，调度器切回 sequential；不删除已产生的审计记录。

### 阶段 P3：人工复核队列和正式总分阻塞

目标：自动失败耗尽后形成可领取、可解决、可审计的人工任务。

工作：

1. 增加 `ManualReviewTask` 迁移、服务、API 和 UI。
2. 定义 trigger code、优先级、SLA、领取和乐观锁。
3. 将 failed_exhausted required rule 转换为 blocked ScoreItem/criterion。
4. 复用 `resolve_block`、重算和 ReviewLog。
5. 人工评分强制理由和原文证据。
6. 所有阻塞项解决前 final_total/grade 为空。
7. 连接级事故去重为 Provider Incident，避免任务风暴。

测试：

- 必需规则失败时正式总分为空。
- 非阻塞 report-only 失败按批准 policy 处理。
- 未处理 blocked 项不能提交 review。
- 最后一个阻塞项解决后确定性重算总分。
- 教师/管理员权限、跨组织访问、双人抢占和乐观锁。
- ReviewLog 不可缺失，导出能区分 AI 与人工。

验收：

- 所有阻塞自动失败都能进入人工队列或明确的 Provider Incident。
- 不存在失败项静默按 0、满分或不扣分聚合。
- 审计可回答“谁、何时、基于什么证据、为什么给出该分数”。

### 阶段 P4：DAG 有界并发与全局 Provider 调度

目标：在正确性和恢复能力已完成后缩短评分耗时。

工作：

1. 实现拓扑分层调度。
2. 增加每 connection 全局 Semaphore 和 RPM/TPM 预算。
3. 使用 `next_attempt_at` 延迟队列替代 Worker `sleep`。
4. 实现动态并发降低、Retry-After、jitter 和 Circuit Breaker。
5. Provider Incident 和 half-open 探测。
6. 保留 sequential feature flag 作为即时回退。

测试：

- DAG 顺序、并发上限、依赖 barrier。
- 多论文 × 多规则不产生嵌套超额并发。
- 429/498 风暴下公平调度、熔断和恢复。
- 一个 connection 故障不影响其他 connection/tenant。
- 取消期间不调度新任务。
- 线程/协程安全和 SQLAlchemy Session 隔离。

验收：

- 无依赖规则可并发，依赖语义保持不变。
- 实际并发永不超过 connection 配置。
- p95 延迟改善且 429/498/失败率不超过维护者批准阈值。

回滚：`RULE_EXECUTION_MODE=sequential`，规则检查点和人工复核仍继续使用。

### 阶段 P5：Groq 服务层与大规模离线批处理

目标：按业务实时性选择 on-demand、flex、auto 或 Batch，而不改变模型评分身份。

工作：

1. 同步交互评分默认使用经授权 service tier。
2. 付费账户可配置 Flex，并处理 498。
3. 允许经授权的同模型 tier fallback，记录实际 tier。
4. 对夜间批量、QWK 和大规模重评分评估 Groq Batch API。
5. 不静默切换模型；任何模型 fallback 都要求单独校准和版本身份。

验收：

- service tier 进入 Runtime Identity 和 usage ledger。
- Batch 结果可按 `custom_id` 幂等映射回 RuleScoringTask。
- 同步与 Batch 的结果差异完成评估。

### 阶段 P6：发布、观察与默认路径决策

目标：完成完整 CI、真实数据校准、观察期和回退演练。

工作：

1. 全套自包含测试、Postgres 迁移、备份恢复和 Docker 冒烟。
2. 长文档、并发、故障注入和人工复核 E2E。
3. QWK 留出集重新锚定基线。
4. Shadow 模式比较 all-evidence legacy/V3 与 scoped V4；超长样本只比较可运行路径，不伪造 legacy 结果。
5. 逐步开启 scoped retrieval、rule checkpoints、manual review、DAG concurrency。
6. 完成 `docs/上线清单.md` 和回退演练。
7. GATE-03 仍按既有发布流程独立完成；本方案的运行观察不得自动授予默认 Core 权限。

## 8. Feature Flags 与回退面

建议配置：

```text
SCORING_PROMPT_ENVELOPE_VERSION=v3|v4
SCORING_EVIDENCE_SELECTION_MODE=all|scoped
SCORING_RULE_TASKS_ENABLED=false|true
RULE_EXECUTION_MODE=sequential|dag_shadow|dag
MANUAL_REVIEW_QUEUE_ENABLED=false|true
PROVIDER_CIRCUIT_BREAKER_ENABLED=false|true
PROVIDER_GLOBAL_CONCURRENCY=<authorized value>
PROVIDER_TOKEN_BUDGET_POLICY=<versioned policy ref>
LLM_OBSERVABILITY_ENABLED=false|true
LLM_OBSERVABILITY_EXPORTER=none|langfuse
LLM_OBSERVABILITY_CONTENT_MODE=metadata_only|redacted
LLM_OBSERVABILITY_SUCCESS_SAMPLE_RATE=<authorized 0..1>
```

要求：

- Flag 必须写入 Runtime Identity 或运行审计。
- 回退不删除新表、不覆盖历史结果。
- `scoped → all` 回退必须仍经过 token preflight；超长文档不能恢复为危险全量 Prompt。
- DAG 回退到 sequential 不改变 Prompt、规则或分数身份。
- 人工复核关闭时，blocked Outcome 仍保持空总分，不能降级为自动通过。

## 10. 验收矩阵

| 维度 | 必须证明 |
|---|---|
| 上下文安全 | 所有请求在发出前满足模型上下文和输出预留预算 |
| 检索正确性 | 当前规则的必要证据在批准的 Recall@K 门槛内；证据可回到权威原文 |
| 缺失判断 | Top-K 未命中不会被当成全文缺失；exhaustive 模式可审计 |
| 分值授权 | LLM 不能返回授权外 rule、档位或 points；代码仍是唯一计分权威 |
| 规则隔离 | 一个规则失败不阻止无关规则和其他论文 |
| 依赖正确性 | 下游只受声明依赖影响，旁支继续 |
| 幂等恢复 | 进程中断或重复调度不产生重复权威结果和重复扣费 |
| Provider 容错 | 429/498/5xx/timeout 有界重试；401/403 熔断；Worker 不长时间 sleep |
| LLM 可观测性 | 一次评分可按 run/rule 还原 Parse/Retrieval/Token/LLM/Validation 链路；Langfuse 故障不影响主链 |
| 观测数据安全 | 默认 metadata-only；文本导出前脱敏；完整论文/Prompt/密钥不进 Langfuse |
| 人工复核 | 必需规则失败后总分为空；所有阻塞项解决后才可发布 |
| 审计 | 可回答 Prompt/检索/模型/错误/人工处理/聚合的完整身份链 |
| 多租户 | 任务、错误、证据和复核严格按组织隔离 |
| 隐私 | 日志和仓库不含 API Key、完整 Prompt、真实论文正文或本地论文 fixture |
| 质量 | QWK、证据有效率、公平性和人工复核率达到维护者批准门槛 |
| 性能 | DAG 并发降低延迟且不突破 connection 并发、RPM/TPM 和失败阈值 |
| 发布 | 全量 CI、Postgres 迁移、备份恢复、上线清单和回退演练通过 |

## 11. 关键风险与缓解

| 风险 | 缓解 |
|---|---|
| 检索遗漏导致评分偏低 | 章节路由 + BM25 + 向量 + rerank + Recall@K 标注集；不足时人工复核 |
| 摘要引入幻觉 | 摘要只用于导航；最终决定必须引用权威原文 |
| Top-K 无法证明缺失 | 缺失类规则强制 exhaustive/deterministic coverage |
| 并发放大 429/成本 | connection 全局 token bucket、动态并发和预算预约 |
| 重试造成重复扣费 | Envelope hash、规则级幂等、缓存和 attempt history |
| Provider 大面积故障产生复核洪峰 | Provider Incident 去重、deferred 状态和 SLA 后再转人工 |
| 人工覆盖破坏可比性 | 冻结原自动结果，human contribution 独立审计，必要时双人复核 |
| 静默模型 fallback 改变尺度 | 禁止静默切换；模型变化必须新 Runtime Identity 和 QWK 校准 |
| 合同升级破坏历史回放 | 发布 V4，V3 保持不可变 fixture 和 replay 测试 |
| Vercel 长任务中断 | 持久化规则任务、短租约、可恢复领取，避免依赖进程内状态 |

## 12. 需要维护者确认的策略项

以下内容在代码实现前必须由维护者或授权用户确认，不能由系统预填为生产默认：

1. 每个 Profile/规则类型的 Top-K、chunk size、覆盖模式和 token safety margin。
2. Groq 账户实际 RPM/TPM/ITPM/OTPM、service tier 和最大并发。
3. 429/498/5xx 的最大重试次数、总重试窗口和 Provider Incident SLA。
4. 哪些 criterion 是必需、可选或 report-only。
5. 哪些失败必须立即人工复核，哪些可以等待 Provider 恢复。
6. 人工评分所需证据、双人复核条件和任务 SLA。
7. 是否允许同模型 service-tier fallback，以及是否允许跨模型 fallback。
8. 检索 Recall、QWK、不公平性、人工复核率、失败率和延迟发布门槛。
9. Shadow 观察窗口、Canary 比例和一键回退责任人。
10. Langfuse 自托管环境、数据位置、RBAC、保留周期、成功 Trace 采样率和允许查看脱敏内容的角色。

## 13. 建议实施顺序与依赖

```text
P0 错误可观测性
    ↓
P1 检索 + Token Budget + Prompt V4
    ↓
P2 规则任务 + 部分成功持久化
    ↓
P3 人工复核队列 + 空总分闭环
    ↓

    ↓
P5 Groq Flex/Batch 可选能力
    ↓
P6 校准、观察、发布和回退演练
```

禁止跳过 P1 直接做 P4；否则只是把多个超长请求同时发送给 Groq。禁止跳过 P2/P3 直接扩大并发；否则故障只会更快地扩散到论文级失败。

## 14. 本方案完成定义

本方案实施完成不是指“Groq 不再返回 400”，而是同时满足：

1. 长论文的每个评分项请求都在可证明的 Token Budget 内。
2. LLM 只看到与当前规则相关的最小授权证据集。
3. 无依赖规则可以安全并发，依赖规则保持确定性顺序。
4. Provider 临时和永久错误得到不同处理，不阻塞无关任务。
5. 规则级失败可恢复、可定向重试、可审计。
6. 自动失败阻塞总分时有正式人工待办和授权解决路径。
7. 所有阻塞项解决前正式总分和等级为空。
8. 人工结果、自动结果和 fallback 身份在报告与导出中可区分。
9. 全量测试、迁移、QWK、上线清单和回退演练通过。
10. 未经 GATE-03 和维护者批准，不改变默认 Core 发布边界。
11. 评分链路可在 Langfuse 中按 run/rule 还原，脱敏与采样经过验证，且关闭或中断 Langfuse 不影响权威评分和任务恢复。
