# 官网试用与部署评估申请落库改造方案

状态：**已确认**（2026-10-18）。第 16 节 Q1–Q8 全部按推荐，技术方案同意实施。

前置：DECISIONS「2026-10-17 根路径改为宣传页、`/about` 官网子页」。宣传页与官网子页已上线（PR #35），原型里两个只改前端状态的表单当时没有上线：提交后显示「已登记」「已收到」，实际上什么也没保存。本方案让它们真正把申请存下来，并让平台管理员能看到、能跟进。

# 第一部分：业务方案

## 1. 目标

| 入口 | 访客填写 | 现在 | 本方案之后 |
|---|---|---|---|
| 宣传页首屏「申请试用」 | 院系邮箱 | 没有表单，按钮跳到子页预约区 | 恢复原型的邮箱输入框，提交后存库 |
| 子页 `/about#contact`「预约部署评估」 | 学校与院系、联系邮箱 | 「发邮件预约」按钮（mailto） | 恢复原型的表单，提交后存库 |

平台管理员在工作台「运维」页看到新申请，标记跟进状态，到期自动删除。

一句话原则：**只收联系所需的最少信息，存在我们自己的库里，到期就删。**

## 2. 访客看到什么

- **提交成功**：
  - 首屏：「已收到 {邮箱}，我们会通过这个邮箱联系你。」（原型写的是「试用开放时会第一时间通知你」，按 Q2 改掉）
  - 子页：「已收到，我们会通过邮件联系你。」（与原型一致）
- **格式不对**：在输入框下方当场提示（「请填写有效的邮箱」「请填写学校与院系」），不清空已填内容。
- **提交太频繁**：「提交太频繁，请稍后再试；也可以直接发邮件到 {联系邮箱}」。
- **服务暂时不可用**（网络错误、5xx）：同上，并给出发邮件的链接。访客的诉求不能因为我们的故障丢掉。
- **表单未开放的部署**（见第 10 节，Vercel 就是这种情况）：保持现在的样子——首屏按钮跳子页、子页给「发邮件预约」。
- 每个表单下方一行小字：「提交即表示同意我们用这个邮箱联系你。申请记录保存 180 天，到期自动删除。」并链接到「数据安全」页。

## 3. 管理员怎么跟进

工作台「运维」页新增一张卡片「官网申请」，只有平台管理员可见（复用现有能力 `view_platform_ops`）：

- 标题旁显示未处理数量（「3 条新申请」）。
- 列表：提交时间、类型（试用 / 部署评估）、邮箱、学校与院系、备注（Q3）、重复提交次数、状态。默认只看「新申请」，可切到全部。
- 每行可以：复制邮箱、「发邮件」（mailto）、改状态（新申请 → 已联系 → 已结束；或标为垃圾）、删除（二次确认）。
- 改状态和删除写审计日志，记操作人，不记邮箱。

本期**不发通知**：系统目前不具备发邮件的能力（邀请与重置链接也是生成后交给管理员转发），管理员需要自己打开运维页查看。通知放到二期（Q5）。

## 4. 隐私与保留

- 只存：类型、邮箱、学校与院系、可选备注、提交页面、状态、时间。**不存原始 IP、不存 User-Agent**。
- 限流需要区分来源：存 IP 的 HMAC 摘要（密钥用已有的 `AUTH_SECRET`），只用于计数，随记录一起删除。
- 保留期默认 180 天（Q4），按最后一次提交时间计算，到期由 worker 自动删除。管理员也可以随时手动删除（访客要求删除时用）。
- 「数据安全」页加一句申请信息的处理说明（Q8）。

## 5. 本期不做

- 邮件或聊天机器人通知（二期，见 Q5）。
- 第三方人机验证（Turnstile、hCaptcha）：理由见第 14 节。
- 申请记录导出 Excel，以及接 CRM。
- 双重确认邮件（double opt-in）：需要发信能力。
- 在 Vercel 上收申请（第 10 节）。

# 第二部分：技术方案

## 6. 总体做法

```
宣传页 / 子页 ──POST /api/site/leads──▶ 校验 ─▶ 防滥用 ─▶ 去重写入 site_leads ─▶ 202
运维页（平台管理员）──GET/PATCH/DELETE /api/site/leads…──▶ 列表、改状态、删除（审计）
worker 巡检（每天最多一次）──▶ 删除超过保留期的记录
```

公开接口不登录、不带组织上下文，所以挂在 `guarded` 路由组之外（与 `/api/auth/*`、`/api/system/*` 一样）；管理接口逐个用 `require_platform_admin`。

## 7. 数据表 `site_leads`（迁移 0039）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | String(36) PK | `new_id()` |
| `kind` | String(24) | CHECK：`trial` / `deploy_assessment` |
| `email` | String(254) | 去首尾空白、转小写后存 |
| `organization_name` | String(120) 可空 | 学校与院系；`deploy_assessment` 必填 |
| `note` | String(500) 可空 | 备注 / 课程范围（Q3 已确认加，仅预约表单） |
| `source_path` | String(64) | `/` 或 `/about`，看申请来自哪张页面 |
| `status` | String(16) | CHECK：`new` / `contacted` / `closed` / `spam`，默认 `new` |
| `submit_count` | Integer | 去重后的累计提交次数，默认 1 |
| `ip_hash` | String(64) 可空 | HMAC-SHA256(AUTH_SECRET, 客户端 IP)，只用于限流 |
| `created_at` / `last_submitted_at` | DateTime | 首次与最近一次提交 |
| `handled_by` | String(36) FK users.id 可空 | 最近改状态的人 |
| `handled_at` | DateTime 可空 | |

索引：`(kind, email)`（去重）、`(ip_hash, last_submitted_at)`（限流）、`(status, last_submitted_at)`（列表与保留期清理）。

**不挂组织**：申请发生在开通账户之前，属于平台级数据。

迁移照 0023 / 0038 的写法：**在迁移里给 `pgs_app` 授权、开 RLS、建 `pgs_app_dml` 策略**；同时把表加进 `postgres_verifier.RUNTIME_ACCESS_TABLES`，迁移授权扫描契约随之覆盖。生产运行角色没有 DDL，漏了这一步迁移照样成功，上线后却是 permission denied，本地与 CI 都测不出来。

降级：按项目惯例**有数据时拒绝降级**。空表可以降级。

## 8. 接口

### 8.1 公开提交 `POST /api/site/leads`

请求体（JSON）：

```json
{ "kind": "deploy_assessment", "email": "a@b.edu.cn", "organization_name": "某大学 计算机学院", "note": "", "website": "" }
```

- `website` 是蜜罐字段：页面上对人隐藏，脚本往往会填。
- 只接受 `Content-Type: application/json`。

响应：

| 情况 | 状态码 | 说明 |
|---|---|---|
| 收下（新写入或去重合并） | 202 `{"status":"received"}` | 两种情况响应一样，不暴露「这个邮箱提交过」 |
| 蜜罐被填 | 202，同上 | 静默丢弃，只记日志 `site_lead_honeypot` |
| 字段不合法 | 422 | 按字段给中文提示 |
| 限流 | 429，带 `Retry-After` | 见第 9 节 |
| 表单未开放 | 404 `{"code":"site_leads_disabled"}` | `SITE_LEADS_ENABLED` 为假时，接口当作不存在 |

日志只记申请 ID、类型与结果，**不记邮箱**。

### 8.2 管理（平台管理员）

- `GET /api/site/leads?status=new&kind=&limit=50&offset=0` → `{ items, total, new_count }`
- `PATCH /api/site/leads/{id}` `{ "status": "contacted" }` → 写 `handled_by` / `handled_at`，审计 `site_lead.status_changed`
- `DELETE /api/site/leads/{id}` → 审计 `site_lead.deleted`（元数据只有 ID 与类型）

非平台管理员一律 403；未登录 401；关闭鉴权的开发模式按现有规则放行。三个接口进 OpenAPI，前端 `api:check` 会随之更新 `schema.d.ts`。只新增接口、不改已有接口，契约版本不必升。

## 9. 防滥用（不引入第三方验证码）

1. **只收同源的 JSON**：不开 CORS，别的网站无法借访客的浏览器代为提交；普通表单提交发不出 JSON。
2. **蜜罐字段**：填了就静默丢弃。
3. **按来源限流**：同一 `ip_hash` 每小时最多 5 次、每天 20 次（Q7），直接数表里的记录，不另建计数表。uvicorn 已开 `--proxy-headers`，Caddy 转来的真实客户端 IP 可用。
4. **全站日上限**：每天新写入超过 300 条就返回 429，同时记一条 WARNING。这样即使被刷，库的增长也有上界。
5. **去重**：同一类型、同一邮箱 30 天内再次提交，不新增行：`submit_count + 1`、刷新 `last_submitted_at`、用新值覆盖学校与备注。
6. **长度与格式**：邮箱 ≤ 254 字符且格式合法；学校与院系 ≤ 120 字；备注 ≤ 500 字；去掉控制字符。页面渲染一律走 Vue 的转义。

## 10. 开关与两个宿主

- 新增环境变量 `SITE_LEADS_ENABLED`，默认 `false`：本地、CI 与内网部署都不受影响。生产（Lightsail）由 GitHub 仓库变量经 `production_env.py` 写进 `.env`，可以不改代码随时关掉。
- 页面怎么知道开没开：沿用宣传页动效那套全局配置。FastAPI 渲染官网入口页时，若开关为真，往 `window.__PGS_CONFIG__` 里加 `siteLeads: true`，页面据此显示表单，否则保持现在的样子。不需要多发一次请求。
- **Vercel 不开表单**：Vercel 的 `/` 是静态文件，拿不到这个值，自然回落到「发邮件」。这也是必须的：Vercel 的接口连的是**旧库**，切流量后整库删除，在那里收的申请会全部丢失（见 Q1）。
- 保留期 `SITE_LEADS_RETENTION_DAYS`，默认 180。

## 11. 保留期清理

worker 现有的全局巡检 `run_global_sweep` 里加一步 `purge_expired_site_leads`：用 `work_runtime_state` 记上次清理时间，每天最多跑一次，删除 `last_submitted_at` 早于保留期的记录，日志记删除条数。Vercel 上没有 worker，但它也不收申请，不受影响。

## 12. 前端

- **宣传页**：开关为真时恢复原型的首屏表单（圆角输入框 + 金色箭头按钮）及成功态；状态为 空闲 / 提交中 / 成功 / 失败，失败提示用 `role="alert"`。蜜罐输入框对屏幕阅读器隐藏，`tabindex=-1`，`autocomplete=off`。
- **子页预约区**：开关为真时恢复原型的表单（学校与院系、联系邮箱，加可选的备注 / 课程范围），否则保留「发邮件预约」。
- 官网页面用原生 `fetch` 提交，不经过工作台的 API 客户端（它会带组织头和契约版本）。
- **运维页**：新增「官网申请」卡片（第 3 节），只对 `view_platform_ops` 可见，每页 50 条。

## 13. 测试与验收（全部本地，不调用任何外部服务）

- **后端**：
  - 字段校验，蜜罐静默丢弃。
  - 每 IP 每小时与每天的限流（含 `Retry-After`），全站日上限。
  - 30 天去重与 `submit_count`，开关关闭时返回 404。
  - 管理接口：401、403、改状态、删除与审计，以及审计里不含邮箱。
  - 到期清理每天只跑一次，日志里不含邮箱。
- **迁移**：`test_migrations` 覆盖升级、空表降级、有数据时拒绝降级；Postgres CI 核对授权与 RLS；运行角色复验清单包含新表。
- **前端单测**：开关为假时没有表单；为真时各状态的文案；失败时给出发邮件链接；运维卡片的列表与状态切换。
- **e2e**：在开了开关的 FastAPI 宿主上提交两种表单，再用平台管理员（鉴权后端）在运维页看到申请、标记「已联系」；纯静态宿主（模拟 Vercel）不出现表单。
- **CLAUDE.md 与文档契约**：迁移 head 改为 0039。

## 14. 放弃了什么（实施时写进 DECISIONS）

- **第三方人机验证（Turnstile / hCaptcha）**：多一个外部依赖和隐私说明，部分地区访问不稳，失败时访客连申请都交不上。以现在的量，蜜罐 + 限流 + 日上限足够；真被刷了再加。
- **本期就接邮件通知（SMTP / Resend 等）**：要发信账号、域名 DNS 记录、密钥与送达率维护，比存库本身还重。先让管理员在运维页看，二期再定渠道。
- **把申请记进现有的 `audit_logs`**：审计日志不该承载可修改的状态和保留期，混在一起后，清理申请时还得小心别删掉审计。
- **浏览器直接写 Supabase**：要把 Supabase 的公开密钥和 RLS 规则暴露给匿名访客，校验与限流也只能放进数据库函数里。
- **在 Vercel 上也收**：会写进切流量后就删除的旧库。
- **跨域把 Vercel 的表单提交到 Lightsail**：要为一个接口开 CORS，而 Vercel 本来就要变成跳转（Q1）。
- **进程内存限流**：重启就清零；按表计数在这个量级上成本可以忽略。
- **Caddy 限流**：官方镜像不带限流模块，要自己编译 Caddy。

## 15. 发布与回滚

1. 合并前先跑 `production-migrate.yml`（需审批）把 0039 迁到生产，沿用「先迁移、后合并」。
2. 合并后自动部署。此时开关仍为假，线上看不到任何变化。
3. 在 GitHub 设仓库变量 `SITE_LEADS_ENABLED=true`，重新部署后核验：提交两种申请，在运维页看到、改状态、删除。
4. 回滚：先把变量设回 `false` 再重新部署，表单消失、数据保留；需要时再回退代码。有数据时不做数据库降级。
