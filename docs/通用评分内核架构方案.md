### 1.2 Core 的职责

- 接收不可变的 submission、document、rubric、execution plan 和 policy。
- 正式版本按已发布 AtomicRule 执行确定性或语义判定；冻结旧标准仅可走显式标记的 legacy compatibility node。
- 由代码完成扣分、选档、cap、repeat、dependency、mutex 和聚合；bonus 待后续 base_score/ceiling 合同明确后再启用。
- 验证所有语义证据，拒绝空 quote 和越权规则。
- 使用真实 PromptEnvelope 生成缓存身份。
- 生成可审计、可持久化、与业务 Profile 无关的结果。
- 控制等级、舍入、复核和阻断策略。
- 提供人工复核所需的稳定 item / rule identity。

### 1.3 Profile 的职责

Profile 只能提供业务语义，不能绕过 Core 的计分和证据规则。

ThesisProfile 负责：

- 论文封面及学生信息。
- 摘要、目录、结论、参考文献等结构识别。
- 图表、引文、格式和研究问题—结论一致性。
- 论文专用 prompt、Mock 行为、HTML/Excel/JSON 扩展。
- 论文校准锚点和 QWK 数据集构建。

TechnicalProposalProfile 负责：

- 技术方案编号、供应商、项目名称等元数据。
- 需求理解、总体方案、实施计划、风险控制、服务承诺等结构语义。
- 方案匹配度、实施可行性、风险覆盖等 prompt 扩展。
- 非论文报告字段和后续独立评估数据集。

### 1.4 强制依赖规则

- scoring/core 不得 import SQLAlchemy Session、Paper、ParsedPaper、papers、coherence、thesis、report 或 FastAPI。
- Profile 不得直接修改总分、等级或绕过 Evidence Validator。
- API 路由不得包含计分逻辑。
- Checker 只返回 observation / verdict / evidence，不决定未授权分值。
- 运行时只消费不可变快照，不在评分过程中再次读取可变 ORM 图。
- 数据库里的 checker_key 只能查显式 registry，禁止动态 import 或执行任意路径。
- 新的通用代码不得出现“论文、学生、摘要、参考文献”等默认业务语义。

## 2. Core 合同设计

### 2.1 不可变 DTO

| DTO | 必需内容 | 明确排除 |
|---|---|---|
| SubmissionSnapshot | submission_id、profile_key、source_hash、通用 metadata、artifact refs | Paper ORM、学生固定字段、磁盘操作 |
| DocumentSnapshot | schema_version、content_hash、full_text、sections、evidence units、metrics、parser diagnostics、profile extensions | ParsedPaper 类型、数据库 Session |
| CompiledRubricSnapshot | rubric_source_kind、rubric_snapshot_hash、business_profile_key、total_score、criteria、AtomicRule、RuleLevel、global_policy；正式版本另含 rubric_version_id/version_hash | 可变 ORM 对象、伪造的 legacy version |
| AtomicRuleSnapshot | rule_code、criterion_code、direction、effect、judge_type、checker、params、evidence policy、repeat/cap/dependency/mutex、levels | 数据库关系懒加载 |
| RuleExecutionPlan | 稳定排序的 AtomicRuleNode；legacy 可另含 LegacyDirectCriterionNode / CompositeCriterionNode；依赖拓扑、registry manifest、policy、plan_hash | 运行中临时查询、正式版本兼容节点 |
| ScoringPolicy | 聚合、等级、舍入、证据阈值、复核规则、失败策略 | 固定百分制假设 |
| ScoringRequest | submission + document + plan + runtime identity + idempotency_key | DB Session、文件路径 |
| ScoringOutcome | criterion outcomes、rule decisions、score contributions、review issues、完整审计身份 | 论文专用展示字段 |

所有 DTO：

- 使用 schema_version。
- 支持 canonical serialization。
- hash 不依赖字典插入顺序、数据库主键生成顺序或本地路径。
- 构造后不可变。
- 提供 round-trip 和稳定 hash 测试。
- idempotency_key 由 submission snapshot、rubric snapshot、plan、policy 和显式 rescore generation 组成；必须持久化并由数据库唯一约束裁决。冲突时逐一核对输入 hash，相同才返回已有权威 run，任何碰撞或不一致都 fail closed。

### 2.2 ScoringPolicy

global_policy 应先编译成强类型 ScoringPolicy，再进入运行时。建议最小合同：

- aggregation.mode：points 或 weighted_normalized。
- aggregation.total_score。
- rounding.mode：half_up 等显式模式。
- rounding.digits。
- grade_scale：基于分数或百分比的有序档位。
- review.total_below。
- review.grade_boundary_tolerance。
- review.confidence_below。
- review.parse_quality_below。
- review.on_invalid_evidence。
- evidence.default_policy。
- failure.unknown_checker。
- failure.rule_conflict。
- failure.semantic_error。

兼容期明确区分两个 policy：

- legacy_behavior_policy：只用于 golden 和 compare，描述旧引擎事实，不作为新 Core 的正确口径。
- corrected_thesis_policy：M1 门禁通过后的所有新论文权威运行采用，包括暂时仍由 legacy engine 计算的运行；在 100 分标准上保持原业务意图，对非 100 分标准按归一百分比修复等级和复核边界。

不能再把“默认行为”散落在 rules.py 和 engine.py。等级判定使用舍入前总分；显示和持久化按 policy 指定阶段 quantize。v1 在数据库 Numeric 精度不扩展前限制 rounding.digits ≤ 2；grade boundary tolerance 必须声明使用百分比点还是原始分数单位。
M1 后 legacy engine 只可产生 criterion raw score；新权威 run 的贡献、等级、舍入与复核边界也必须走冻结 corrected_thesis_policy，不能把正确性修复推迟到默认 Core 切换。

### 2.3 weight 的唯一语义

只允许两种互斥模式：

1. points
   所有 weight 为空；要求所有 max_score 之和等于 total_score；总分为各项 awarded 之和。

2. weighted_normalized
   所有 weight 均存在且大于 0；单项贡献为 total_score × weight / Σweight × awarded / max_score。weight 可以使用任意正数尺度。

禁止：

- 部分 criterion 有 weight、部分没有。
- 负权重或零权重。
- create、update、import、发布和评分开始前未通过同一 policy 校验。
- 发布后再改变聚合语义。
- 只在总分中隐式换算而不保存贡献。

每个结果必须保留 raw score、max score、weight 和 weighted contribution；初评、人工改单项、最终提交复核必须使用同一个冻结 policy。v1 在不改变 RubricCriterion.weight 精度前只接受可由 Numeric(6,2) 精确表示的 0.01..9999.99，额外小数或越界值直接拒绝，不能静默舍入。

### 2.4 证据类型

不能再用一种 evidence 结构同时表示 LLM 原文引用和确定性测量。

SourceQuoteEvidence：

- quote trim 后必须非空。
- evidence_unit_id 必须存在于本次 DocumentSnapshot。
- 归一化 quote 必须逐字存在于指定 evidence unit。
- location / section 作为定位信息，但不能替代 quote。
- evidence_sufficient 由系统推导，不信任模型布尔值。

DeterministicObservation：

- checker_key 和 checker_version。
- locator。
- measured_value / expected_value。
- observation code。
- 可选原文 quote；没有 quote 时也必须能从 snapshot 重放。

ScopedAbsenceEvidence / CoverageEvidence：

- 用于“缺少风险负责人”等没有可引用原句的结论。
- 必须记录 document_snapshot_hash、被检查 section/evidence-unit IDs、查找目标、覆盖结果和可选邻近原文。
- 只有 evidence policy 明确允许 absence evidence，且检查范围达到声明覆盖度时，才能触发自动 score effect。
- 不能用“未召回到内容”代替“已检查完整范围且确认缺失”。

ValidationIssue：

- issue code。
- 严重级别。
- 被拒绝的 evidence / rule reference。
- 对 score、review 或 block 的实际影响。

deductive 和 banded 的决策证据同样必须按 AtomicRule.evidence_policy 校验。
required evidence 无效时，相关 criterion 的 auto/final score 与 run.final_total 都为空；optional evidence 无效时只丢弃对应 effect，是否进入复核由冻结 ScoringPolicy 决定。人工普通改单项不能把 required invalid 或 block 改成 resolved。

新 DocumentSnapshot 不使用数据库自增或 UUID 作为证据身份。evidence_unit_id 按 ADR-0001 的 `evidence-unit-id-v1`，由 normalized content hash、section path、0-based 全局 section ordinal、section 内 0-based unit ordinal 与 unit text hash 派生；LegacyPaperAdapter 必须把 PaperChunk 转换为这种 snapshot-local 稳定 ID。
PaperChunk.id/chunk_id 只能保留在 adapter 的非权威 source reference 中，不能参与 Core evidence 验证、PromptEnvelope 或 cache identity。

### 2.5 AtomicRule 执行语义

LLM 或 Checker 只返回判定，不直接决定任意分值。

| AtomicRule 字段 | 运行语义 |
|---|---|
| judge_type=deterministic | 用 checker_key + checker_params 调用显式 Checker |
| judge_type=semantic | 用 Profile prompt + 规则快照请求语义判定 |
| direction=deduct | v1 将 max_points 解释为每个唯一 occurrence 的固定授权扣分，再按 repeat / cap 计算 |
| direction=band | 模型只能选择已发布 level_code，代码从 RuleLevel 取 points |
| direction=bonus | 保留枚举但 v1 不可执行、不可发布；后续只有定义显式 base_score 与 ceiling 后才能启用 |
| direction=none | 只产生 review、block 或 report effect |
| effect_type=score | 允许影响分数 |
| effect_type=review | 只标记复核 |
| effect_type=block_submission | 阻断自动定分 |
| effect_type=report_only | 只进入报告 |
| depends_on_rule_codes | 仅当依赖规则已有效执行且状态为 triggered 时才满足；否则记录 skipped |
| mutex_group | 多规则同时触发时 fail closed，冲突 criterion 不形成自动最终分 |

以下情况不得影响分数：

- 未知 rule_ref。
- 跨 criterion 或跨 rubric version 的规则。
- 未发布或状态无效的规则。
- 模型自报 points 超过授权值。
- 负 points。
- 超过 repeat / cap。
- required evidence 未通过。
- 未知 band level。

原始模型输出可保留用于审计，但不能作为最终计分依据。

RuleDecision 只允许：

- triggered：规则已有效触发。
- not_triggered：已检查且未触发。
- not_applicable：规则对当前范围不适用。
- invalid：输出、证据或规则合同无效。
- skipped：依赖未满足，未执行。

AtomicRule 审核状态使用 draft → review → approved，另允许 review → rejected / draft。只有 approved 规则能进入发布候选；approved/rejected 必须有 reviewed_by、reviewed_at 和可验证的审核事件。v1 复用 RubricCompilation.human_changes，并冻结事件 schema：change_id、rule_code、field_path/action、before/after、actor_id、occurred_at、reason；approve/reject 事件的 actor/time 必须与规则审核字段一致。Rubric 发布后 compilation 事件与父版本一同冻结，不再改变规则状态。

v1 分数顺序：

1. 每个 criterion 先执行并验证全部 rule decisions。
2. deduct criterion 以 criterion.max_score 为起始分；review_only criterion 的 auto score 为空，不能从满分起算。
3. band criterion 恰好包含一个 band AtomicRule，由该规则选出唯一 RuleLevel；该 band rule 的 mutex_group 为空，RuleLevel 不建模成多个互斥 AtomicRule，且 v1 不允许同一 criterion 再混用 deduct。字段细则以 ADR-0001 D06 为准。
4. deduct 按唯一 occurrence 计算；occurrence_id 由 rule_code、finding code、稳定 evidence-unit IDs 和 locator hash 组成，用于去重与幂等。
5. 所有 RuleLevel.points 和自动 criterion score 必须在 0..criterion.max_score；越界即 invalid，不做隐式 clamp 掩盖规则错误。
6. criterion contribution 按 ScoringPolicy 计算，最后由未舍入 contribution 聚合 run total。

v1 合法组合：

- direction=band/deduct 只能搭配 effect_type=score；direction=bonus 在 v1 一律发布失败。
- direction=none 只能搭配 review/block_submission/report_only。
- once、per_occurrence、capped deduct 均要求 max_points；capped 还要求 cap_points。
- mutex 冲突、未知依赖、invalid required rule 或 block_submission 会令相关 criterion final score 为空，run.final_total 为空并进入人工处理，不能用“未扣分”冒充满分。
- review_only 是 criterion assessment mode：只含 none-effect 规则，auto score 永远为空，必须经授权人工给 final score 后才参与总分；不得按 max_score 自动送分。

### 2.5.1 llm_direct 与 hybrid 的兼容边界

`llm_direct` 不是 AtomicRule direction。为了让冻结旧标准可以由 Core 承接，RuleExecutionPlan 允许 `LegacyDirectCriterionNode`，但必须同时满足：

- rubric_source_kind=legacy_unversioned。
- 由 LegacyRubricAdapter 显式生成并带 legacy prompt/version 身份。
- 模型分数只能在 0..criterion.max_score，required evidence 通过统一验证器；否则该 criterion 与 run.final_total 为空。
- policy 可以强制人工复核；该节点不能出现在新 RubricVersion、不能由新导入默认生成、不能作为发布绕行口。

新标准若仍是 llm_direct，发布前必须由维护者选择 band、deduct 或 review-only；无法转换时保持 draft。M8 切换后，未编辑的历史标准仍可通过上述兼容节点评分，任何 clone/upgrade 后的版本都必须完成迁移。

旧 `hybrid.sub_checks` 由 LegacyRubricAdapter 变成 `CompositeCriterionNode`：有序叶子分别执行，parent raw score 为叶子之和并验证不超过 parent.max_score，parent weight 只应用一次。正式 RubricVersion 不保存这种兼容节点；发布编译器把 sub-check 展开成稳定编码的独立叶子 criteria，每个叶子只允许一种执行语义：

- points 模式直接聚合叶子分值。
- weighted_normalized 要求模板显式给出可表示的叶子 weight，或编译器按 parent.weight × child.max / parent.max 用 Decimal 精确派生；无法精确持久化时阻断发布。
- 父子关系只保留为来源追踪与报告分组，不再形成第二层计分。
- 语义叶子必须转为 band/deduct/review-only，不得把 llm_direct 隐藏在 hybrid 内。

### 2.6 人工复核边界

- AI 输出、RuleDecision、证据验证和自动 calculated score 是不可变审计事实。
- 人工可在 0..criterion.max_score 内设置 final criterion score，即使它不同于自动规则结果；这属于显式 human override，不得反写或伪造 AtomicRule outcome。
- 每次 override 记录 actor、权限、reason、before/after、policy hash、时间和关联的 validation/block resolution。
- 普通改单项不能清除 execution-plan invalid、未发布版本或 block_submission；这些问题必须通过授权的 resolve_block / 修正规则后重评分处理。
- 任一必需 criterion 仍为 blocked/invalid/unresolved 时，final_total 保持为空；不能只改 run 状态就绕过。

### 2.7 CheckerRegistry

Registry 条目至少包含：

- 不可变、带合同版本的 namespaced checker_key，例如 core.required_sections.v1、thesis.citation_consistency.v1。
- checker_version。
- implementation hash。
- params schema。
- 支持的 DocumentSnapshot schema / profile。
- 纯函数或显式 runtime port。
- observation schema。

发布和构建执行计划时即验证 key 与参数，不等到评分中才失败。已注册版本不可原地替换；修复行为必须注册新版本并让新 RubricVersion 显式采用。plan 固化精确 checker manifest，因此 rubric version 相同但 checker/profile/compiler manifest 不同会得到不同 plan hash。重命名 criterion.name 不得改变 checker 路由，但名称进入语义 prompt 时仍会改变 rubric/cache identity。

profile_key 与现有 workflow_profile 不是同一概念：

- business_profile_key：thesis、technical_proposal 等评分业务，Submission 与 Rubric 必须一致。
- workflow_profile：保留 template_driven、excel_only 等导入/编译工作流语义。

0013 为 RubricVersion 和 ScoringRun 增加 business_profile_key。plan 构建时同时验证 Submission.profile_key、Rubric.business_profile_key 和 checker 支持范围。

### 2.8 Cache 与 PromptEnvelope

缓存键必须直接来自即将发送给 provider 的 canonical PromptEnvelope，而不是另维护一份近似字段清单。

PromptEnvelope 至少包含：

- profile key 和 profile prompt version。
- engine / schema / prompt version。
- provider、model、model version、采样、thinking、response schema。
- rubric_snapshot_hash、plan hash、policy hash；published_version 还必须包含 rubric_version_id、version_hash 与 hash_scheme。
- criterion 和被授权 AtomicRule 的完整快照。
- submission 的判分相关字段。
- source_artifact_hash、normalized_content_hash 和 scoring-relevant document_snapshot_hash。
- 目标标题。
- evidence 文本、evidence_unit_id、location、section_title。
- absence/coverage 使用的 declared scope、被检查 evidence-unit IDs 的 canonical hash、coverage completeness、absence evidence policy/version。
- structure / deterministic observations。
- calibration anchors 的内容 hash。

标题、位置、章节、规则、policy、profile、模型参数、rubric snapshot/version identity 或 coverage manifest 任一变化都必须 cache miss。改 prompt 或输入构造时仍需 bump PROMPT_VERSION。

key 始终对实际发送给 provider 的原始 canonical envelope 求 hash。审计展示可以保存 redacted projection，但不能称它为“同一 envelope”；若要严格 replay，则把原始 envelope 存入访问受控、可配置保留期的缓存账本，并单独保存 redacted projection 和 original_envelope_hash。

在正式 RubricVersion 接入前，legacy 路径使用 LegacyRubricAdapter 生成的 rubric_snapshot_hash；不得继续使用可变的 Rubric.version 字符串。

## 3. 兼容与数据演进

### 3.1 兼容原则

- 保留 score_paper() 的函数签名。
- 保留 /papers、现有 CLI 命令、旧 HTML/JSON/Excel 输出。
- 保留 papers、paper_chunks、grading_batches 和历史 ScoringRun。
- 历史运行不回写、不伪造 version hash。
- 新 Core 运行必须记录不可变 rubric identity / policy / document / engine 身份；正式版本与 legacy content hash 要明确区分。
- 论文能力先通过 facade 迁移，确认调用方切换后再移动文件。
- 旧表至少跨两个稳定发布周期后才讨论删除或物理重命名。

### 3.2 LegacyRubric 处理

历史 Rubric 没有 0009/0010 图谱，不能假装拥有正式 RubricVersion。

兼容规则：

1. 有已发布 RubricVersion 的新标准：只允许加载该不可变版本。
2. 只要存在 provenance / version 图但没有合法发布版本，就必须 fail closed，不能回退成 legacy。
3. 完全没有版本图的历史标准：由 LegacyRubricAdapter 构造 source_kind=legacy_unversioned 的显式 snapshot 和 rubric_snapshot_hash；正式 version 字段保持空。
4. 历史运行的权威字段永不回填。若分析需要推断关联，只能另存 inferred_version_link、依据和置信度，且不得用于评分、复核或报告身份。
5. legacy published rubric 可以继续评分，但编辑必须 clone/upgrade 成正式图。
6. legacy draft 禁止走旧直接发布；必须通过 upgrade_legacy_rubric_to_compilation() 生成完整 manual_json provenance 图后进入统一 review/publish，无法升级时保持 draft。

### 3.3 迁移 0012：冻结正确性口径

M1 先解决“初评和人工复核跨部署使用不同 policy”的问题，不等待完整 Core：

scoring_runs：

- policy_snapshot / policy_hash / policy_schema_version。

score_items：

- aggregation JSON + aggregation_schema_version，记录 raw / max / weight / contribution。
- auto_score_status：calculated / invalid / blocked；历史行允许为空。
- ai_score 改为可空，使 required evidence invalid 时可以真实表达“没有自动定分”。

review_logs：

- policy_hash。
- resolution_type，区分 ordinary_override、resolve_validation、rescore。

新运行的 policy 三字段必须全有或全无，并在创建 run 的同一事务冻结；复核只能读取 run 上的 snapshot。迁移前历史 run 无 snapshot 时禁止用当前部署 policy 自动重算，只允许显式 legacy-preservation 或新建 rescore generation。

0011 → 0012 的空数据 downgrade 必须可行；只要出现冻结 policy/aggregation、invalid/blocked nullable score 或新 review resolution 等旧表无法表达的数据，就先导出并拒绝 downgrade，不能静默删除。

### 3.4 迁移 0013：版本、重放与幂等身份

在不引入通用 submissions 表之前，完成 Core 运行审计闭环。

rubric_versions：

- business_profile_key；既有版本明确回填 thesis。
- hash_scheme；既有版本明确回填 rubric-content-v1。

grading_batches：

- rubric_version_id，可空以兼容历史数据。

scoring_runs：

- rubric_source_kind：published_version 或 legacy_unversioned。
- rubric_snapshot_hash：两条新 Core 路径都必须有值。
- rubric_version_id，可空以兼容历史。
- rubric_version_hash / rubric_hash_scheme，正式版本运行时拷贝；legacy 可空。
- business_profile_key / workflow_profile。
- execution_plan_snapshot / execution_plan_hash / plan_schema_version。
- checker_manifest。
- source_artifact_hash / normalized_content_hash。
- document_snapshot_ref / document_snapshot_hash / document_schema_version。
- engine_version。
- rescore_generation：新 Core run 必填且非负。
- idempotency_key：由 submission/document/rubric/plan/policy/profile/runtime identity 与 rescore_generation 计算。

score_items：

- rule_results JSON + rule_results_schema_version；aggregation 沿用 0012。

约束：

- 历史行允许为空；新 Core run 的身份字段在同一事务原子写入，不能产生半完整身份。
- idempotency_key 建唯一约束（历史 NULL 可重复）；并发 insert 冲突后只有全部输入 hash 一致才返回已有 run，否则按 hash collision / contract violation 阻断。
- published_version 必须同时有 rubric_version_id/version_hash，legacy_unversioned 必须二者均空。
- batch/run 的 rubric_version_id 必须属于同一 rubric_id，正式 hash 必须匹配引用版本；使用复合约束或等价的数据库约束与事务校验。
- 版本与审计依据使用 RESTRICT 删除策略，不能 cascade 删除。
- policy 与 execution plan 的小型冻结 snapshot 直接随 run 保存；DocumentSnapshot 正文使用 content-addressed 不可变对象，run 同时保存 ref 和 hash。
- 仅有孤立 hash、却找不到对应 snapshot 的 run 不得标为可重放。
- v1 rounding.digits ≤ 2，或同一迁移扩展所有持久化分数字段精度。

Hash 合同：

- 当前实现会动态遍历表列；0013 加列前必须先改为按 scheme 选择固定字段白名单，禁止 ORM 新列自动进入旧 hash。
- rubric-content-v1 固定为 pre-0013 图字段白名单；hash_scheme 本身、business_profile_key 及任何后来新增列都不进入 v1。既有已发布 fixture 在 0012/0013 前后重算必须逐字节相同。
- 新发布版本使用 rubric-content-v2，把 business_profile_key 和明确列出的新图字段纳入内容；已发布 v1 hash 永不重写。
- 新 snapshot、policy、plan 各自声明 hash_scheme/schema_version，不能混用 version hash 算法。
- Loader 按版本声明的 scheme 和对应白名单重算完整图并校验，不只比较两个已存字符串。
- 新 draft 图在持久化前先完成编译和 canonical hash，在同一原子写入中给 compilation.final_version_hash 与 RubricVersion.version_hash 赋相同初值；发布时按同一 scheme 复算。
- plan hash 的完整输入为 rubric snapshot + policy compiler version + business profile version + checker manifest + engine contract；只有这些输入全部相同，plan hash 才应稳定。

0012 → 0013 空数据 downgrade 必须测试。若只有迁移对既有版本回填的 thesis/rubric-content-v1 默认值，可安全删除列；一旦存在新 profile/v2 hash 的版本、batch version pin、任一 Core run identity/snapshot/idempotency，即使尚未评分，也必须先导出并拒绝 downgrade。测试必须包含“已发布但未评分的新版本”。

### 3.5 迁移 0016：通用 Submission

0014、0015 已分别用于发布门禁 profile 与运行时身份；通用 Submission 因此落在 0016。Core 与 LegacyPaperAdapter 稳定后增加：

- evaluation_batches：通用批次字段 + metadata。
- submissions：profile_key、metadata、artifact identity、状态。
- document_snapshots：不可变解析快照及 hash。
- scoring_runs.submission_id。
- 迁移期 paper_id 可空，数据库增加 exactly-one CHECK：paper_id 与 submission_id 必须恰有一个非空。

不复制历史 Paper 内容，不在 0016 中顺带重命名旧表。只要存在任何 evaluation batch、submission 或 document snapshot，包括已上传但未评分的 submission，downgrade 都必须先导出并明确拒绝；不能只检查 submission-only run，更不能伪造 Paper 或静默删数据。

### 3.6 迁移 0017：可恢复批评分与观察策略

`batch_scoring_jobs` 保存批次、代次、用户提供的观察策略及哈希、有界并发、租约心跳、聚合指标和终态；`batch_scoring_items` 保存逐论文状态、开始前评分结果基线、当前结果、错误与完整尝试历史。单批次只能存在一个 queued/running/cancel_requested 任务；恢复时只有过期租约可被接管，并用结果基线避免“评分已提交、检查点未提交”造成重复权威 run。任一任务/检查点存在时，0017 downgrade 明确拒绝。

观察策略及阈值来自生产用户建立的数据库关联，不写死在模型或 Web 中。缺少 paired legacy/Core delta、样本窗口或任一指标时统一 fail closed；PGS-6 观察报告固定 `production_default_switch_authorized=false`，不能替代 GATE-03 的完整身份与人工批准。

v2 ingestion 把文件格式提取与业务解释分开：

- 通用 document extractor 只产出段落、样式、页码、表格和稳定 evidence units。
- Profile interpreter 再识别论文摘要/参考文献或技术方案章节。
- /api/v2/submissions 根据 business_profile_key 选择 interpreter；不能先构造 ParsedPaper 再删论文字段。

### 3.6 切换开关

建议增加 SCORING_ENGINE_MODE：

- legacy：旧引擎产出并持久化。
- compare：测试/离线环境同时计算；只把 legacy 结果写入正式 ScoringRun/ScoreItem，Core 候选结果和差异写入独立、非权威的 comparison artifact；真实 LLM 不做重复外呼。
- core：Core 产出并持久化。

compare artifact 不得进入人工复核、报告或导出，避免产生两个“最终分”。compare 主要用于 Mock、确定性规则和冻结 fixture：

- 只有新旧 PromptEnvelope hash 完全相同时，才能共享同一语义响应并称为完整 outcome 对比。
- envelope 不同时，只能复放同一 RuleDecision 做“下游计分对比”，必须标记 decision_replay，不能据此评价新 prompt。
- 新 prompt 的语义效果只能在受控 eval 中单独调用模型；生产 compare 不做双倍外呼。

### 3.7 来源图与生命周期真相

- provenance / AtomicRule 图是正式真相；旧 RubricCriterion 只是派生兼容投影。
- 有 provenance 的 draft 只能经领域服务编辑；服务更新正式图后原子重建旧投影，发布前验证两者一致。API 不得分别编辑两份数据。
- 文件解析和 LLM 编译发生在数据库事务外；验证完成的内存图在一个短事务内原子持久化，不能持有事务等待网络模型。
- Excel/Word 导入生成真实 SourceArtifact/SourceRule/TemplateItem。
- 手工 POST /rubrics 不废弃，但要生成 artifact_type=manual_json 的 canonical SourceArtifact，并为每条输入规则生成可定位 SourceRule。
- 规则审核 API/CLI 至少支持：编辑 draft、提交 review、approve/reject AtomicRule、confirm/reject 必需 RuleTemplateLink、记录 reviewer/time/human_changes。
- 未知 business_profile_key 或 workflow_profile 是发布 blocker。
- 发布 validator 对 review candidate 执行纯可执行性校验；runtime loader 另行强制只加载 published 版本。二者复用验证原语，但职责不同。
- 已发布旧图若不满足新增验证规则，保持只读；只能 clone 后修复，禁止原地修改。
