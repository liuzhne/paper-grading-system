# 评分助手过程流式方案

> 状态：维护者 2026-11-05 确认，第 11 节五个问题都按推荐；S1、S2 已在同一个 PR 里实现，开关默认关。S3（生产打开并核实）待做。
>
> 实现时补的一点：TestClient 要等整个响应生成完才交出内容，测不了“读一半断开”；后端测试改为把响应生成器换成推出第一条就结束，验证回合跑不跑完与有没有人读响应无关（`test_assistant_stream.py`）。
>
> 相关：[评分助手Agent化方案](评分助手Agent化方案.md) 第 14 节（最终回复的输出契约）、[评分助手v2界面改造方案](评分助手v2界面改造方案.md) 第 3.6 节（老师的话先显示）。

## 1. 背景

维护者在 11-05 提出：AI 回复能不能做成流式。同一天已经做了“老师的话先显示”（v2 界面方案 §3.6），这份方案讨论回复本身。

现在一次运行就是一次 `POST /assistant/conversations/{id}/runs`。后端跑完整个回合，校验、落库之后一次返回，回合可能走规则、流程或 Agent。这段时间前端只显示“正在整理…”。

- **Agent 回合**：要做多步模型调用，例如“有哪些评分标准”要先加载工具、再调用工具、最后写回复，还要加上查数据和校验。UI-v2 评测里 P50 是 2.3 秒，P90 是 4.7 秒，最长 7.4 秒。上限 60 秒（`agent/budget.TURN_SECONDS`）。需要压缩历史的那一轮还要多一次摘要请求。
- **规则模式、快捷按钮、流程卡片**：不调模型，几乎是瞬时的。

## 2. 结论：做“过程流式”，不做“逐字流式”

### 2.1 为什么不逐字输出模型写的文字

- **违背输出契约**：Agent 化方案 §14 规定代码校验之后才显示。回复要整段校验：状态说法要有工具依据（§14.1）、带分数的句子要删掉、做注入检测、冒号结尾后面要有内容、引用的编号由代码换成卡片或名单（§14.2）。逐字显示的话，老师可能先看到一句随后被撤回的话，例如编造的“已经评完”或一个分数。
- **拿不到逐字的文字**：回复放在 `reply` 工具调用的 JSON 参数里，要逐字显示就得解析半截 JSON。Gemini 经 OpenAI 兼容接口返回函数参数时是不是分块给的，要实测才知道，没有实测不下结论。
- **省不了多少时间**：时间主要花在写回复之前的几步（加载工具、查数据），这几步本来就没有能给老师看的文字。
- **改动大**：`openai_compatible_adapter.complete_with_tools` 和 `transport` 的重试、截止时间、熔断、计量都是按整次响应写的，改成流式要重做这一层。

### 2.2 过程流式是什么

- 运行期间，后端把“现在在做哪一步”推给前端。文字由代码从固定的表里取，不经过模型。
- 最终回复照旧在校验完之后一次显示。
- 不增加模型调用，不改提示词和工具定义，提示词指纹不变，不需要重新评测。

## 3. 老师看到什么

- 发出一句话后，自己的话立即出现（已经做了）。
- 下面的“正在整理…”换成当前这一步：

| 时机 | 文字 |
|---|---|
| 开始 Agent 回合 | 正在理解你的问题… |
| 压缩历史（真的要发摘要请求时） | 正在整理之前的对话… |
| 调用查询工具 | 正在查：{工具标题}…（评分任务列表、评分任务概况、某一份的评分结果、需要人工复核的内容、可用的评分标准、帮助条目） |
| 调用提议工具（开始评分、导入、重试、取消） | 正在准备确认卡片… |
| 回复不合格、退回模型重写 | 正在核对回复… |

- `tool_search`（加载工具）不单独显示，老师不需要知道这一步。连续两次是同一句文字时只显示一次。
- 一步超过 5 秒时，在后面加上已用的秒数，例如“正在查：可用的评分标准… 6 秒”。
- 规则模式和快捷按钮没有进度，跟现在一样很快返回。
- 回复到了以后，进度行消失，回复和卡片一起出现。

## 4. 后端

### 4.1 事件从哪来

- `RunContext` 加一个 `emit` 字段（`emit(kind, data)`：`kind` 是事件种类，`data` 是字典）和 `progress(label)` 方法。`emit` 默认是 None，这时 `progress` 什么都不做，原来的 JSON 接口、测试和助手评测都不受影响；连续两次同一句只发一次。
- 只在这几处发事件：
  - `runner._try_agent_turn` 开始时；
  - `compaction.maybe_compact` 的 `summarize` 回调里，也就是真的要发摘要请求时；
  - `turn._tools_node` 调用业务工具之前，按工具的 `kind` 和 `title` 查表；
  - `turn._tools_node` 判定回复不合格、要退回模型重写时。
- 进度文字只来自一张固定的表（新文件 `assistant/agent/progress.py`）。唯一的参数是工具目录里写死的标题，不含模型输出、学生文字或分数。

### 4.2 新接口

`POST /assistant/conversations/{id}/runs/stream`。请求体和 `/runs` 相同，返回 `text/event-stream`：

```
event: accepted
data: {}

event: progress
data: {"label": "正在查：可用的评分标准…", "step": 2}

: ping                      （每 15 秒一次，防止代理把空闲连接断开）

event: done
data: {与 /runs 的返回体相同：messages、pending、conversation}

event: error
data: {"status": 500, "detail": "…"}
```

- 会话归属、角色、请求体校验和抢运行锁都在开始推送之前做完。不通过的照旧返回 404、409、422 这些普通响应，前端按现在的方式处理。
- 开始推送之后再出错，状态码已经是 200 了，改发 `error` 事件。
- `done` 的数据和 `/runs` 完全一样，前端的合并逻辑不用改。
- 响应头：路由上已经有 `Cache-Control: private, no-store`，再加 `X-Accel-Buffering: no`。
- `/runs` 保留：`resume` 和 `select` 不调模型、很快，仍走它；开关关闭时说话也走它。流式失败**不退回 `/runs` 重发**（请求可能已经被处理）：开始推送前的 4xx 照常报错；5xx、5xx 的 `error` 事件和连接中断先核对会话（§5）。

### 4.3 运行和连接分开

- **怎么跑**：接口是 async 的，先在线程池里做校验、抢运行锁，然后起一个后台线程跑 `runner.run`。
  - 这个线程自己开一个 `SessionLocal`，不用请求的会话。锁已经抢到了，线程只负责最后释放。
  - 事件经 `loop.call_soon_threadsafe` 放进 `asyncio.Queue`，响应生成器从队列里取出来，写成 SSE。
- **老师刷新、关页面、切换组织时**（切换组织时前端会中止在途请求）：生成器被取消，但后台线程照样跑完、提交、释放锁。回复会存进会话，重新打开就能看到。
- **进程退出时**（发版）：线程跟着结束。这和现在一样：事务没有提交，锁 120 秒后过期（`runner.LOCK_SECONDS`）。
- **权限**：请求用的会话没有设置 RLS 变量（`db/session.get_db` 只是 `SessionLocal()`），所以后台线程新开的会话权限完全一样。
- **并发**：uvicorn 只有一个进程（`deploy/production/compose.yml`）。每个进行中的回合多占一个后台线程和一个数据库会话。时长通常在 Agent 回合 60 秒的预算之内，但这个预算只在步骤之间检查，正在执行的模型请求或工具调用会跑完，所以没有硬上限；运行锁 120 秒过期只是防卡死，不会中断线程。按现在的用户量不设上限。日志记每个回合的结果与耗时（`assistant_stream_run`）和连接断开（`assistant_stream_disconnected`），不够了再加限制。

### 4.4 会话是不是正在运行

`AssistantConversationRead` 加一个只读字段 `running`，即 `run_locked_until` 晚于当前时间。前端断线之后靠它判断还要不要继续等。

### 4.5 开关

- 新环境变量 `ASSISTANT_STREAM_ENABLED`，默认关。
- `/assistant/settings` 返回 `stream_enabled`，前端据此决定走哪个接口。开关关闭时 `/runs/stream` 返回 404。
- 生产经仓库变量打开：开关列在 `scripts/production_env.py` 的可选开关里，部署流水线（`ci.yml` 的 Lightsail 部署任务、`production-cutover.yml`）的 env 把仓库变量传进去；`deploy/production/compose.yml` 用 `env_file: .env` 整体传给应用，不用改。

## 5. 前端

- **流式请求**：`api/client.js` 加 `postStream(path, body, { onEvent })`，用 fetch 加 `ReadableStream` 逐块解析 SSE。浏览器自带的 `EventSource` 只支持 GET，所以不用它。组织头、契约守卫、`StaleContextError`、切换组织时中止，这些都照 `request` 的做法。
- **发送**（`store.send`）：开关打开时走流式。
  - `progress`：更新 `store.progress`，记下当前文字和这一步开始的时间。
  - `done`：走现在的合并逻辑。
  - 开始推送前就返回的 4xx：后端确实没收下，显示原因，把本地消息标成“没有发出去”。
  - 5xx 的 `error` 事件、开始推送前就返回的 5xx：说不准有没有收下，和断线一样先核对会话（见下一条）；会话里已经有这句话就照常显示，不报错。
- **断线取回**：请求已经发出、还没收到 `done` 时连接断了，不要重发，以免多发一条。11-06 起 5xx 与 `error` 事件也走同一个取回（`/runs` 一样），后端自己返回的 5xx 只读一次会话、不等 `running`；等不到结束标“还不确定”，不给重发。
  - 显示“连接中断，正在取回结果…”，每 2 秒 `GET` 一次会话。
  - `running` 变成 false 之后，按文字找这句话（附件按“评分这 N 份文件”）：有就用返回的消息替换本地消息；没有也不标“没有发出去”，标“还不确定”——请求可能还在路上、还没拿到运行锁（#79 复审）。
  - 最多等 70 秒（回合上限 60 秒加余量），还没结束就提示老师刷新页面。
- **进度显示**：`ChatThread` 里的“正在整理…”换成 `store.progress` 的文字。
- **不做打字机式逐字展开**，见第 11 节 Q2。

## 6. 部署

- **压缩会卡住推送**：生产 Caddy（`deploy/production/caddy/Caddyfile`）对整站开了 `encode zstd gzip`。压缩器可能攒够一段才发出去，SSE 就会被卡住。
  - 把流式路径排除在压缩之外：两份 Caddyfile 都定义 `@compressible not path */runs/stream`，写成 `encode @compressible zstd gzip`。用后缀匹配，不依赖 API 前缀。
  - `reverse_proxy` 遇到 `text/event-stream` 默认会立即转发，但要在实例上用 `curl -N` 实测，事件要一条一条到，不能攒到最后一起到。
  - 内网用的 `deploy/Caddyfile` 同步改。
- **FastAPI 直接托管**（本地、内网直连）不经过 Caddy，不受影响。
- **Vercel** 已经不再部署，不用考虑。

## 7. 接口契约

- 只新增接口和 `running` 字段，旧接口不变，所以 `API_CONTRACT_VERSION` 不用改。按 `core/contract.py` 的规则，只有停用或改变前端在用的接口时才改它。前端、后端和 `public/` 都在同一个镜像里，一起发布。
- OpenAPI 里给 `/runs/stream` 声明 `text/event-stream` 响应，用 `api:dump && api:check` 重新生成 `schema.d.ts`。

## 8. 测试

**后端**（离线，用脚本化的假模型）：

- 事件顺序是 `accepted` → `progress`（`rubric_list` 的标题）→ `done`，且 `done` 和 `/runs` 的返回体一致。
- 进度文字只来自固定表：模型输出里的字不会出现在任何一条 `progress` 里。
- 运行锁被占时直接返回 409，不开始推送；会话不属于自己时返回 404；开关关闭时返回 404。
- 读到一半断开：后台线程仍然提交，重新打开会话能看到回复，锁已经释放。
- 规则模式和快捷按钮只有 `accepted` 和 `done`。

**前端**：

- SSE 解析：一个事件跨两块、一块里有多个事件、心跳行。
- store：进度更新、`done`、`error`、断线后取回。
- `ChatThread`：显示进度文字。

**浏览器验收**：e2e 的后端用 Mock LLM，没有 Agent 回合，所以只验证流式接口下的发送、显示和断线取回。Agent 回合的进度由后端测试覆盖。

**生产核实**：打开开关后，在 Lightsail 上问一句需要查数据的话（例如“有哪些评分标准”），看进度是不是一步一步出来的；再用 `curl -N` 确认事件不是攒到最后一起到的。

## 10. 放弃了什么

- **逐字输出模型写的文字**：理由见 §2.1。
- **WebSocket**：要双向长连接、单独的鉴权和重连，Caddy 也要另配。这里只需要服务器单向推送。
- **轮询进度接口**（把进度写进数据库，前端每秒查一次）：每一步都要写库，还得和运行锁、回合的事务分开提交。SSE 不落库。
- **把进度写成对话消息**：会进入历史，Agent 下一轮会看到，而且会改写对话记录。
- **断点续传**（`Last-Event-ID`）：要把事件存下来。断线之后能取回最终结果就够了，中间的进度丢了无所谓。
- **`resume`、`select` 也走流式**：它们不调模型，本来就很快。

## 11. 确认结果（维护者 2026-11-05：都按推荐）

1. **Q1 进度怎么显示**：只显示当前一步加秒数（推荐），还是把已完成的几步也列出来？
2. **Q2 要不要打字机式展开**：回复到了以后逐字展开，只展开校验过的文字，系统设置“减少动态效果”时不展开。推荐不做：校验过的整段直接出现更利索，逐字展开只是观感，还会拖慢阅读。
3. **Q3 开关怎么开**：默认关，到 S3 在 Lightsail 上核实后再打开（推荐）。
4. **Q4 限流时要不要提示**：遇到 429 原地重试时显示“模型有点忙，稍等…”，需要从 `transport` 往上传一个回调，改动稍大。推荐先不做，进度停在上一步。
5. **Q5 怎么分 PR**：S1 和 S2 合成一个 PR（推荐），还是分开提？
