# 部署指南（Vercel 生产与内网试点）

公网生产使用 GitHub Actions 门禁后的 Vercel 预构建发布；内网试点形态使用 Caddy HTTPS 反代 + FastAPI 静态 Web/API + Postgres。CLI/纯本地形态见 `docs/本地模型与离线部署.md`。

---

## 1. 准备

- Docker Engine + Docker Compose。
- 一个内网访问名，例如 `paper-grading.local` / `paper-grading.lan`，由内网 DNS 或客户端 hosts 文件指向部署机器。
- 一个 LLM provider（Mock / 本地私有模型 / 云 APIKey，见 §4）。
- 一个已提交、可追溯的发布 revision；不要从包含未提交改动的工作区直接构建生产镜像。

发布 revision 必须先通过 GitHub Actions 的三项门禁：

- `pgs-unit-and-sqlite-evidence`：锁文件全量测试。
- `pgs-postgres-migration-restore-evidence`：Postgres 16 迁移、约束与隔离恢复。
- `pgs-docker-compose-smoke-evidence`：构建并启动完整 Compose 栈，验证 HTTPS、登录、合成文档上传/解析/Mock 评分、HTML/Excel 和容器内备份。

## 2. Vercel 生产发布

### 当前权威发布链路

生产部署方式已经从 Vercel Git 集成/人工提升切换为 **GitHub Actions 门禁后部署**：

1. 在功能分支完成修改和测试，按保护规则合入 `main`。
2. `main` 的 push 触发 `.github/workflows/ci.yml` 中的 `pgs-production-gates`。
3. `unit-and-sqlite-migrations` 与 `postgres-migrations-constraints-and-restore` 并行运行；成功后执行 `docker-compose-smoke`。
4. 三项门禁全部成功后，`deploy-vercel-production` 才进入 GitHub `production` Environment。
5. 部署任务依次执行 `vercel pull --environment=production`、`vercel build --prod`、`vercel deploy --prebuilt --prod`，并把生产 URL 写入 GitHub Job Summary。

`vercel.json` 的 `git.deploymentEnabled=false` 会关闭 Vercel Git 集成的自动部署，避免同一提交被 GitHub Actions 与 Vercel Git 集成重复发布。不得从本地未提交工作区直接执行生产部署，也不得用 Preview 成功替代上述生产门禁。

### GitHub Environment 与 Secret

仓库必须存在名称完全为 `production` 的 GitHub Environment，并配置：

| Secret | 来源与要求 |
|---|---|
| `VERCEL_TOKEN` | Vercel Account Settings 创建的长期 Access Token；必须能访问目标团队和项目，不能使用会过期的本机 CLI 登录会话令牌。 |
| `VERCEL_ORG_ID` | `vercel link` 生成的 `.vercel/project.json` 中的 `orgId`。 |
| `VERCEL_PROJECT_ID` | 同一文件中的 `projectId`。 |

Secret 只存 GitHub Environment，不得写入仓库、Actions 日志、artifact 或部署摘要。`Validate Vercel deployment secrets` 只能确认值非空；若 `vercel pull` 报 `Could not retrieve Project Settings`，应核对 Token 权限及两个 ID 是否属于同一个 Vercel 项目。

### CLI 固定版本与升级条件

生产任务当前固定 `vercel@58.4.0`。Vercel CLI `58.4.4+` 会在 `deploy --prebuilt` 时重新把 `.vercelignore` 应用于 Python 构建产物的 `filePathMap`，可能导致远端组装时报 `ENOENT`（上游：[vercel/vercel#17386](https://github.com/vercel/vercel/issues/17386)）。不要通过删除 `.vercelignore` 规避，这会扩大上传范围并削弱 Secret/开发文件隔离。

只有在上游确认修复后，才允许在独立分支升级 CLI；升级必须通过本仓库全套测试、真实 `vercel build --prod`、`vercel deploy --prebuilt --prod` 和生产 URL 冒烟，再合入 `main`。

### 发布验证与回滚

- 在 Actions run 中确认四个 Job 全部为 `success`，保存 run URL 与三类门禁 artifact。
- 从 Job Summary 读取 Production URL，验证 `/` 与 `/api/system/integrations` 返回 HTTP 200，并抽检内容哈希 JS/CSS。
- 新增 Alembic 迁移时，CI 的隔离 Postgres 演练不等于已迁移生产数据库；必须按变更计划使用独立迁移凭据先备份、验证并升级生产库，再放行依赖新 schema 的应用版本。
- 若门禁失败，不会执行部署；修复后提交新的 `main` revision。仅 Secret 配置错误且代码未变化时，可以重跑失败 Job。
- 若 Vercel 新版本已 Ready 但线上冒烟失败，在 Vercel 回滚到上一 Ready deployment，并在 GitHub/值班记录中保留失败 revision、部署 URL 与原因；不得改写历史评分结果。

完整证据填写在 [生产上线与灾备验收清单](上线清单.md)。

## 3. Docker Compose 起服务

```bash
git clone <repo> && cd paper-grading-system
cp .env.intranet.example .env.intranet
# 编辑 .env.intranet：至少改 POSTGRES_PASSWORD / AUTH_PASSWORD / AUTH_SECRET / PAPER_GRADING_SITE
docker compose --env-file .env.intranet up -d --build
```

Compose 会启动三类服务：

- `db`：Postgres 16，数据在 Docker volume `postgres_data`。
- `app`：FastAPI + 静态 Web 前端；容器启动时先执行 `alembic upgrade head`，再启动 Uvicorn。
- `caddy`：HTTPS 反代，默认监听宿主机 `80/443`，应用数据在 `app_storage`，Caddy 内部 CA 在 `caddy_data`。

访问：

```text
https://paper-grading.local/
```

健康/集成自检：

```text
https://paper-grading.local/api/system/integrations
https://paper-grading.local/api/system/llm-check
```

确认应用镜像内的备份客户端与数据库主版本一致：

```bash
docker compose --env-file .env.intranet exec app pg_dump --version
# 预期：pg_dump (PostgreSQL) 16.x
```

CI 使用 `python -m backend.app.scripts.seed_dev` 和合成 DOCX 执行完整冒烟；该 seed 仅用于一次性 CI/验收数据库，不得在承载真实数据的生产库中运行。生产首次启动后，应由负责人通过 Web 导入、审核并发布获授权的正式评分标准。

### 信任内网 HTTPS 证书

Caddy 使用 `tls internal` 生成内网证书。试点机器第一次访问可能看到浏览器证书警告。可从容器导出 Caddy 内部 CA 根证书，并安装到试点客户端的受信任根证书中：

```bash
docker compose --env-file .env.intranet cp caddy:/data/caddy/pki/authorities/local/root.crt ./paper-grading-root.crt
```

之后把 `paper-grading-root.crt` 分发给试点教师/管理员机器安装。若内网已有正式域名证书，也可改 `deploy/Caddyfile`，去掉 `tls internal` 并挂载正式证书。

## 4. 配 LLM（Mock / 本地 / 云）

`.env.intranet` 里选择一套预设：

- Mock：`LLM_PROVIDER=mock`，不触网，适合验流程。
- 本地私有模型：`LLM_PROVIDER=local` + `LOCAL_LLM_BASE_URL`。若模型跑在宿主机，容器内可用 `http://host.docker.internal:<port>/v1`；若模型也是容器，用服务名。
- 云：`LLM_PROVIDER=openai` 或 `openai_compatible` + API Key。该模式会外呼厂商，需试点单位明确允许。多用户鉴权部署还必须显式设置 `PLATFORM_MANAGED_LLM_ENABLED=true`；否则只能使用私有 BYOK 连接或 Mock，避免无意使用共享 `.env` Key。

内网试点建议先用 Mock 验证账号、上传、报告和备份，再切本地私有模型或已批准的云模型。

## 5. 鉴权（单租户简单登录）

`.env.intranet.example` 默认开启：

```bash
AUTH_ENABLED=true
AUTH_USERNAME=admin
AUTH_PASSWORD=<强密码>
AUTH_SECRET=<随机长串>
AUTH_TOKEN_TTL_SECONDS=86400
```

开启后数据类端点（rubrics/batches/papers/scoring/exports/calibration）需登录；`/api/auth/login` 建立 `HttpOnly`、`Secure`、`SameSite` Cookie 会话，前端不保存 Bearer Token 或 API Key。`/api/system/*` 与 `/api/auth/*` 保持开放（登录页/自检需登录前可达）。试点期间不要共用弱密码；人员变动后应轮换 `AUTH_PASSWORD` 和 `AUTH_SECRET`。

> 单租户：一套共享凭据保护整个部署；`owner_id` 列已预留，将来多用户隔离在此基础上扩展。

## 6. 持久化与备份

- Postgres：Docker volume `postgres_data`。
- 论文/解析/报告/导出/LLM 缓存：Docker volume `app_storage`，挂载到容器 `/app/storage`。
- Caddy 内部 CA/证书：`caddy_data`。

使用内置工具同时备份 Postgres 与完整 `app_storage`；数据库密码只通过 libpq 子进程环境传递，不进入命令参数、manifest 或报告：

```bash
docker compose --env-file .env.intranet exec app \
  python -m backend.app.scripts.ops_backup create \
  --storage-root /app/storage --destination /app/ops_backups \
  --migration-head 0023_rule_scoring_review_tasks --revision <部署commit>
```

复制备份包到仓库外受控存储后执行 `ops_backup verify <package>`。恢复演练必须使用隔离 recovery database 和空 storage 目录，并显式传 `--confirm-database <精确库名>`；工具会先验证全部 SHA-256，再运行 `pg_restore`，不会覆盖非空目录。操作步骤和 RTO/RPO 记录见 [生产上线与灾备验收清单](上线清单.md)。

## 7. 运维要点

- 迁移：`app` 容器启动时会自动执行 `alembic upgrade head`；当前 head 为 `0023_rule_scoring_review_tasks`，迁移链由 `test_migrations.py` 守护。0017 的 `batch_scoring_jobs` / `batch_scoring_items`、0022 的历史租户归属以及 0023 的规则检查点/人工复核任务都是恢复与审计状态，存在真实数据时降级会拒绝数据丢失。0022 会将升级前所有资源归入默认组织、保留历史模型/结果，并且不会从 `.env` 复制任何 AI Key。
- 上传体积：Caddy 用 `CADDY_MAX_UPLOAD_SIZE` 限制请求体，应用侧保留 `MAX_UPLOAD_SIZE_MB` 配置。
- 隐私：`LLM_DEBUG_LOG_ENABLED=false`，否则日志可能含论文/学生 PII。
- 启动安全：`AUTH_ENABLED=true` 时，登录密码必须至少 12 位且非默认/用户名，`AUTH_SECRET` 至少 32 位且非占位；同时必须关闭 LLM 原文 debug。任一条件不满足即拒绝启动。
- OPS 诊断：鉴权后读取 `/api/system/ops-readiness`，检查磁盘、数据库容量、批任务心跳、LLM 失败率和安全配置。阈值由 `.env.intranet` 的 `OPS_*` 设置并经责任人批准；该端点固定 `production_default_switch_authorized=false`。
- 日志：`docker compose --env-file .env.intranet logs -f app caddy`。
- 升级：拉取新代码后执行 `docker compose --env-file .env.intranet up -d --build`。
- 评分定位：系统为"粗档辅助评分 + 人工复核"，不作可信排名（详见报告内说明 / `代码改造计划.md` §0）。

### M8 / GATE-03 发布边界

- 切换前运行 `pgs core-cutover-audit --json`。它只验证所有活跃 published RubricVersion 可重放、legacy compatibility 节点明确可执行；报告即使无 blocker 也固定为 `production_default_switch_authorized=false`。
- 正式批评分应先由获授权用户通过 Web 或 `POST /api/batches/{id}/score-jobs` 提交**经批准的观察策略**，再调用 `/api/batch-scoring-jobs/{id}/run`；状态、并发上限、租约心跳、逐论文检查点、错误尝试历史和指标都保存在数据库。`cancel` 协作取消未启动项，`retry` 只恢复失败/取消项；心跳未过期的运行任务不允许第二执行者接管。
- 观察信号覆盖 legacy/Core paired delta、无效证据、未授权规则、人工复核、按 Profile+RubricVersion 的缓存命中、checker/LLM/429/timeout、延迟和重试。任何 paired comparison、样本窗口、阈值或指标缺失都 fail closed；PGS-6 报告不能代替 GATE-03 批准。
- 当前 `SCORING_ENGINE_MODE` 默认 `legacy`。这只影响 `legacy_unversioned` compatibility，不会让正式 published RubricVersion 绕过 Core。
- GATE-03 必须在仓库外冻结真实 dataset/truth、唯一 published immutable RubricVersion、DocumentSnapshot manifest、不可变 model/provider artifact、policy/plan/prompt/anchors/checker/revision，并确认 anchors 与 holdout 排除。
- 只有门禁产物为 `gating_eligible=true`、全部阈值与回退容差通过且取得维护者批准后，才允许生产默认切换；test-only Mock/parity 结果不能授权切换。
- 若观察窗口内触发批准的回退条件，只回退未版本化入口到 legacy compatibility；历史权威 run 与已发布版本不改写。

## 8. 本机开发启动

如果只做开发/冒烟，不用 Docker app 栈：

```bash
docker compose --env-file .env.intranet up -d db
uv sync
uv run alembic upgrade head
uv run python -m backend.app.scripts.seed_dev
uv run uvicorn backend.app.main:app --reload --port 8000
```
