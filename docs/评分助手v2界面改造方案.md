# 评分助手 v2 界面改造方案

状态：已确认（2026-10-29，§9 全部按推荐），已实施（分支 `claude/assistant-v2-ui`）；§7 两项与“排除”落库待下一轮
实施偏离：①“排除”落库不可行——发布门禁要求每条细则都 approved，驳回的会挡住发布，按 §5.1 约定改为单独补后端，本轮核对视图只做“确认”；
②`next_steps` 不进 `QUICK_ACTIONS`（那里的键写在 Agent `reply.next_steps` 的工具定义里，加键会改提示词指纹），单独放 `views.CHIP_ACTIONS`；
③会话进度存 `focus.progress`（plan 每次改卡片时同步），不给 `AssistantConversationRead` 加字段，免得列会话时逐个读消息；
④确认开始只剩“开始评分 / 不评了”，“重新选择文件”去掉（上传后没有删除已解析材料的动作）；带附件开始时由建任务那一步发一张 `upload_papers` 卡片承接等待。
设计稿：Claude Design 项目「作业论文评分系统设计」`评分助手 v2.dc.html`（2026-10-29 版）
关联：`docs/对话评分助手改造方案.md`、`docs/评分助手计划卡片方案.md`、`docs/评分助手Agent化方案.md`

## 1. 设计稿说了什么

三栏：深色会话栏 · 对话 · 工作区。和现在最大的不同是**工作区不再嵌入现有页面（iframe），而是原生的、按步骤组织的面板**：

| 区域 | 设计稿 |
|---|---|
| 会话栏 | 品牌标记 + “有据智评 / 评分助手”；可收成 56px 窄轨；“＋ 新对话”；“最近”列表每条两行：标题 + “步骤 2/8 · 今天 10:21”或“已完成 · 10月24日”；底部“助手模型设置”“返回工作台”。窗口 < 1240px 默认收起 |
| 对话头 | 60px：会话标题 + 等宽字体的模型行；工作区收起时出现“打开工作区 [2/8]” |
| 消息 | 居中，最宽 720px。助手消息带头像、“有据智评 10:22”；老师消息是深绿气泡；附件显示为带扩展名色块的文件卡；“你发布了《…》v1.0 · 10:55”这类事件显示为分隔线；消息里的卡片只是一个**入口按钮**（“01 核对评分规则 · 2/6 项已确认”→“在右侧查看 / 正在右侧显示”） |
| 输入区 | 自上而下：**任务条**（“待你处理 · 核对评分规则，还有 4 项未确认 [继续核对]”，进行中时带进度条）、**建议问题**（随步骤变化）、输入框（附件图标、自动增高 34–140px、发送） |
| 工作区头 | **标签**：第一个固定是“任务”，其后是本会话问出来的结果（进展 / 解释 / 建议 / 待办，各有颜色标签）；放不下的收进“更多 · N”；右侧“全宽/还原”“收起”。任务标签下是 **8 段步骤条**（完成绿、当前琥珀、未到灰；宽度不够时只显示当前步骤名） |
| 工作区体 | 任务标签按步骤显示：来源文件解析 · 核对评分规则 · 评分模型 · 待评分文件（上传、预检、确认共用）· 评分进度 · 评分结果汇报。看已完成的步骤时顶部有“正在查看已完成的步骤 · 回到当前：…”。结果标签：进展快照（带“刷新”）、细则来源解释、单篇得分解释、改进建议（采纳/忽略）、待办清单 |
| 工作区底 | 固定操作条：左边一句状态，右边主按钮（“确认本项 3 条，下一项”“发布评分标准 v1.0”“开始评分 · 12 篇”“前往结果复核”） |
| 交互 | 分隔条可拖（400px 到“总宽 − 400px”，记在本机，双击恢复 560）；老师 60 秒内在任务标签上操作过时，新结果不抢焦点，改为顶部黑条“新结果：… 查看 / 稍后”；窗口 < 1000px 时工作区盖在对话上，按钮变成“返回对话” |

步骤顺序（设计稿 8 步）：导入标准 → 核对发布 → 评分模型 → **选择文件 → 上传预检 → 确认开始** → 评分 → 汇报结果。

## 2. 和现状的差距

| 方面 | 现状 | 设计稿 | 改动落在 |
|---|---|---|---|
| 工作区 | iframe 嵌现有页面，`focus.workspace` 决定显示哪页 | 原生面板：任务标签按计划步骤显示，结果另开标签 | 前端重写；后端 `show_workspace` 不再驱动界面 |
| 卡片 | 交互全在对话卡片里（选文件、确认开始、移除文件、导入表单…） | 对话里只放入口；需要老师做的事放在**任务条 + 工作区底部操作条** | 前端 |
| 步骤条 | 计划卡片在对话里，标题下一行“第 3/7 步” | 工作区顶部步骤条，会话栏也显示“步骤 x/n” | 前端；会话列表接口加进度 |
| 流程顺序 | 选文件 → **确认** → 上传与预检 → 评分 | 选文件 → **上传预检 → 确认** → 评分 | 后端流程图 |
| 无法评分的文件 | 预检后单独再问一次“移除吗” | 预检结果直接显示在确认那一步 | 后端流程图 |
| 事件 | 无 | “你发布了《…》v1.0”分隔线 | 后端写事件消息 |
| 结果汇报 | 概览卡片五个数字 | 统计 + 分数分布 + 建议复核（带原因）+ 全部成绩 | 前端；批次汇总补复核原因 |
| 细则来源解释、改进建议 | 无 | 有 | **新能力，本轮不做**（§7） |

色板、字体、圆角在工作台已经和设计稿同源（`tokens.css` 取自同一个设计项目），不需要换主题。

## 3. 前端方案

### 3.1 拆分

现在的 `AssistantView.vue`（285 行）+ `AssistantCard.vue`（429 行）拆成：

```
views/AssistantView.vue              三栏骨架、分隔条拖动、窄屏覆盖
components/assistant/
  ConversationRail.vue               会话栏（展开 / 窄轨）
  ChatThread.vue                     消息、事件分隔线、入口卡片、空会话欢迎
  （components/AssistantCard.vue 保留，只留对话里的交互卡片，见 3.3）
  EntryCard.vue                      流程卡片与结果卡片在对话里的“在右侧查看”入口
  ChatComposer.vue                   任务条 + 建议问题 + 输入框
  WorkspacePanel.vue                 标签、更多、步骤条、新结果提示、底部操作条
  ws/WsLayout.vue                    各视图共用的骨架：滚动正文 + 底部操作条
  ws/SourceStep.vue                  来源文件解析（导入流程第 1 步，含导入表单）
  ws/RubricStep.vue                  评分标准（评分流程第 1 步：用哪份、换一份）
  ws/ReviewStep.vue                  核对评分规则（导入流程第 2 步）
  ws/ModelStep.vue                   评分模型
  ws/FilesStep.vue                   待评分文件（选择、上传预检、确认）
  ws/GradingStep.vue                 评分进度
  ws/ReportStep.vue                  评分结果汇报
  ws/ProgressArtifact.vue            进展快照
  ws/PaperArtifact.vue               单篇得分解释
  ws/TodoArtifact.vue                待办清单
lib/assistant-workspace.js           纯函数：步骤 → 视图、标签容量、任务条、建议问题、待办、快照
```

`stores/assistant.js` 增加工作区状态：当前标签、正在看的步骤、工作区模式（open / closed / focus）、宽度、新结果提示、最近一次在任务标签上操作的时间。宽度存 `localStorage`（读写包 try/catch，取不到就用 560）。

### 3.2 数据从哪来

工作区不另建“工作区状态”表：**任务标签 = 最近一张计划卡片**（步骤与状态都在卡片上，后端每走一步更新），**结果标签 = 本会话消息里的结果卡片**。刷新页面后从消息重建，和对话保持一致。步骤条按卡片上的步数画：导入流程 8 步（与设计稿一致），用已发布标准直接评分是 7 步（第 1 步是“评分标准”，没有导入与核对）。

| 视图 | 数据 | 写动作 |
|---|---|---|
| 来源文件解析 | 导入会话 `GET /rubrics/import-sessions/{id}`、评分标准评分项 | 等待导入时显示导入表单（现有 `importRubric`） |
| 评分标准 | `focus.rubric_*`、已发布列表 | “换一份”（§4.3） |
| 核对评分规则 | `GET /rubrics/{id}/review-workspace` | 确认 / 排除 / 撤销 / 发布，调用与评分标准页**同一组接口**（§5.1） |
| 评分模型 | 计划卡片 `model` 步的说明 | “更换”打开账户与连接页 |
| 待评分文件 | 本页选中的文件、上传队列（`upload` store）、确认卡片上的预检结果 | 选择文件、开始评分、不评了 |
| 评分进度 | `GET /batches/{id}/score-jobs/latest` + 批次汇总 | 取消剩余（现有 `confirm_cancel`） |
| 评分结果汇报 | 批次汇总 | 导出成绩表、前往结果复核 |
| 进展快照 | 卡片里存的快照 | “刷新”在本页按当前计划重算（不落库，刷新页面后回到提问时的那份） |
| 单篇得分解释 | `GET /scoring-runs/{run}/items?include_view=true`（现 `paper_result`） | 在结果复核中打开 |
| 待办 | 计划卡片 + 等待中的步骤，实时计算 | 每项的按钮就是那一步的主动作 |

不在流程里的查询（例如新对话里问“评分进度”，选了某个任务）没有计划卡片：工作区没有任务标签，结果直接开成结果标签。现有 `overview` / `review_list` 卡片打开成“结果”标签，复用汇报视图——这是设计稿之外加的一种标签。

### 3.3 哪些卡片留在对话里

工作区接管“流程里等老师做的事”：选文件、导入表单、确认开始、核对发布、看进度。对话里只留一个入口按钮。

仍在对话里交互的，是**对话本身产生的选择**：选择任务 / 选择材料、重试确认、取消确认、“要放弃上一步吗”、失败诊断。按设计稿的样式重做（白底细边框、10px 圆角、主按钮深绿），逻辑不变。

### 3.4 任务条与建议问题

- 任务条由“等待中的步骤 + 计划卡片”算出：等老师时琥珀色“待你处理”+ 主按钮（与底部操作条同一个动作）；后台进行时绿色“进行中”+ 进度条；工作区已经显示这一步时，按钮换成“已在右侧打开”。
- 建议问题按步骤给 2–3 个，发出时带 `quick_action`，后端按键直接分派，不经规则与模型。用现有的 `query_progress`、`query_paper`、`query_review`，新增一个 `next_steps`（“接下来我要做什么？”，§4.5）。

### 3.5 页面导航

“在评分标准页打开”“前往结果复核”“更换（模型）”这类链接**在新标签页打开**：选好的待评分文件只在本页内存里，跳走就丢了（现在靠刷新后“重新选择这批文件”兜底）。

## 4. 后端与接口

### 4.1 流程顺序：先上传预检，再确认

新顺序：`files → upload → confirm → scoring → report`。

```
wait_files ─► create_batch ─► wait_upload ─► precheck ─► propose_start ─► wait_confirm ─┬─► start_scoring
                                                                                     ├─► remove_papers ─► start_scoring
                                                                                     └─► 结束（任务留作草稿）
```

- 选完文件就建任务、上传、预检。建任务从“确认之后”提前到“选完文件之后”：老师上传文件这个动作本身就是要评这批文件，建的是草稿任务，不开评。
- 确认卡片带上预检结果：可评 N 份、需注意几份（扫描件等，照常评分并标记需复核）、无法评分几份。无法评分的文件**并入这一步**：按钮是“移除 2 份，开始评分 · 10 份”，不再单独问一次。
- “不评了”：任务保留为草稿（与现在预检后放弃一致），回复里给出任务名。
- ~~“重新选择文件”：回到选文件，上一批草稿任务删除~~ 实施时去掉（偏离 ④）：上传后没有删除已解析材料的动作。
- 计划步骤键顺序随之调整；`plan.STEPS` 的键名不变，只换顺序。
- 已在旧顺序上等待确认的流程（状态里没有 `batch_id`）：恢复时作废，回复“流程已更新，请重新说开始评分”。生产 Supabase 迁出后没有评分标准，预计没有这样的流程。

### 4.2 无法评分的判定不变

`blocking_findings` 照旧把预检结果分成“可移除”与“还没解析完”。还没解析完的照旧结束流程、提示稍后重试。

### 4.3 换评分标准挪到第 1 步

确认时任务已经建好，评分标准跟着任务定了，不能再换。“换一份”挪到评分标准那一步：等选文件时，`pick_files` 的恢复值多接受 `{"action": "change_rubric", "rubric_id": …}`，更新计划卡片第 1 步并继续等选文件。上传后要换，就“不评了”再重新开始。

### 4.4 事件消息

老师在工作区做的、会推进流程的动作，用一条事件消息记下：`ctx.event(text)` 写一条 `intent="event"` 的助手消息，前端显示成分隔线。本轮只有一处：发布评分标准（`watch_rubric` 核对到已发布时）。不加角色、不加迁移。事件消息不进 Agent 上下文。

### 4.5 新快捷动作 `next_steps`

“接下来我要做什么？”：回一句话 + 一张 `todo` 卡片（只有编号），清单内容由前端按计划实时计算。不经模型。`QuickAction` 字面量、前端 `QUICK_ACTIONS`、`views.QUICK_ACTIONS` 三处同步。

### 4.6 进展快照卡片

流程里问进展（`query_progress` 快捷动作，会话有进行中的计划时）：回一张 `progress_snapshot` 卡片，存提问时的计划步骤副本与评分计数、时间。没有计划时行为不变（选任务 → 进度）。

### 4.7 接口字段

| 接口 | 改动 |
|---|---|
| `GET /assistant/conversations`、会话详情 | `focus.progress`：`{"status": "running" \| "done" \| …, "step": 2, "total": 8}`，计划卡片每次更新时同步；没有计划时没有这个键（实施偏离 ③） |
| `POST …/runs` | `quick_action` 加 `next_steps`；`pick_files` 的恢复值可以是 `{"action": "change_rubric", "rubric_id"}`；`confirm_start` 只剩 `confirm` / `cancel`（确认即移除无法评分的文件，实施偏离 ④） |
| `GET /batches/{id}/summary` | `BatchPaperSummary` 加 `latest_review_reasons: list[str]`（最近一次评分里需要复核的评分项与原因，“T03 名称：原因”，每份最多 3 条），汇报页“建议人工复核”用 |

响应只加字段；确认卡片的恢复值少了“换评分标准 / 重新选择文件”，所以契约版本升为 `2026-10-29.assistant-v2`（旧页面自动刷新）。OpenAPI 合同快照（`api:dump && api:check`）随之更新。**不需要迁移**。

### 4.8 Agent

- 系统提示、工具与登记表都不改，提示词指纹不变，上线门槛不拦。
- 模型看得到的两处说明要跟着流程改：`agent/context.PENDING_DETAILS` 里 `confirm_start`、`confirm_remove`，以及帮助条目 `grading.start`（“点开始评分才会建任务”不再成立）。这两处不在指纹里。
- 新卡片类型（`progress_snapshot`、`todo`）不加进 `CARD_LABELS`，Agent 看不到。

## 5. 其它页面

色板与基础组件已经同源，不做全站翻新。要统一的是**同一份内容在助手工作区和独立页面各显示一次**的地方：抽成公共组件，两边用同一个，样式和行为一起对齐。

| 内容 | 独立页面 | 做法 |
|---|---|---|
| 扣分细则核对 | 评分标准页“核对”步（`RuleReviewPanel`） | 抽 `RuleCard`：问题 + 严重度标签 + 扣分（等宽红字）+ 条件 + 来源标签（原文 p[61] / 评分说明 B2 / AI 推断 · 无原文依据）+ 确认 / 排除 / 撤销。评分依据（评分说明 + 原文段落）折叠区同样共用 |
| 上传与预检清单 | 新建任务页 | 抽 `PaperCheckRow`：序号、标题、“姓名 · 类型 · 页数”、状态点 + 文字、需注意时的黄色说明 |
| 评分进度清单 | 任务执行页 | 抽 `PaperProgressRow`：完成显示分数、评分中、排队中、需复核标签 |
| 结果汇报 | 结果复核页顶部 | 抽 `ScoreStats`（三格统计）与 `ScoreBands`（分数分布条） |
| 步骤条 | 评分标准页三步详情 | 步骤条组件改成设计稿的细条样式（完成绿 / 当前琥珀 / 未到灰），两处共用 |

### 5.1 “排除”要真正保存

评分标准页现在的“排除”只存在页面内存里（`excluded` 集合），刷新就没了；设计稿是“确认结果即时保存”，排除后显示“已排除 · 恢复”。改为调用已有接口：排除 → `POST /rules/{code}/reject`，恢复 / 撤销 → `/reopen`。两处页面一起改。实施前先核对：被驳回的规则在发布、编译时是否按“不参与评分”处理，发布门禁是否允许“已确认 + 已驳回”的组合；不是的话，这一条改为单独补后端。

## 6. 放弃了什么

- **不保留 iframe 工作区。** 嵌现有页面的好处是“页面改了助手自动跟着变”，代价是两套导航叠在一起、窄屏难用、工作区的动作和对话卡片各管一半。设计稿要的是按步骤的精简视图，所以改成原生；同一内容靠公共组件保持一致（§5）。`AppShell` 的“嵌入时隐藏侧栏”与 `X-Frame-Options: SAMEORIGIN` 本轮保留，确认没有其它嵌入后再清理。
- **不把工作区状态存库。** 当前标签、宽度、看哪一步都是本机界面状态，刷新后回到“任务标签 + 当前步骤”；宽度存 `localStorage`。
- **进展快照的“刷新”不落库。** 落库要么改原消息（历史被改写），要么再发一条消息（刷一次多一条）；都不如只在本页重算。
- **不做“暂停评分”。** 设计稿评分进度底部有“暂停”，现在没有暂停能力，只有取消剩余；按钮换成“取消剩余”。
- **建任务提前到确认之前**，代价是老师放弃时会留下一个草稿任务（会写明任务名，可以在评分任务页删除）。

## 7. 本轮不做（下一轮单独出方案）

- **细则来源解释**（“这条是从哪来的”→ 评分说明 → AI 的推断 → 生成的细则 → 原文依据）：规则上只记了 `ai_origin` / `ai_model`，没有存推断过程。要补存储或现场生成，属于新能力。
- **改进建议的采纳**（“采纳后写入草稿，需要在核对中重新确认”）：规则审查（`rule_review`）已能给出问题，但没有“一键改写细则”的写动作。
- 这两类结果标签的位置与样式在本轮的标签体系里预留。
