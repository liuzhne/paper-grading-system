## 先看这一条：推送 `main` 会直接触发生产部署

CI 的 `deploy-vercel-production` 条件是：

```yaml
if: github.event_name == 'push' && github.ref == 'refs/heads/main'
```

这 51 个提交现在都在**本地 `main`** 上。直接 `git push` 意味着：全部门禁通过后
**自动部署到生产**，中间没有人工审阅环节。

计划最初要求「重新启一个分支」，中途因为部署那次 PR 合入 main 后继续在 main 上
提交，分支结构没有恢复。**建议先把这些提交移到特性分支再开 PR**，而不是推 main。
这一步会重置本地 `main` 到 `origin/main`，属于会改变仓库状态的操作，等你确认。

## 重点审这 11 个 `fix` 提交

`feat` 提交是按计划新增的能力，`fix` 提交是**实施过程中暴露出来的既有缺陷或我自己
引入的缺陷**——风险集中在这里。其中 7 处是最后一轮自审时发现的，也就是说它们从未
被除我以外的任何人看过。

按危险程度排序：

1. **`fix(api)` 导出审计与预检补上角色门控** —— `POST/PATCH /export-events` 原先只查
   组织归属不查角色，任何能看到批次的成员都能改写导出审计（包括把成功标成失败）。
   审计记录能被随手改写，它就不再是审计。同一轮还查出 `batch_upload_precheck`
   同样没有门控，而它返回逐份材料的文件名。
2. **`fix(session)` 组织切换失败不留半切状态** —— 切换在服务端确认前就改了
   `organizationId`，失败时客户端在 B、服务端在 A，写请求的 `X-Organization-ID`
   指错组织。AppShell 还会用这个值回填选择框，界面看不出发生过失败。
3. **`fix(ops)` 补录脚本对非本地目标默认拒绝** —— RUNBOOK 上那条命令不带
   `DATABASE_URL`，而 `settings` 加载 `.env.local`。**按文档执行一次就会连上生产**，
   去掉 `--dry-run` 就是一次没人授权的生产写入。（我在验证时确实连上了生产，
   是一条立刻报错的 SELECT，未读到数据、无写入。）
4. **`fix(tests)` 阻断测试连到真实部署库** —— 同一类问题的测试侧，`alembic/env.py`
   无条件用 `settings.DATABASE_URL` 覆盖调用方传入的 URL。
5. **`fix(scoring)` 旧写入口接上归档守卫** —— 新端点防了并发与归档，旧 SPA 的改分
   入口没防，等于守卫可以绕过。
6. **`fix(migrations)` 0025-0028 补齐有损降级守卫** —— §7 要求有数据时拒绝降级，
   0024 有、0025-0028 漏了。降级会删掉复核原因、幂等回执与导出审计。
7. **`fix(deploy)` Docker 补 `public/`** —— 镜像里没有工作台产物，容器里访问
   `/workbench` 只会 404。
8. **`fix(api)` 投影与队列补 `no-store`**、**`fix(batches)` 归档补「无活动任务」条件**、
   **`fix(cli)` 归档拒绝翻译成可读退出**、**`fix(workbench)` 判空覆盖 undefined**。
