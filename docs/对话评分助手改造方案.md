# 第一部分：业务方案

## 1. 定位

在工作台中增加“评分助手”，老师在对话里完成整个评分动作：上传待评分文件、确定评分标准、开始评分、查看结果、查询每篇论文的扣分点与证据。

- **流程由系统固定推进**。页面上原本要点按钮的地方，改为助手在对话里提问；用户点“确定”，执行的是与页面按钮相同的后端逻辑。
- **AI 只在不符合要求或出问题时参与**。引入 AI 的目的是让人只做重要的决策。
- **评分的中间过程仍在现有页面上展示**。助手右侧的工作区就是现有页面，用户在对话旁边实时看到每一步的数据。
- **助手的评分权为零**：不判分、不改分、不替用户审核或发布评分标准。评分仍由现有批任务执行；评分结果的权威来源仍是 `ScoringRun` / `ScoreItem` 与人工复核记录。

## 2. 需求（维护者决定）

| # | 决定 |
|---|---|
| U1 | 一期只面向老师与管理员；一期完成后加入学生查询自己论文 |
| U2 | 多数情况复用已发布的评分标准；单个登录用户通过助手一次最多提交 30 份，不设下限；系统总量不设上限，以承载能力为准 |
| U3 | 只在关键节点提问：没上传评分规则和模板时，默认用最新的评分标准；上传了规则和模板时，让用户去确认评分标准 |
| U4 | 可控、不影响评分结果的动作可以自动执行 |
| U5 | 期望自动处理的异常：模型 JSON 输出被截断时调大输出上限；某篇卡住时先跳过（二期，见第 4.4 节） |
| U6 | 上传的是待评分文件 |
| U7 | 对话里可以查询证据、扣分点等客观信息；改分放到后续需求 |
| U8 | 布局与常见 Agent 产品一致 |
| U9 | 第一次使用时让用户配置助手模型；不配置就用自己的连接；没有自己的连接就用平台模型，并提醒会非常慢 |
| U10 | 使用 LangGraph 框架 |

## 4. 使用流程

### 4.1 场景 A：没有上传评分规则和模板（默认）

| 步骤 | 谁来做 | 说明 |
|---|---|---|
| 1. 选文件 | 用户 | 附件按钮或“开始评分”；超过 30 份只收前 30 份并说明（U2、B5） |
| 2. **确认开始评分** | **用户（关键节点）** | 卡片：评分标准（默认取用户可见、最近发布的一份，可换，B6）、文件数、评分用的模型连接 |
| 3. 建任务、上传、解析、预检 | 自动 | 上传由浏览器直传（T5） |
| 4. 移除无法解析的文件 | 有阻断项时由**用户决定**（B1） | 卡片列出文件与原因：“移除这几份，评其余的吗？”没有阻断项时跳过 |
| 5. 开始评分 | 自动 | 工作区切到“评分进度”页 |
| 6. 失败项重试 | 自动（B3） | 失败项全部为临时性错误时自动重试一次 |
| 7. 完成汇报 | 自动 | 平均、最高、最低分，需要复核的份数，失败项诊断，查询入口 |

### 4.2 场景 B：上传了评分规则和模板（一期视时间而定，B9）

1. 用户在专门的卡片里选择规则文件和模板文件，并点明各是哪一份（B2），不让模型猜文件用途。
2. 系统建导入草稿（与评分标准页的“导入”同一个动作），确认前不产生评分标准。
3. **关键节点**：工作区打开评分标准页并定位到这个导入草稿，由用户核对、确认、发布。规则校对是对照原文、合入差异的高密度交互，留在页面上完成。
4. 助手确认标准已发布后，进入场景 A 的第 1 步，评分标准固定为这一份。

### 4.3 查询（只查客观信息，U7）

| 问法示例 | 处理 |
|---|---|
| “评到哪了” | 进度卡片；工作区切到进度页 |
| “第 3 篇扣了哪些分”“张三为什么扣分” | 代码定位论文（上传顺序、姓名或文件名）；卡片列出各项得分、扣分点和证据原文；工作区定位到这篇 |
| “哪些需要复核” | 需要复核的论文列表；复核在工作区的评分工作区里完成 |
| “整体怎么样”“平均分多少” | 分数概览 |

分数、扣分点、证据由前端从接口直接渲染，**不经模型转述**（B8）。定位不唯一时给出选择卡片，不猜。

### 4.4 异常处理

| 情况 | 处理 |
|---|---|
| 失败项全部为临时性错误（限流、超时、服务繁忙、网络、熔断） | 自动重试一次并说明（B3）；重试后仍失败则给诊断 |
| 其它失败 | 诊断卡片：按根因分组列出受影响的文件和处理建议，附“重试失败项”（可重试时） |
| 判断不确定（证据不足、低置信、需要人工复核） | 只汇总哪几篇、哪几项、为什么，引导到复核页；**不给建议分数** |
| 系统缺陷（规则执行失败、未知错误） | 告知“系统错误”并附任务名，不尝试处理 |

**U5 的两个例子放到二期，在评分执行层实现**（B4）：

- **调大输出上限**：批次创建时冻结了连接配置（`ai_connection_snapshot`，含输出上限），改了连接配置后该批次的重试会以 `AI_CONNECTION_CONFIG_CHANGED` 失败。正确做法是在执行层对被截断的规则按固定策略放大一次输出上限重试，不改用户的连接配置。
- **跳过卡住的论文**：即 PR #17 A1 的“连续无进展上限”。
- 放在助手里做，只在对话页开着时生效，从页面发起的任务享受不到。一期助手只识别并说明。

## 5. 一期不做

改分（U7）；学生角色（U1）；在对话里完成规则校对与发布；AI 处理人工复核项或给建议分数；U5 的两项执行层策略；模型对诊断的自然语言解释。

# 第二部分：技术方案

## 6. 总体架构

```
浏览器（AssistantView：只负责展示、输入、上传与轮询）
   │ 用户输入 / 点“确定” / 上传完成 / 发现评分结束
   ▼
POST /api/assistant/conversations/{id}/runs
   ▼
LangGraph 图（库嵌入 FastAPI，T7）
   · 线程 = 当前流程实例；运行到下一个中断点或结束就返回
   · 流程状态存在自写的状态存储（Alembic 表，T3）
   │ 节点调用
   ▼
共享守卫 + 后端服务层（与页面接口相同的权限检查与业务逻辑，T4）
   ▼
数据库 / 批任务（现有执行路径不变）

工作区：现有页面以同源 iframe 嵌入（T10）
```

- **流程推进在后端的图里**；前端不再编排流程，只做浏览器才能做的事：选文件、上传、轮询进度后通知图继续。
- **调模型一律走现有适配器**（T2）：自带连接、Bedrock、同时请求数、限流重试、熔断、用量计量都在适配器里。只用 LangGraph 的图、中断、状态保存三样，不用 LangChain 的模型封装与预制智能体（`create_react_agent` 等）。
- **单次请求时长可控**：每次 `runs` 只运行到下一个中断点；最耗时的是意图识别的一次模型调用（截止 30 秒），远低于 Vercel 300 秒上限。上传在浏览器，评分在批任务，都不占这次请求。

## 7. 图的设计

### 7.1 两类图

| 图 | 用途 | 状态保存 |
|---|---|---|
| **流程图**（有状态） | 场景 A 评分流程、场景 B 导入流程 | 有中断点，必须保存；每个会话同一时间最多一个进行中的流程 |
| **查询图**（无状态） | 意图识别、查询、帮助、没理解时的回复 | 不保存；选择卡片（选任务、选论文）把所需参数放在卡片里，选完发起一次新的查询 |

这样，流程停在“等评分结束”时，用户照样可以随时查询，查询不会打断或改变流程状态。

### 7.2 意图识别（T9、M1）

- 先用规则识别（“进度”“第 N 篇”“复核”“重试”“取消”“开始评分”“上传评分规则和模板”等）；识别不了才调用一次模型（`complete_json`，`attempts_limit=1`，截止 30 秒，不在原地等 429）。
- 模型输入：本句、**用户最近 3 句原话（每句最多 500 字）**、当前任务名与评分标准名。**不含论文原文、证据、助手自己之前的回复**。
- 模型只输出 `{intent, paper_ordinal, paper_name, clarify}`，按 schema 校验，不合格即“没理解”并给快捷按钮。Mock 不用于意图识别。
- 提示词版本 `ASSISTANT_PROMPT_VERSION` 独立于评分的 `PROMPT_VERSION`，改它不影响评分缓存，也不需要重新锚定 QWK。

### 7.3 评分流程图（场景 A）

```
选标准与模型 → ⏸选文件(若还没选) → ⏸确认开始 → 建任务 → ⏸等浏览器上传
→ 校验论文归属 → 预检 → (有可移除的阻断项 → ⏸是否移除 → 移除) → 开评
→ ⏸等评分结束 → 核对任务状态 → (全部临时性失败且未自动重试过 → 重试 → ⏸等评分结束)
→ 诊断与汇报 → 结束
```

| 中断点 | 浏览器恢复时带回 | 后端校验 |
|---|---|---|
| 选文件 | 文件数、文件名 | 1–30 份 |
| 确认开始 | `confirm` / `change_rubric(rubric_id)` / `repick` / `cancel` | 卡片编号与当前中断一致；评分标准已发布且对用户可见 |
| 等浏览器上传 | 论文编号列表 | 论文都属于本批次、本组织；份数 ≤ 30 |
| 是否移除 | `remove` / `cancel` | 待移除的论文仍为“解析失败且从未评分” |
| 等评分结束 | `job_finished` | **以服务器上的任务状态为准**，未结束则继续等待，不信任浏览器 |

### 7.4 导入流程图（场景 B）

```
⏸等浏览器建导入草稿（浏览器调用与评分标准页相同的导入接口，带回草稿编号）
→ 校验草稿归属与状态 → ⏸等用户在工作区确认并发布 → 核对已发布 → 转入评分流程图（评分标准固定）
```

### 7.5 LangGraph 使用约定

- **有副作用的操作（建任务、开评、重试、移除）放在中断点之后的独立节点里，并做成幂等**：恢复时，被中断的节点会从头重跑；建任务节点以流程实例编号作幂等键，重跑时返回同一个任务。
- 中断返回给浏览器的内容只含可 JSON 序列化的数据（卡片类型与编号）。
- 状态里只放编号与标志位（见第 9 节），不用框架自带的消息列表类状态。
- 版本锁定到一个确切的 1.x 版本（`langgraph` 及其依赖的 `langgraph-checkpoint`、`langchain-core`），升级单独评估。

### 7.6 工具登记（T14）

| 字段 | 说明 |
|---|---|
| 名称 | 例如 `query_progress`、`query_paper`、`create_batch`、`start_scoring` |
| 说明 | 一句中文，给日志、文档与将来的模型工具描述共用 |
| 参数 | JSON Schema；节点调用前按它校验 |
| 是否只读 | 只读工具（查询类）与写工具（建任务、开评、重试、移除）分开标注 |
| 实现 | 指向服务层函数，经共享守卫执行（T4） |

约束：

- 一期模型不调用任何工具，只输出意图；图按意图选择工具。
- **写工具只能由图里的确定性节点在中断点之后调用**，永远不开放给模型直接调用。
- 二期如果需要模型多步取数（例如解释诊断时补查数据），只开放只读工具，并先在三个协议适配器上补齐工具调用及兼容性测试。

## 8. 关键技术决定

| # | 决定 |
|---|---|
| T1 | 编排框架用 LangGraph（与其它框架的比较见第 13 节） |
| T2 | 节点里调模型用现有适配器，不用 LangChain 的模型封装与预制智能体 |
| T3 | 自写状态存储：实现 LangGraph 状态存储的同步接口（取最新、列出、写入、写入中间结果、按线程删除；以锁定版本的接口为准），数据放在 Alembic 管理的表里，给 `pgs_app` 授权并建 RLS；测试（SQLite）与生产（Postgres）走同一份代码。不用官方 Postgres 存储：它在运行时自己建表，生产运行角色没有这个权限 |
| T4 | 节点里的写操作调用后端服务层；把散落在路由里的权限检查（`_visible_batch`、`_visible_rubric`、`_batch_or_404`、`_job_or_404`、角色校验等）抽到共享模块，页面接口与图共用，并补“同一请求两条路径结果一致”的测试。建批次、开评与重试的派发、移除论文等路由里的业务逻辑同步抽成服务函数，行为不变，由现有测试兜底 |
| T5 | 文件仍由浏览器直传；图在“等上传”中断，浏览器传完后带论文编号恢复 |
| T6 | 一期由对话页的进度卡片轮询现有任务接口，发现结束后通知图继续；评分 worker 主动唤醒放到二期，与 PR #17 一起做。代价：关掉对话页后，汇报与自动重试要等下次打开才发生 |
| T7 | LangGraph 只作为库嵌入现有 FastAPI；不用 LangGraph 官方服务端，不依赖 LangSmith；调用链追踪可接已有的 Langfuse |
| T8 | 对话历史存自己的消息表；状态存储只存流程状态 |
| T9 | 意图识别规则优先、模型兜底（第 7.2 节） |
| T10 | 工作区是现有页面的同源 iframe；页面在框架内运行时隐藏外壳侧栏与模型引导弹窗；`vercel.json` 与 `deploy/Caddyfile` 的 `X-Frame-Options` 由 `DENY` 改为 `SAMEORIGIN`，并加 `Content-Security-Policy: frame-ancestors 'self'`，跨站嵌入仍被禁止 |
| T11 | `DELETE /papers/{id}` 允许删除“解析失败且从未评分”（无评分记录、无批任务条目、无分块）的材料，页面同样受益；能力表新增 `abilities.use_assistant`（开发模式、平台管理员、`org_admin`、`teacher`） |
| T12 | 迁移 `0035_assistant_conversations`（第 10 节）；PR #17 落地时编号顺延 |
| T13 | 原型代码按新方案改写（第 12 节） |
| T14 | **工具调用方式：结构化输出 + 代码分派**。模型只输出经 JSON Schema 校验的意图（第 7.2 节），调用哪个工具、怎么调用由图里的代码决定；一期**不用厂商原生工具调用（function calling），也不用 MCP**。图里的每个工具统一登记：名称、说明、参数的 JSON Schema、是否只读（第 7.6 节），格式与 function calling、MCP 的工具描述基本一致，将来升级任一种都不用重写 |
| T15 | **对外开放 MCP 服务**（让外部 AI 工具查询本系统的分数与扣分点）不进一期、二期，记为以后的规划项；届时包装同一套服务层与共享守卫，用 OAuth 鉴权 |

## 9. 对话记忆（M1–M4）

### 9.1 原则

记忆里**只存“指向”（编号），不存分数、扣分点、证据的副本**。分数会被人工改、任务会被重试、批次会被归档，副本会让助手拿过期的数字回答；系统数据是唯一事实来源，每次现查。

### 9.2 四层

| 层 | 存什么 | 存在哪 | 保留多久 | 给模型看吗 |
|---|---|---|---|---|
| ① 流程状态 | 流程走到哪一步、在等什么、相关编号（任务、评分标准、导入草稿、作业）、是否已自动重试 | 状态存储表 | 流程结束后只保留最近 **10** 份快照（M2）；会话删除时一并删除 | 不给 |
| ② 当前焦点 | 当前任务、当前评分标准、最近谈到的论文（编号与名称） | 会话表 `focus` | 跟随会话 | 只给任务名、评分标准名 |
| ③ 对话记录 | 用户原话、助手回复、卡片（类型与编号） | 消息表 | 不自动过期，创建者删除（B7） | 只给用户最近 **3** 句原话（M1） |
| ④ 长期偏好 | 助手用哪个模型 | 偏好表（每人每组织一行） | 长期，用户可改 | 不给 |

### 9.3 规则

- **流程状态**：每个会话同一时间最多一个进行中的流程（条件更新加锁，第二个请求返回 409“上一步还在处理”）。“等用户确认 / 选文件 / 上传 / 是否移除”这类停顿 **7 天**无回应即作废（M3），卡片标为已过期，提示重新开始；“等评分结束”不设过期。
- **当前焦点**：建好任务、用户选了任务或论文、查询展示了某篇论文时更新；换任务时清空“当前论文”；用户说“换一个任务”时整个重置。“第 N 篇”按当前任务的上传顺序数。焦点里的任务每次使用前都经共享守卫现查：已归档、已删除或无权访问时提示换一个，**不沿用旧信息回答**。
- **新建会话不继承上一个会话的焦点**（M4），从空白开始。
- **对话记录**：模型看不到助手自己之前的回复，避免把上一轮可能说错的内容当事实引用、错误越滚越大；上下文长度固定，一期不做长对话摘要。
- **长期偏好**：只记用户明确设置的东西，不让模型自动从对话里提取“用户习惯”。

### 9.4 隔离与隐私

- 全部记忆按“用户 + 组织”隔离；切换组织看到的是另一组会话，其它组织的编号永不被引用。
- 会话只对创建者可见，他人访问一律 404；响应 `Cache-Control: private, no-store`。
- 日志只记编号，不记学生原文。
- 二期加学生角色时，学生会话与老师会话完全分开，学生只能查到自己论文的编号范围。

## 11. 接口（前缀 `/api/assistant`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET / PUT | `/settings` | 助手模型设置；GET 返回是否已配置、实际生效的来源与“平台模型较慢”提示 |
| GET / POST | `/conversations` | 列出（按最近更新）/ 新建 |
| GET / PATCH / DELETE | `/conversations/{id}` | 含消息与当前等待的中断 / 改标题 / 删除（连同流程状态） |
| POST | `/conversations/{id}/runs` | 体为三种之一：`{type: "message", text}`、`{type: "resume", card_id, value}`、`{type: "select", card_id, value}`（选择卡片触发的查询）。返回本次新增的消息与当前等待的中断（类型、卡片、需要浏览器做的事） |

- 权限：全部要求 `org_admin` / `teacher`（U1）。
- 恢复值按中断类型逐一校验（第 7.3 节）；卡片编号与当前中断不一致返回 409，防止旧卡片、双击与多标签页。

## 13. 放弃了什么（实施时写进 DECISIONS）

**框架（第 1 次比较，2026-10-11）**

| 方案 | 不选的原因 |
|---|---|
| pydantic-graph | 依赖最轻、类型严格，但人工确认要自己拼“走一步、保存、下次读回”，资料与社区少得多；作为次选保留 |
| 不用框架（自写状态机） | 零依赖、最可控，但中断、恢复、状态保存都要自己实现；维护者指定 LangGraph |
| LlamaIndex Workflows | 跨请求恢复要自己序列化上下文；异步优先，与同步后端不合；生态重心在检索问答 |
| Microsoft Agent Framework | 很新、接口变化快，生态偏 Azure |
| Google ADK | 生态偏 Gemini / Vertex；2.0 改了会话表结构，表结构由框架决定 |
| OpenAI Agents SDK、CrewAI | 核心是“模型决定下一步”或多角色协作，与固定流程相反 |
| DBOS | 与 PR #17 的“数据库即队列”重复建设；默认需要常驻进程负责恢复，不适合 Vercel；自带建表 |
| Temporal | 需要单独部署服务集群，内网与 Vercel 都不现实 |

**其它**

- **模型自主规划流程（Agent 循环）**：步骤已知、成败可由代码判定（与规则解析模块“放弃自主 Agent”同理）；让模型决定下一步，成本、耗时与结果都不可控。
- **每一步都调用模型生成提问**：一次评分十几步，每步一次调用既慢又贵，还可能把分数说错；改为代码模板。
- **LangChain 模型封装、`create_react_agent`**：会绕过现有适配器的连接、限流、熔断与计量。
- **厂商原生工具调用（function calling）**：流程固定，下一步由代码决定，一次结构化输出就够；三种协议的工具调用格式各不相同，要分别实现与测试，自带的兼容接口与免费模型常不可靠；模型可以点名调用工具，就多了一条被论文里夹带的指令利用的途径。代价：将来若要模型多步取数，需要补适配器的工具调用（第 7.6 节已留扩展口）。
- **应用内用 MCP 接工具**：工具都是同一进程里的服务函数，改走 MCP 只多一层进程或网络调用；用户身份要传给 MCP 服务并在那里再做一遍权限检查，多一处与页面接口不一致的风险；三种部署都要多管一个服务。MCP 适合“把系统能力开放给外部 AI 工具”，记为以后的规划项（T15）。
- **官方 Postgres 状态存储**：运行时建表，生产运行角色没有权限；测试与生产走两套实现。
- **LangGraph 官方服务端、LangSmith**：多一个部署平台和外部服务，内网用不了。
- **前端编排流程（原型做法）**：编排在浏览器里，状态易丢，写动作的一致性靠前端约定；改为后端图。
- **图节点在进程内调用自己的 HTTP 接口**：一致性最好，但写法别扭、多一层序列化；改为共享守卫加服务层，并用一致性测试兜底。
- **模拟点击页面按钮**、**把页面组件直接嵌进助手**：前者一改版就失效；后者页面内链接会带走整个助手页；改为 iframe，代价是每切一次工作区重新加载、两边各自轮询、安全头放宽到同源。
- **让模型猜附件用途**：猜错一次就把论文当评分标准导入。
- **在对话里完成规则校对与发布**、**AI 处理人工复核项或给建议分数**：前者留在页面由用户完成；后者等于用一个模型为另一个模型的不确定判断兜底。
- **在助手里实现 U5 两项**：只在对话页开着时生效；改连接配置会让批次重试失败。二期在执行层实现。
- **助手调用进入批量评分的名额队列**：用户在等回复，排在正在评分的论文后面可能等几分钟；代价是同一连接上可能多出一个并发请求（维护者确认暂时忽略）。
- **卡片存分数副本**、**框架状态当对话历史**、**向量检索型记忆**、**自动提取长期记忆**、**跨会话继承焦点**、**组织内共享会话**：见第 9 节。
