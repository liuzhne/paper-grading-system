# 评分请求 token 压缩方案

- 状态：**阶段 0–5 已实施（2026-10-05）**；真实模型验证与 QWK 重新锚定待授权（见第 12 节）
- 日期：2026-10-04；修订：2026-10-05（加入阶段 0、阶段 3–5）
- 范围：Core 语义规则的模型调用（`rule_executor` → `ThesisLLMRuntime` → `score_core_envelope`），以及围绕它的用量计量、预估和结果复用。确定性检查器、legacy v1 路径和 AI 起草不在本方案范围内。
- 关联：DECISIONS「2026-10-04 评分 token 压缩方案（Proposed）」、「2026-10-04 评分请求采样参数与熔断状态修复」

## 1. 背景

2026-10-03 至 10-04，本地批次「评分测试 01」先后两次重跑，耗尽了百炼 kimi-k3 和其它模型的免费额度，并产生了扣费。下面的数字来自本地拆解（只读数据库，不调用模型），样本是《高校反霸凌互助系统的设计与实现》。

### 1.1 用量

- 每篇 135 次模型调用（每条规则一次），每次约 1.85 万字符。
- 实测一条规则的 `usage.prompt_tokens` 为 11233，约 2.23 字符/token。
- 一篇约 **112 万输入 token**，3 篇约 400 万。百炼单个模型常见的免费额度约 100 万 token，一篇都跑不完。

### 1.2 单次请求的构成

| 内容 | 占比 | 模型是否需要 |
|---|---|---|
| 证据单元的 64 位哈希 ID、定位等元数据 | 32.3% | 基本不需要 |
| `profile_prompt_extensions`：参考文献列表 10.9%、篇章一致性发现 10.8%、结构检查 4.6%、学生信息等 | 28.3% | 大多数规则不需要 |
| 审计与缓存元数据：`evidence_selection_identity` 13.2%、`runtime_identity`、`token_budget_identity`、各类哈希 | 22.8% | 不需要 |
| **证据原文** | **9.8%** | 需要 |
| 系统指令 | 3.6% | 需要 |
| 规则与评分项快照 | 3.3% | 需要（但目前缺少规则原文，见 1.4） |

真正有助于判断的内容只占约 15%。

### 1.3 结构性浪费

- **证据重复**：整篇被选为证据的片段只有 99 个、约 7300 字，却随 135 次调用重复发送。
- **同一缺陷问三次**：135 条规则中有 129 条属于 43 个互斥组，每组是“轻 / 中 / 重”三档，分值递增，例如 T01-B01-G01 为 2 / 6 / 14 分。同一个缺陷要分三次单独问模型。
- **三档可能冲突**：同组如有一档以上被判为触发，`_criterion_results` 会记录 `MUTEX_CONFLICT`，整个评分项判为 `invalid`。分开询问会主动制造这种冲突。
- **重试重复计费**：kimi-k3 那次重跑中，两篇分别已有 68 条和 59 条规则判定成功，其余规则失败后，重试又从第 1 条开始、重新付费。原因是 Core 路径没有使用 L0 缓存（L0 缓存是存在本地 SQLite 文件里的旧机制，Vercel 上不可持久），规则任务也只在整篇算完后才批量落库，无法从单条规则续跑。
- **用量不可见**：Core 评分运行的 `scoring_runs.prompt_tokens / completion_tokens / total_tokens` 恒为 0，`ai_usage_ledger` 也是 0，事前无法预估、事后无法对账。

### 1.4 同时发现：规则原文没有进入模型请求

`AtomicRuleSnapshot`（`contracts._normalize_atomic_rule_snapshot`）是封闭字段集，不含 `name`、`rule_text` 和示例。扣分规则又没有档位描述，所以模型只看得到规则编号，无从判断。证据检索的查询词（`selection._query_text`）同样没有用到规则原文。

结果是两个模型都给出 0 条触发，论文拿到满分。补上规则原文是阶段 1 的一部分。

## 2. 目标与不变量

**目标**：

1. 每一次模型调用都可计量；评分开始前能看到预估用量，并可以设置上限。
2. 已经成功、并且仍然有效的规则判定不再重复付费。
3. 一篇论文首跑的输入 token 降到约 10 万以内，同时不减少判断所需的信息。

**不变量**（实施时不得破坏）：

1. 扣哪条规则、扣多少分，仍然只由已发布规则授权；模型不输出分值，分值由系统按规则计算。
2. 证据逐字校验不变：`quote` 必须出现在对应证据单元的**原始** `normalized_text` 中，否则视为无效。
3. 结果仍按每条规则落库（`RuleScoringTask.result_snapshot`），报告、复核、导出、人工复核队列都不变。
4. 已发布 `RubricVersion` 的身份（`rubric_version_hash`，`rubric-content-v2`）不变。该哈希本来就覆盖了规则的 `name`、`rule_text` 和示例列。
5. 审计和身份字段仍在本地计算并保留在信封对象中；发给模型的内容是从信封派生出的投影，派生规则带版本号，可以复现。
6. 不改变 `SCORING_ENGINE_MODE` 默认值，也不授予 GATE-03 发布权限。
7. **阶段 0 不改变任何判定结果**：只做计量、预估和对“身份完全相同的判定”的复用。

## 3. 阶段总览

| 阶段 | 内容 | 借鉴 | 预计效果 | 改变判定吗 |
|---|---|---|---|---|
| **0（最先做）** | token 计量；评分前预估与上限；规则级决策账本（缓存与断点续跑） | 持久记忆；精确计数并可审计 | 首跑用量不变；失败重试只为失败的规则付费；用量可见、可设上限 | 否 |
| 1 | 方案 A：判断用视图 + 补规则原文 | 清理工具结果、只保留调用记录 | 一篇约 21 万 token（−81%） | 是（补规则原文后判定才有意义） |
| 2 | 方案 B：互斥组合并 | — | 每篇 49 次调用，约 8 万 token（−92%） | 是（三档一次判断） |
| 3 | 证据按类型压缩并设预算 | DeepSeek Harness Fresh / Aggregate、头 / 中 / 尾裁剪 | 证据部分再减，证据质量提升 | 可能（证据变化） |
| 4 | 稳定前缀排序，复用厂商前缀缓存 | 提示缓存 | 降低单价，用量不变 | 可能（证据集合按评分项共享时） |
| 5 | 确定性论文概况卡 | Agent Compact（跳过 LLM 摘要调用） | 帮助定位，几乎不增加成本；可替代部分整段上下文 | 可能 |

## 4. 阶段 0：计量、预估与规则级决策账本（已实施，2026-10-05）

> 实现与本节计划的差异：
> - 账本没有实现 `CacheLedger`，而是新增一个窄接口 `DecisionLedger`，作用域由适配器绑定。原因是 `CacheLedger` 要求 Core 传入请求方作用域，而 Core 不知道租户和连接。
> - “重新评分时绕过”用上下文变量实现，因为 `score_paper` 的签名受兼容合同约束，不能加参数。
> - 两个上限默认是 0（不限），需要显式配置。
> - 规则任务新增 `decision_reused` 列，用于审计复用；批次遥测新增 `decision_ledger_reused/judged` 和 token 字段，不计入原有的 `cache_hits`。
>
> 详见 DECISIONS「2026-10-05 评分用量计量、预估上限与规则级决策账本」。


### 4.1 token 计量

- 适配器从厂商响应中读取 `usage`。Chat 用 `prompt_tokens / completion_tokens`，Responses 用 `input_tokens / output_tokens`；能拿到的话，同时记录缓存命中的输入 token 和推理 token。用量随规则结果一起返回，不进入 `SemanticRuleResponseV2`，因为判定合同保持不变。
- 每条规则的用量记入该规则任务的执行记录。按整篇汇总后写入 `scoring_runs.prompt_tokens / completion_tokens / total_tokens`，BYOK 连接同时写入 `ai_usage_ledger`。现在 Core 路径这几个值恒为 0。
- 失败的调用（4xx、超时、截断）也要计入：截断和超时同样会计费，`ai_usage_ledger.failure_count` 要反映这一点。
- 批次页和运行详情显示每篇的实际用量。

### 4.2 评分前预估与上限

- 每条规则的请求在发出前都会计算 `token_budget_identity.estimated_input_tokens`，所以预估只需要在本地组装请求并累加，**不调用模型**。估算偏保守（utf8 / 3）。
- 点击“开始评分”或“重试”前，显示本次预计的调用次数和输入 token；会命中决策账本（4.3）的规则不计入。
- 设两级上限，**超过任一级时拒绝启动**，界面说明原因：
  - 单篇上限：可以设在连接或部署配置上；
  - 单批次上限。
- 运行中的硬上限：一篇的实际用量超过上限时，停止发出新请求，剩余规则记为失败（错误码 `TOKEN_BUDGET_EXCEEDED`）。已经成功的判定照常写入账本，提高上限后重试可以续跑。

### 4.3 规则级决策账本（缓存与断点续跑）

**决策身份**：对下列内容做规范化序列化，再取 SHA-256，得到 `decision_identity_hash`：

- 文档快照哈希（`document_snapshot_hash`）
- 规则快照，包括它所属的 `rubric_version_hash`
- 评分项快照
- 证据选择哈希（`evidence_selection_identity.selection_hash`）
- provider 身份：模型、`model_version`、采样参数、`thinking`、`response_format`
- `prompt_version`、provider 视图版本（阶段 1 引入）
- `profile_key / profile_version`
- AI 连接 ID

只要其中任何一项变化，例如换模型、改规则、改提示词、改证据选择或者论文重新解析，就不会命中旧结果。

**存储**：

- 新表 `rule_decision_ledger`：`organization_id`、`decision_identity_hash`（在组织内唯一）、`rule_code`、通过校验的规范化判定、用量、`created_at`、`expires_at`。
- 配一个 Alembic 迁移，**在迁移中给 `pgs_app` 授权并建 RLS**（照 0023 的做法；漏掉的话，迁移会成功，但生产会报 permission denied）。
- 这张表就是 Core 已定义却还没有实现的 `CacheLedger` 接口的数据库实现。不用 L0 的 SQLite 缓存，因为 Vercel 函数没有持久磁盘，多实例之间也无法共享。

**读写规则**：

- 执行语义规则前，先按身份查账本；命中且未过期时直接使用，不调用模型。规则任务记为“复用”，并记下来源，该规则的用量计 0。
- 每条语义规则**判定成功并通过校验后立即写入账本**，不等整篇结束。这样无论是厂商报错、进程中断还是 Vercel 300 秒超时，重试时都能跳过已经判过的规则。
- 只写入成功的判定。失败、`invalid`、越权证据都不写入。
- 显式的“重新评分”（`BatchScoringJob.rescore=true`）不读账本，强制重新判断，但会写入新结果。
- 作用域：同一组织，并且身份中包含 AI 连接 ID。不同连接之间不复用，避免用 A 的密钥算出的结果被 B 当作自己的结果。
- 过期时间默认 30 天，可配置；过期记录由定期清理任务删除。

**与后续阶段的关系**：阶段 1 的视图版本、阶段 2 的组合同都会进入决策身份，所以上线后旧账本自然不再命中，不会把旧语义的判定混进新版本。阶段 2 之后，账本按“组调用”记录，一条记录覆盖组内三档。

**效果**：首跑用量不变；失败重试只为失败的规则付费。以这次为例，kimi-k3 已经成功判完的 127 条不会再付一次钱。

### 4.4 为什么不改变判定

账本只复用身份完全相同的判定，身份涵盖了影响判定的全部输入；没有命中时，执行路径和现在完全一致。计量和预估都是只读的附加信息。

## 5. 阶段 1（方案 A）：只给模型发“判断用视图”（已实施，2026-10-05）

> 实现与计划的差异：
> - 规则原文只用于证据**排序**，覆盖模式仍按结构化查询判断，否则“缺少 / 缺失”类原文会让多数规则切到全量证据。
> - 视图版本没有作为运行身份的新字段，而是编码进 `core-semantic-provider@3`（进入 provider artifact 哈希）。
> - 参考文献上下文中的每条文献截断到 90 字、最多 30 条。
> - 实现在 `llm/core_view.py`。


### 5.1 视图字段

在 `core_adapter` 中新增 `provider_view(envelope)`，Responses 和 Chat 两种适配器共用，取代当前直接 `json.dumps(envelope)` 的做法。

| 类别 | 处理 |
|---|---|
| 评分项 | 保留 `criterion_code`、`name`、`assessment_mode`；不发 `max_score` |
| 规则 | 保留 `rule_code`、`direction`、`effect_type`、**`name`、`rule_text`、正例 / 反例 / 边界示例**（新增），band 规则的 `levels`，以及允许的 `finding_code`；不发 `max_points`、`cap_points`、`repeat_policy`（不让模型看到分值） |
| 证据 | 每个单元只发 `{ref: "E1", section: "<章节名>", text: "<normalized_text>"}` |
| 条件上下文 | 参考文献、篇章一致性发现、结构检查只在规则需要时附带（见 5.4） |
| 不再发送 | `runtime_identity`、`rubric_identity`、`rubric_snapshot_hash`、`plan_hash`、`policy_hash`、`submission`、`evidence_selection_identity`、`token_budget_identity`、`coverage_mode`、64 位 `evidence_unit_id`、完整 locator，以及学生姓名、学号、院系、专业、指导教师 |

不再发送的字段仍留在本地信封中，用于身份校验、观测和决策身份（4.3）。

### 5.2 补上规则原文

- 新增 `atomic-rule-snapshot@3`，在 @2 的基础上加入 `name`、`rule_text`、`positive_example`、`negative_example`、`boundary_example`。`rubric_snapshot._atomic_rule_schema_version` 对 M4 编译器产出 @3；@1 / @2 继续可以解析，供历史运行回放。
- `selection._query_text` 加入规则名称和原文，让证据检索按规则本身的含义选片段。
- 系统指令补充三种判定的含义：对扣分规则，`triggered` 表示论文**存在**规则描述的缺陷；`not_triggered` 表示证据显示不存在该缺陷；`not_applicable` 只用于规则的适用前提在本论文中不成立的情况。

### 5.3 证据短别名

- 按信封中证据的顺序编号为 `E1…En`；JSON Schema 的证据引用字段枚举这些别名。
- 适配器拿到回包后，先把别名映射回 `evidence_unit_id`，再交给现有的 `normalize_core_provider_response`。逐字校验和越权引用校验都不变；映射失败（未知别名）按越权证据处理。

### 5.4 条件上下文

- 编译规则快照时，根据规则原文的关键词，确定性地派生出 `context_needs`（取值范围 `references` / `coherence` / `structure`），冻结进快照并参与哈希。关键词示例：文献、参考、引用、检索、信息来源 → `references`；一致、对应、前后、印证 → `coherence`；章节、缺失、完整 → `structure`。
- `structure` 只附**未通过**的检查项。
- 后续在规则校对页允许人工修改 `context_needs`（不在本方案范围）。

### 5.5 预算与版本

- `preflight_v4_provider_payload` 改为对实际发送的视图做计数。证据选择阶段的预算计算保持不变，以免改变选证结果；它基于完整信封，偏保守。
- 升级 `CORE_PROVIDER_PROMPT_VERSION`（`core-semantic-provider@3`）和 `cache/llm_cache.PROMPT_VERSION`；在运行身份中记录视图派生版本 `provider-view@1`。

### 5.6 估算

单次约 3.5k 字符，约 1.6k token；一篇约 **21 万 token（−81%）**。64 位十六进制 ID 实际按更多 token 计，所以真实降幅可能更大；以阶段 0 的计量为准。

## 6. 阶段 2（方案 B）：同一互斥组合并为一次调用（已实施，2026-10-05）

> 实现与计划的差异：
> - 没有新建“组信封”合同：成员仍各自构建 V4 信封（共用一次选证），组请求只是由成员信封派生的视图。
> - `group_call_id` 是单独一列（并入迁移 0033），不写进 `result_snapshot`。
> - 新增可选端口 `ExecutionJournal` 记录复用和组调用，执行器签名扩展为 6 个参数。
> - 评分器不支持组调用（例如 Mock）或成员证据不一致时，回落为逐条判断。
> - 实测发现并修复了一个问题：共用选证的查询曾带入成员自己的规则编号，导致真实论文上各档选出的证据不同。


### 6.1 适用条件

同时满足以下条件时才合并：同一 `mutex_group`、同一评分项、全部为 `semantic`、`direction=deduct`、组内没有 `depends_on_rule_codes`。不满足时回落为逐条调用。当前版本 `17c1c659` 的 43 组都满足条件，另有 6 条无组规则逐条调用，**合计每篇 49 次**。

### 6.2 一次调用的判定

模型在一次调用中给出组级结论，三选一：

- `not_triggered`：各档都不成立；
- `not_applicable`：规则前提不适用；
- `triggered`：并给出 `selected_rule_code`（必须是组内某一档）和逐字证据。

组内各档的原文按分值从低到高一起提供，让模型比较档位之间的边界。

### 6.3 投影回每条规则

- 选中档 → 该规则 `triggered`（带 occurrences），组内其余规则 → `not_triggered`；
- 组级 `not_triggered` / `not_applicable` → 组内全部规则取同一状态。
- 这样结构上不会再出现 `MUTEX_CONFLICT`。原有的冲突检查保留，作为防御。

### 6.4 证据

把组内各档的规则原文合并为检索查询，只选一次 top-k（沿用 `SCORING_EVIDENCE_TOP_K`）。

### 6.5 合同与执行

- 新增 `semantic-group-request@1`（视图）和 `semantic-group-response@1`（回包）合同。
- `rule_executor.execute_rule_plan` 在遇到组内第一条规则时执行组调用，并缓存组内其它规则的结果；组调用失败时，组内全部规则记为 `invalid`，使用同一个错误码。
- 落库仍是每条规则一条 `RuleScoringTask`；`result_snapshot` 增加 `group_call_id`（同组共享），便于审计“这三档来自同一次判断”。决策账本按组调用记录。

### 6.6 估算与代价

- 49 次 × 约 1.7k token ≈ 一篇 **8 万 token（−92%）**。
- 代价：
  - 判断单元从“一次一条规则”扩展为“一次一个互斥组”，要改规则执行合同和执行器；
  - 组调用失败时三档一起失败，重试粒度变粗；
  - 失去“各档独立判断”的形式独立性。不过三档本来就是互斥的，独立判断并没有实际价值，反而会制造冲突。

## 7. 阶段 3：证据按类型压缩并设预算（已实施，2026-10-05）

> 实现与计划的差异：额外识别封面个人信息片段（姓名、学号、导师等），一律不发送。代码参考文献条目原样保留（通常很短），只在条件上下文的参考文献列表里截断。实现在 `retrieval/compression.py`。


借鉴 DeepSeek Harness 社区插件：按内容类型选择压缩器，并按预算分级压缩；Harness 本身对过长的工具输出做头 / 中 / 尾裁剪。

- **按证据单元类型选择压缩器**：

  | 类型 | 处理 |
  |---|---|
  | 段落 | 超过单元上限时，保留命中检索词的句子窗口，再加上首句和末句 |
  | 表格 | 保留表头和命中检索词的行，并注明省略了多少行 |
  | 代码清单 | 保留首尾几行和总行数；只有代码类规则才保留更多 |
  | 参考文献条目 | 规范化为“作者. 题名. 年份” |
  | 图题、表题、目录 | 默认不选，除非规则涉及图表或结构 |

- **预算**：每个单元设字数上限（初值建议 400 字），每次请求的证据部分设总上限（初值建议 3000 字）。超出时先降低低分证据的配额，再截断。
- **逐字约束**：发给模型的文本必须由原文中**连续的片段**组成，片段之间用“…”标明省略；`quote` 不得跨越省略号。校验仍然针对**原始** `normalized_text`，所以压缩不会削弱防编造。
- **可审计**：本地记录每个单元的压缩决定（单元、压缩器、触发原因、压缩前后的字数），连同选择版本（`section-bm25-diverse@2`）一起进入决策身份。
- **效果**：证据原文目前只占约 10%，主要收益在阶段 1 之后（届时证据会成为请求的主体），同时也能剔除“title | varchar | 200”这类低价值片段，提升判断质量。

## 8. 阶段 4：稳定前缀排序，复用厂商前缀缓存（已实施，2026-10-05）

> 实现：
> - 视图顺序固定为 概况卡 → 评分项 → 上下文 → 证据 → 规则；系统指令对同类请求完全一致。
> - 评分项级共用选证由 `SCORING_EVIDENCE_SCOPE=criterion` 开启，默认 `rule`，按本节的取舍等计量数据再决定。


借鉴提示缓存：系统提示词和工具定义保持稳定，作为前缀反复命中缓存。

- 请求按以下顺序组织：固定指令 → 论文级上下文（概况卡，见阶段 5） → 本评分项共享的证据 → 本次规则或规则组。同一评分项的调用按顺序连续发出（单篇本来就是串行执行）。
- 百炼部分模型的隐式缓存、DeepSeek 的磁盘前缀缓存，都会对命中的输入按折扣计费；具体折扣和最短前缀以厂商说明为准。
- **前提和取舍**：只有证据集合在评分项级别共享，才会有足够长的共同前缀。这和阶段 1 / 3“按规则精准选证”存在张力：评分项级的证据更多，但可以缓存；按规则选的证据更少，但无法共享。需要用阶段 0 的计量数据评估“折扣 × 共享长度”是否大于多发的 token，再决定是否启用。
- 用量不变，只降低单价；**不改变判定**的前提是证据集合不变。如果为了共享前缀而改成按评分项选证，就属于改变判定，需要按第 12 节验证。

## 9. 阶段 5：确定性论文概况卡（已实施，2026-10-05）

> 实现与计划的差异：
> - 大纲只保留章级标题，再按文档顺序补二级标题，直到 360 字为止；剔除“未命名开头”、表格行和三级标题。
> - 概况卡含 JSON 键名约 650 字符，比计划的 500 字略多。
> - 实现在 `retrieval/digest.py`，写入 `profile_prompt_extensions.paper_digest`。


借鉴 DeepSeek Harness 的 Agent Compact 插件：让 agent 自己写检查点，省掉一次 LLM 摘要调用。这里的对应做法是：不用 LLM 生成摘要，而是直接从解析结果中确定性地提取。

- **内容**（不超过 500 字）：
  - 标题；
  - 一级 / 二级章节大纲；
  - 正文字数、图表数量；
  - 参考文献的数量、类型分布和年份分布；
  - 是否有需求分析、设计、测试、总结等关键章节；
  - 未通过的结构检查项。
- **用途**：放在请求前缀中，帮助模型了解全文、判断规则前提是否成立；可以用统计信息代替部分整段上下文，例如用文献数量和年份分布代替完整的参考文献列表。
- **约束**：概况卡**不能作为证据**。扣分仍然必须引用证据单元的原文，系统指令中要明确这一点。这是与 Claude Code 压缩历史最大的不同：那里丢掉细节可以接受，评分不行。
- 概况卡由解析器生成，有版本号，并进入决策身份。

## 10. 不在本方案内、另行评估

- **适用性预筛**（借鉴按需加载工具和技能）：先给规则标题和论文大纲，标出明显不适用的规则并跳过。预筛误判会直接漏掉扣分，所以优先用规则里的确定性适用条件（`applies_to`）；LLM 预筛另行评估。
- **按章节先分析**（借鉴子代理）：每篇按章节各分析一次，产出带原文引用的结构化发现，规则判断只读这些发现。降幅大，但属于架构级改动，判断质量取决于第一阶段有没有漏掉问题。
- **按评分项批量判断**（每篇 6 次）：一篇可降到约 3–4 万 token，但一次要输出几十条判断，单条出错会影响整批，规则之间会相互干扰，重试粒度很粗。等阶段 1、2 做完并评估质量后再决定。
- **规则分流**：可由代码判定的规则交给确定性检查器；论文本身核验不了的过程性要求（如“按期完成”“工作努力程度”）交给指导教师人工打分；与论文类型无关的模板规则按适用条件跳过。需要逐条确认归属，另行方案。

## 11. 放弃的方案

- **只降低证据 top-k 或删减证据**：证据原文只占约 10%，省得很少，还会伤害判断质量。证据质量改进放在阶段 3。
- **用 LLM 压缩或摘要评分上下文**（Claude Code 的 compaction）：评分是 135 次彼此独立的单次调用，没有不断增长的历史可以压缩；LLM 摘要既有损又要额外付费，而评分要求证据逐字可查。
- **改由模型通过工具按需获取上下文**（如参考文献）：每多一轮工具调用，就要把整个上下文再发一遍，对单次判断反而更贵。改用确定性的条件附带（5.4）。
- **规则级复用沿用现有 L0 缓存**：L0 缓存存在本地 SQLite 文件里，Vercel 函数没有持久磁盘，多实例之间也无法共享。改用数据库中的决策账本（4.3）。
- **把哈希和身份字段继续发给模型**：模型不使用这些字段；身份由系统在发送前后校验，不靠模型回传。
- **继续向模型发送学生个人信息**：判断用不上，还有隐私风险。

## 13. 风险

- **账本复用错误判定**：身份漏掉某个会影响判定的输入时，可能复用不该复用的结果。缓解：身份宁宽勿窄；`rescore` 可以强制重判；账本记录来源，便于追查。
- **规则原文质量**：有些规则写的是“p[136]要求…”这类评分标准原文的段落编号，补上原文后模型仍然难以理解，需要在规则校对时改写。
- **`context_needs` 关键词派生**：可能漏附或多附上下文。漏附会影响文献类、一致性类规则的判断，需要人工校对兜底。
- **组调用失败的影响面**：三档一起失败。缓解：决策账本按组记录，重试时只重跑失败的组。
- **证据压缩丢失关键信息**：缓解：预算可配置；记录压缩决定，便于对比。
- **估算偏差**：本文的 token 数按 2.23 字符/token 估算，只有一条规则做过实测；实施后以阶段 0 的计量为准。
