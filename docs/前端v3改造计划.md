## 0. 本轮决策

| # | 决策 | 影响 |
|---|---|---|
| **V3-a** | **不保留空白新建**，评分标准只能由导入产生 | `POST /rubrics` 退出界面（CLI/测试仍用）。副作用是好的：每份标准都带模板溯源，`publish` 那条「legacy draft 必须先显式升级溯源」的分支在新界面上不再可能触发 |

## 1. 结论：先解决一个比「缺按钮」严重得多的问题

### 1.1 生产当前评出来的是 Mock 假分

`/api/system/integrations` 在生产返回：

```json
{"provider": "mock", "model": "mock", "adapter": "MockLLMScorer",
 "api_key_configured": false, "fallback_to_mock": true}
```

评分取模型的逻辑是（`backend/app/services/scoring/engine.py:147`）：

```python
if batch.ai_connection_id is None:
    return get_llm_scorer()          # → provider="mock" → MockLLMScorer()
```

而**新建任务页从头到尾没有让用户选择 AI 连接**——`NewTaskView.vue` 里没有任何
`ai_connection` 字段。于是通过当前界面建的每一个任务都 `ai_connection_id = null`，
**评出来的分数来自 Mock**，界面上没有任何地方提示这一点。

同一条路径也影响 AI 起草扣分细则：不带 `ai_connection_id` 调用
`draft-deduction-rules`，得到的是 Mock 编出来的扣分规则，却以「AI 起草 · 待确认」
的形态呈现给用户确认——**确认之后它们会进入正式发布的评分标准**。

决策 V3-b 正好堵住这条路，但覆盖面要扩大到**评分本身**，不止起草。

> 注：`get_llm_scorer()` 里那道「认证部署禁止平台模型」的保护
> （`factory.py:57`）排在 `provider == "mock"` 分支**之后**，所以 provider 为 mock 时
> 它不生效。这不是配置写错，是保护顺序的问题。

### 1.2 四条链路断在半途

| # | 断点 | 现状 |
|---|---|---|
| **A** | **评分标准的全部创作能力随旧 SPA 一起消失** | 生产上无法新建、导入、审核或发布任何评分标准。后端 20 个端点齐全，新工作台只调用了 2 个只读端点 |
| **B** | 新建评分任务页无入口 | `/workbench/tasks/new` 路由与页面都在，全站没有任何链接指向它 |
| **C** | 评分工作区只读 | 不能改分、不能加评语、不能「确认此份」。设计稿的三个核心动作全缺 |
| **D** | 阻塞任务无法解决 | 队列能看到阻塞项，没有 claim/resolve 入口；阻塞项不清零就点不动「完成复核」——**provider 一出错，这个批次永远走不完** |

A 意味着系统当前无法完成一次从零开始的评分：新建任务要选「已发布的评分标准」，
而现在没有任何途径产生一个。

## 3. 目标：两条必须走得通的完整流程

### 3.1 流程一 · 模板标准：从生成到可用于评分

```
导入规则 Excel（可带 Word 批注模板）
  → 解析与编译 → 补全扣分细则（用自己的连接）→ 逐条确认
  → 提交审核 → 校验 → 选择编译产物发布 → 可被任务选用
```

每一步的**退出条件**（不满足不能进下一步，UI 必须说清为什么）：

1. **导入**：必须上传规则 Excel。返回的 `warnings` 与 `template_summary` **原样展示**，
   不吞掉。可见范围默认「仅自己可见」（V3-c）。
2. **解析与编译**：产生 `RubricCompilation`。有歧义（`ambiguity`）时明确标出，不替用户挑。
3. **补全扣分细则**：`rule-coverage` 给出每项的 `complete / pending_review / missing`。
   `missing` 是**阻断项**，UI 要说清后果：「评分到该项时没有判据可用」。
   起草**必须选一个自己的 AI 连接**；没有连接就挡住并链到账户与连接页。
   AI 只补缺失部分，**用户原文表述保留**。
4. **逐条确认**：AI 起草的规则默认 `待确认`，**未确认不进入可执行版本**。确认记录
   确认人、时间、模型与生成指纹（后端已有）。
5. **提交审核 → 校验**：有阻断项时拒绝提交，给出「去修改 T02 →」式定位跳转。
6. **发布**：要求显式 `compilation_id`——**UI 必须让用户看到自己发布的是哪一份编译
   产物**，不提供「用最新的」快捷方式。发布后版本冻结。
7. **可用于评分**：新建任务页的标准下拉只列已发布版本。

### 3.2 流程二 · 评分任务：从使用到查看结果

```
新建任务 → 选已发布标准 → 选自己的 AI 连接 → 上传材料 → 解析预检
  → 开始评分 → 监控与异常处置 → 逐份复核（改分/评语/确认）
  → 解决阻塞项 → 完成复核 → 导出
```

关键退出条件：

1. **新建任务**：工作台与评分任务页都要有入口（现在两处都没有）。
2. **选 AI 连接**：**必选**。不选就不能开始评分——否则评的是 Mock（§1.1）。
3. **上传与预检**：已实现。预检问题如实展示。
4. **开始评分**：批次进入 `scoring`，逐份检查点，中断可续跑。
5. **异常处置**：失败材料可单独重试，整批可取消。**目前完全缺失**。
6. **逐份复核**：能改分、写理由、加评语、「确认并进入下一份」。改分 bump
   `review_revision`，并发冲突原子拒绝。
7. **解决阻塞项**：能 claim → 处理 → resolve。**不解决就完不成批次，必须有。**
8. **完成复核 → 导出**：已实现。

## 4. 后端改动清单（少，但都不能省）

### 4.1 最高优先：让「没有可用模型」变成明确失败，而不是假结果

三处一起改，缺一处就还能绕过去：

1. **`get_llm_scorer()` 的保护顺序**：把「认证部署禁止平台模型」的判断提到
   `provider == "mock"` 分支**之前**。认证部署下没有绑定连接就调用，应当抛错，
   而不是安静地返回 `MockLLMScorer`。
2. **`POST /batches` 要求 `ai_connection_id`**：认证部署下缺失即 422，错误文案指向
   账户与连接页。（开发模式 `AUTH_ENABLED=false` 保持可空，否则本地与验收全断。）
3. **`draft-deduction-rules` 同样要求连接**：现在 `ai_connection_id` 可空且回落到
   `get_llm_scorer()`。

> 这三条是 V3-b 的实际落地。**不做这一步，后面所有界面工作都建立在假分数上。**

### 4.2 13 个评分标准写端点没有角色门控

`rubrics.py` 里只有 `create_rubric` 与 `import_rubric_from_files` 调了
`require_organization_role`，其余 **13 个写端点只做组织可见性检查**：

```
clone_rubric              draft_rubric_deduction_rules   submit_rubric_review
return_rubric_to_draft    recompile_rubric_draft         submit_atomic_rule_review
patch_atomic_rule         approve_atomic_rule_review     reject_atomic_rule_review
reopen_atomic_rule_review review_atomic_rule_template_link
update_rubric             publish_rubric
```

**发布一个评分标准决定了全组织的论文怎么被打分。** 它们现在难以触及只是因为 UI 没
了；v3 恰恰要把它们放到界面上，**必须先补门控再暴露**。做法与导出出口那次一致，
并补一条覆盖全文件写方法的测试。

### 4.3 编辑并发

`PATCH /rubrics/{id}` 与逐条规则编辑没有乐观并发标识，两人同编同一草稿会后写覆盖
先写。复用批次那套：给 `Rubric` 加 `state_version`，写入校验，冲突 409。
**这是 v3 唯一需要的新迁移。**

### 4.4 可能需要的聚合读端点

详情页三步要同时用 `rubric` + `execution-draft` + `rule-coverage` + 规则明细。先用现
有端点并行取；**只有实测出 N+1 或首屏明显变慢才加聚合端点**，不提前造。

### 4.5 不需要改的

评分任务侧的写能力（改分、单份复核、重试、取消、阻塞任务处置）后端全部就绪，且已
有并发与幂等约束。这一侧是纯前端接入。

## 5. 页面与交互（对齐设计稿）

### 5.1 评分标准：列表 + 三步详情

| 步骤 | 内容 | 主要动作 |
|---|---|---|
| **1 · 基本信息与评分项** | 名称、版本、总分、可见范围、评分项表 | 编辑保存 |
| **2 · 评分规则** | 完整度总览；按评分项展开规则组（问题类型/严重程度/扣分/触发条件/**来源**） | `生成全部缺失细则`（需选连接）、逐条 `确认`/`排除`、`确认并应用全部` |
| **3 · 校验与发布** | 阻断项清单 + 定位跳转；**编译产物选择**；可见范围 | `保存并重新校验`、`提交模板审核`、`发布` |

头部常驻状态条：`v3.2 草稿 / 有未保存的修改 · 当前校验结果来自上一个执行草稿`。
**这句话不是装饰**——它区分「你改了但还没重新编译」和「校验结果是新的」，缺了它
用户会把过期的校验结果当成当前状态。

列表页补 `导入评分模板` 与每行 `克隆`（**不做空白新建**，V3-a）。

### 5.2 AI 连接的配置与选择（V3-b）

配置页**已存在**且功能完整（账户与连接：新建、保存前试连、轮换密钥、停用）。
v3 只需补「选择」与「挡住」：

- 新建任务页加**必选**的连接下拉，显示 `名称 · provider · 模型`；
- 评分标准页的 `生成全部缺失细则` 同样要选；
- **没有任何可用连接时**：两处都禁用主按钮，给一句话说明 + 链到账户与连接页，
  不允许「先跑起来再说」；
- 连接的密钥轮换或配置变更后，已建批次会因快照不一致而拒绝继续
  （`engine.py:158`），UI 要把这条错误翻译成「该任务绑定的连接已变更，请重新建任务」。

### 5.3 评分任务：补入口与工作区写能力

- **工作台**与**评分任务页**都加 `新建评分任务` 主按钮（设计稿里出现 6 次，全站最高频）。
- **评分工作区**从只读改为可写：每项可改分（带理由）、`添加评语`、
  `确认此份评分` / `确认并进入下一份`；显示 `review_revision`，冲突提示刷新而非静默覆盖。
- **任务行**补 `重新解析`（单份）、`重试失败项`、`取消`（整批）。
- **复核队列**的阻塞项补 `领取 → 处理 → 解决`，解决后触发重算。

## 6. 阶段划分与退出条件

每阶段**先写测试再写实现**，组件/状态测试与浏览器验收同步补。

| 阶段 | 内容 | 退出条件 |
|---|---|---|
| **V3-0** | §4.1 模型绑定三处 + §4.2 十三个写端点门控 + §4.3 `state_version` 迁移 | 认证部署下不绑连接调用 LLM 直接失败；非授权角色被拒；并发编辑返回 409 |
| **V3-1** | 评分标准列表补 `导入` / `克隆`；导入结果如实展示 warnings 与 template_summary | 能从零导入一份标准并看到解析结果 |
| **V3-2** | 三步详情步骤 1、2（含 AI 起草与逐条确认，强制选连接） | 未确认规则不进入可执行版本；无连接时起草被挡住 |
| **V3-3** | 三步详情步骤 3：校验、阻断定位、显式 `compilation_id` 发布 | **一份新标准可走完「导入→确认→发布」并出现在新建任务下拉里** |
| **V3-4** | 新建任务入口 + **必选 AI 连接**；批任务取消/重试/重新解析 | 从工作台点进去能建任务并跑完；不选连接不能开始 |
| **V3-5** | 工作区写能力：改分、评语、确认此份/下一份；`review_revision` 冲突处理 | 改分写入复核记录；并发冲突被拒而非覆盖 |
| **V3-6** | 阻塞任务 claim/release/resolve | **provider 失败的批次能被人工解决并完成复核** |

**V3 的完成定义**：在干净环境里用一个账号完成
「配置连接 → 导入标准 → 确认规则 → 发布 → 新建任务 → 上传 → 评分 → 改一份分 →
解决一个阻塞项 → 完成复核 → 导出」，全程不碰 CLI、不碰数据库，**且评分用的是真实
模型而非 Mock**。这条端到端路径进浏览器验收矩阵。

## 7. 风险与控制

| 风险 | 控制 |
|---|---|
| **界面工作建立在 Mock 假分之上** | V3-0 的 §4.1 必须最先做完，不与任何界面阶段并行 |
| **写端点搬上界面而门控没跟上** | §4.2 与 §4.1 同属 V3-0，一起做完再开 V3-1 |
| **仅自己可见的标准同事用不了**（V3-c 的连带后果） | 见 §8 第 1 条，需先定改可见范围的路径 |
| AI 起草覆盖用户原文表述 | 后端已保证只补缺失；前端标出每条规则的 `来源`（原文/AI），保留「排除」 |
| 发布了错误的编译产物 | 发布必须显式选择 `compilation_id` 并展示其摘要，不提供「用最新的」 |
| 改分与批量采纳互相覆盖 | 共用 `review_revision`；批量采纳已拒绝改过分的项，单份改分同样校验 |
| 阻塞任务被两人同时处理 | 用后端已有的 claim/release 租约，UI 显示当前领取人 |
| 连接密钥轮换后旧任务不可续 | 后端已 fail-closed；UI 要把错误翻译成可操作的说明（§5.2） |

## 8. 未决事项（动工前需确认）

1. **「仅自己可见」之后怎么共享**（V3-c 的连带后果）：`private` 标准只有创建者能看到，
   同组织的其他教师**无法选它建任务**。改成 `organization` 目前要求 `org_admin`
   （`rubrics.py:236`）。是放开为「创建者本人可改为组织可见」，还是保留 org_admin 审批？
   **不定这条，导入出来的标准就只有自己能用。**
2. **平台是否配置一个真实模型**：生产现在 `LLM_PROVIDER=mock`。V3-0 之后，不绑 BYOK
   连接就无法评分。这是期望行为，还是应当同时配置一个平台默认模型？
3. **设计稿与已定决策冲突的三处文案**，实现时按后者改：
