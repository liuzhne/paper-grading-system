# 前端 v3 改造计划（模板生成→使用、任务使用→查看结果）

> 本文只给方案，不含实现代码。当前 Alembic head `0029_runtime_access_for_v2_tables`，
> 生产已切到 v2 工作台、旧 SPA 已下线（见 [前端v2改造计划.md](前端v2改造计划.md) §0 决策 15）。

---

## 0. 结论：这不是「缺几个按钮」

盘完设计稿、旧 SPA、新工作台和后端路由，实际情况是**四条链路各自断在半途**，其中
一条是我们上一轮下线旧页时**带走的**：

| # | 断点 | 严重程度 | 现状 |
|---|---|---|---|
| **A** | **评分标准的全部创作能力随旧 SPA 一起消失** | **阻断** | 生产上**无法新建、导入、审核或发布任何评分标准**。后端 20 个端点齐全，新工作台只调用了 2 个只读端点 |
| **B** | 新建评分任务页无入口 | 阻断 | `/workbench/tasks/new` 路由与页面都在，全站没有任何链接指向它 |
| **C** | 评分工作区只读 | 阻断 | 不能改分、不能加评语、不能「确认此份」。设计稿的三个核心动作全缺 |
| **D** | 阻塞任务无法解决 | 阻断 | 队列能看到阻塞项，没有 claim/resolve 入口；而阻塞项不清零就点不动「完成复核」——**provider 一出错，这个批次永远走不完** |

A 是最高优先级：**它意味着系统当前无法完成一次从零开始的评分**。新建任务页要选
「已发布的评分标准」，而现在没有任何途径产生一个已发布的标准。

另有两处非阻断但影响可用性：批任务不能取消/重试失败项（后端有
`/batch-scoring-jobs/{id}/cancel|retry`）、材料不能单独重新解析（后端有
`/papers/{id}/parse`）。

## 2. 目标：两条必须走得通的完整流程

### 2.1 流程一 · 模板标准：从生成到可用于评分

```
新建/导入 → 解析与编译 → 补全扣分细则 → 逐条确认 → 提交审核 → 校验 → 发布 → 可被任务选用
```

每一步的**退出条件**（不满足就不能进下一步，UI 必须说清为什么）：

1. **新建/导入**：可选两条路——空白新建（手填评分项），或上传规则 Excel（可带 Word 批注模板）。导入返回 `warnings` 与 `template_summary`，**必须原样展示**，不能吞掉。
2. **解析与编译**：产生 `RubricCompilation`。存在歧义（`ambiguity`）时明确标出，不自动挑一个。
3. **补全扣分细则**：`rule-coverage` 给出每个评分项的 `complete / pending_review / missing`。`missing` 是**阻断项**——UI 必须说清后果：「评分到该项时没有判据可用」。AI 起草只补缺失部分，**用户原文表述保留**。
4. **逐条确认**：AI 起草的规则默认 `待确认`，**未确认不进入可执行版本**。确认要记录确认人、时间、模型与生成指纹（后端已有）。
5. **提交审核 → 校验**：存在阻断项时拒绝提交，并给出「去修改 T02 →」式的定位跳转。
6. **发布**：`POST publish` 要求显式 `compilation_id`——**UI 必须让用户看到自己发布的是哪一份编译产物**，不能后台随便挑一个。发布后版本冻结。
7. **可用于评分**：新建任务页的标准下拉只列已发布版本。

### 2.2 流程二 · 评分任务：从使用到查看结果

```
新建任务 → 选已发布标准 → 上传材料 → 解析预检 → 开始评分 → 监控/异常处置
  → 逐份复核（改分/评语/确认） → 阻塞项解决 → 完成复核 → 导出
```

关键退出条件：

1. **新建任务**：必须能从工作台与评分任务页进入（现在两处都没有入口）。
2. **上传与预检**：已实现。预检发现的问题（缺章节、解析质量低）如实展示。
3. **开始评分**：批次进入 `scoring`，逐份检查点，中断可续跑。
4. **异常处置**：失败材料可单独重试；整批可取消。**这是目前完全缺失的一段**。
5. **逐份复核**：工作区里能改分、写理由、加评语、「确认并进入下一份」。改分要 bump `review_revision`，并发冲突原子拒绝。
6. **阻塞项解决**：能 claim → 处理 → resolve。**不解决就完不成批次，这条必须有。**
7. **完成复核 → 导出**：已实现。

## 3. 页面与交互（对齐设计稿）

### 3.1 评分标准：列表 + 三步详情

设计稿的详情页是三步式，与后端生命周期一一对应：

| 步骤 | 内容 | 主要动作 |
|---|---|---|
| **1 · 基本信息与评分项** | 名称、版本、总分、可见范围、评分项表（code/name/满分/说明） | 编辑保存 |
| **2 · 评分规则** | 扣分细则完整度总览；按评分项展开规则组（问题类型/严重程度/扣分/触发条件/来源） | `生成全部缺失细则`、逐条 `确认`/`排除`、`确认并应用全部` |
| **3 · 校验与发布** | 阻断项清单 + 定位跳转；编译产物选择；可见范围 | `保存并重新校验`、`提交模板审核`、`发布` |

头部常驻状态条：`v3.2 草稿 / 有未保存的修改 · 当前校验结果来自上一个执行草稿`。
**这句话不是装饰**——它区分「你改了但还没重新编译」和「校验结果是新的」，缺了它
用户会把过期的校验结果当成当前状态。

列表页补 `新建评分标准`、`导入评分模板` 两个入口，以及每行的 `克隆`。

### 3.2 评分任务：补入口与工作区写能力

- **工作台**与**评分任务页**都加 `新建评分任务` 主按钮（设计稿里它出现 6 次，是全站最高频动作）。
- **评分工作区**（`GradeView`）从只读改为可写：
  - 每个评分项可改分，带理由输入；
  - `添加评语`；
  - 底部 `确认此份评分` / `确认并进入下一份`；
  - 右上角显示 `review_revision`，冲突时提示刷新而不是静默覆盖。
- **任务行**补 `重新解析`（单份）、`重试失败项`、`取消`（整批）。
- **复核队列**的阻塞项补 `领取 → 处理 → 解决`，解决后触发重算。

## 4. 后端改动清单（少，但都不能省）

### 4.1 必须先做：13 个评分标准写端点没有角色门控

`rubrics.py` 里只有 `create_rubric` 与 `import_rubric_from_files` 调了
`require_organization_role`，其余 **13 个写端点只做组织可见性检查**：

```
clone_rubric              draft_rubric_deduction_rules   submit_rubric_review
return_rubric_to_draft    recompile_rubric_draft         submit_atomic_rule_review
patch_atomic_rule         approve_atomic_rule_review     reject_atomic_rule_review
reopen_atomic_rule_review review_atomic_rule_template_link
update_rubric             publish_rubric
```

**发布一个评分标准决定了全组织的论文怎么被打分。** 现在它们难以触及只是因为 UI 没
了；v3 恰恰要把它们放到界面上，**必须先补门控再暴露**，否则等于把这条路径开给任何
能看到该标准的成员。做法与导出出口那次一致，并补一条覆盖全文件写方法的测试。

### 4.2 编辑并发

`PATCH /rubrics/{id}` 与逐条规则编辑目前没有乐观并发标识。两个人同时编辑同一个草稿
会后写覆盖先写。建议复用批次那套：给 `Rubric` 加 `state_version`（新迁移），写入时校验，
冲突返回 409。**这是 v3 唯一需要的新迁移。**

### 4.3 可能需要的聚合读端点

详情页三步要同时用到 `rubric` + `execution-draft` + `rule-coverage` + 规则明细。先用
现有端点并行取；**只有实测出 N+1 或首屏明显变慢，才加聚合端点**，不提前造。

### 4.4 不需要改的

评分任务侧所有写能力（改分、单份复核、重试、取消、阻塞任务处置）后端全部就绪，
且已有并发与幂等约束。v3 在这一侧是纯前端接入。

## 5. 阶段划分与退出条件

每阶段**先写测试再写实现**，前端组件/状态测试 + 浏览器验收同步补。

| 阶段 | 内容 | 退出条件 |
|---|---|---|
| **V3-0** | 补齐 4.1 的 13 个写端点门控 + 4.2 的 `state_version` 迁移 | 非授权角色被拒的定向测试通过；并发编辑冲突返回 409 |
| **V3-1** | 评分标准列表页补 `新建` / `导入` / `克隆`；导入结果如实展示 warnings 与 template_summary | 能从零导入一份标准并看到解析结果 |
| **V3-2** | 三步详情页：步骤 1、2（含 AI 起草与逐条确认） | 未确认规则不进入可执行版本，有测试钉住 |
| **V3-3** | 三步详情页步骤 3：校验、阻断定位、显式 `compilation_id` 发布 | **一份新标准可走完「导入→确认→发布」并出现在新建任务的下拉里** |
| **V3-4** | 新建任务入口（工作台 + 任务页）；批任务取消/重试/重新解析 | 从工作台点进去能建任务并跑完；失败材料可单独重试 |
| **V3-5** | 工作区写能力：改分、评语、确认此份/下一份；`review_revision` 冲突处理 | 改分写入复核记录；并发冲突被拒而非覆盖 |
| **V3-6** | 阻塞任务 claim/release/resolve | **一个 provider 失败的批次能被人工解决并完成复核** |

**整体验收（V3 的完成定义）**：在一个干净环境里，用一个账号完成
「导入标准 → 确认规则 → 发布 → 新建任务 → 上传 → 评分 → 改一份分 → 解决一个阻塞项
→ 完成复核 → 导出」，全程不碰 CLI、不碰数据库。这条端到端路径要进浏览器验收矩阵。

## 6. 风险与控制

| 风险 | 控制 |
|---|---|
| **把写端点搬上界面而门控没跟上** | V3-0 必须先做完，不与 V3-1 并行 |
| AI 起草覆盖用户原文表述 | 后端已保证只补缺失；前端要标出每条规则的 `来源`（原文/AI），并保留「排除」 |
| 发布了错误的编译产物 | 发布必须显式选择 `compilation_id` 并展示其摘要，不提供「用最新的」快捷方式 |
| 改分与批量采纳互相覆盖 | 共用 `review_revision`；批量采纳已拒绝改过分的项，单份改分要同样校验 |
| 阻塞任务被两人同时处理 | 用后端已有的 claim/release 租约，UI 显示当前领取人 |
| 三步详情页状态复杂导致误操作 | 「有未保存的修改」状态条常驻；未重新校验时不允许提交审核 |

## 7. 未决事项（动工前需确认）

1. **空白新建 vs 仅导入**：是否保留「不上传 Excel，直接手填评分项」这条路？后端支持，
   但它绕过了模板溯源。建议保留但在发布前提示「本标准无原始输入」。
2. **AI 起草的连接选择**：`draft-deduction-rules` 接受 `ai_connection_id`。是让用户在
   页面上选私有 BYOK 连接，还是固定用组织默认？
3. **可见范围的默认值**：导入表单的 `visibility` 默认 `private`；组织内共用是否应默认
   `organization`（需 org_admin）？
4. **`扫描件/OCR`**：设计稿预检文案提到 OCR，但决策 1 明确不支持扫描件。文案要改，
   不能让用户以为支持。
5. **压缩包上传**：设计稿写「拖入 PDF、DOCX 或包含材料的压缩包」，决策 12 已降级为多选
   文件。同样需要改文案。
6. **单份上限**：设计稿写 60 MB，配置实为 50 MB。以配置为准，改设计稿文案。
