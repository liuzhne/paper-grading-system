# 第一部分：业务方案

## 1. 目标

| 位置 | 现在 | 本方案之后 |
|---|---|---|
| 评分标准页“核对”步（`RuleReviewPanel`） | “排除”只存在 `RubricsView.vue` 的内存集合 `excluded` 里：刷新、切换模板、保存重新校验都会丢；被排除的细则仍算“待确认”，挡住“下一步” | 排除立即保存；刷新后仍显示“已排除 · 恢复”；排除的细则不算待确认，不挡发布 |
| 评分助手工作区“核对评分规则”（`ReviewStep`） | 没有排除按钮 | 与评分标准页同一组接口、同一个 `RuleCard`，加回“排除 / 恢复” |
| 发布与评分 | 驳回（`rejected`）的细则挡住发布（`rule_not_approved`） | 驳回的细则不进入发布版本，评分时不参与 |

一句话原则：**排除和确认一样，是老师对“这条细则算不算分”的签字。** 所以它同样要即时落库、留不可改的审计、经过发布门禁核对，并且在评分时真正生效。

## 2. 老师看到什么

- 待确认的细则右侧两个按钮：“排除”“确认”。点“排除”后卡片变淡、标题划线，按钮位置显示“已排除 · 恢复”。不弹确认框（排除可以随时恢复，且不会自动发布）。
- 点“恢复”后细则回到“待确认”，需要重新确认（恢复不等于确认）。
- 一个评分项只剩最后 1 条未排除的细则时，“排除”按钮不可点，悬停提示“每个评分项至少保留 1 条细则”。后端同样拒绝（§4）。
- 计数：“5 条 · 已确认 3 · 待确认 1 · 已排除 1”。“统一确认最终规则”只确认待确认的，不碰已排除的。
- 已确认的细则本期不能直接排除（Q3）；已发布的版本不能排除或恢复（发布后版本不可改，和现在一致）。
- 排除的细则不进报告、不进评分明细——它们在评分快照里就不存在（§3.2）。

## 3. 驳回的细则在编译、发布、评分里怎么处理

### 3.1 发布门禁（`executable_validator.validate_publishable_rubric`）

门禁把细则分成两组：**参与评分的**（`status != "rejected"`）和**已排除的**（`status == "rejected"`）。

| 检查 | 现在 | 改后 |
|---|---|---|
| `rule_not_approved` | 每条非 `approved` 都报 | 只对参与评分的细则报；已排除的不报 |
| 完整性：`criterion_rules_missing` / `criterion_numeric_scoring_missing` | 按全部细则算 | 只按参与评分的细则算：全部排除等于“缺少评分细则” |
| 内容合法性（`deduct_rule_invalid`、`band_levels_invalid`、`rule_text_missing`、证据策略、checker 等） | 全部细则 | 只查参与评分的。排除一条写坏了的 AI 细则，本身就是一种合法的处理方式 |
| 分档评分项 `band_criterion_invalid`、`review_only_criterion_invalid` | 全部细则 | 只按参与评分的细则算 |
| 依赖 `depends_on_rule_codes` | 依赖不存在报 `dependency_unknown` | 新增 `dependency_rejected`：参与评分的细则依赖了已排除的细则（执行计划 `_dependency_order` 遇到不存在的依赖会直接失败，必须在发布前挡住）。提示“细则 X 依赖已排除的细则 Y：请恢复 Y，或一并排除 X” |
| 依赖环 `dependency_cycle` | 全部细则 | 只看参与评分的 |
| 互斥组 `mutex_definition_invalid` | 同组少于 2 条即报 | 按参与评分的成员判断；若同组原本 ≥2 条、只因排除剩下 1 条，不报（见 3.4） |
| 模板映射 `template_link_pending` | 所有映射 | 只看参与评分的细则的映射 |
| 驳回审计（新增） | — | 每条已排除的细则必须有与 `reviewed_by` / `reviewed_at` 一致的 `reject` 审计事件，否则报 `rule_rejection_audit_missing` / `rule_rejection_audit_mismatch`（与现有的批准审计检查对称，见 §6） |

`allow_pre_m4_provenance`（只有 `atomic-v1` 编译走这条，生产不产生这种编译，只在测试夹具里出现）提前返回的位置不变，但完整性检查同样只按参与评分的细则算。

### 3.2 版本哈希与评分快照

这是本方案唯一碰到“发布身份”的地方，单独说明。

- **现状**：`lifecycle._canonical_version_hash` 把版本下的**全部**细则写进内容哈希，但**不含** `status`。评分快照 `CompiledRubricSnapshotLoader.load_from_session` 同样取全部细则，并重算哈希核对。
- **改法**：两处都只取参与评分的细则（`status != "rejected"`）。即发布版本的内容 = 会被执行的细则；已排除的细则行和它的审计仍留在库里（`human_changes` 本来就不在哈希里）。
- **为什么必须改哈希、不能只在快照里过滤**：只过滤快照的话，“排除了 X”和“确认了 X”的两个版本哈希完全相同，但执行内容不同——哈希不再能代表“这一版怎么评分”；而 `load()`（按存储的版本图加载）的规则内容里没有 `status`，也无从过滤。改哈希之后，发布后若有人在库里把已排除改回已确认（或反过来），重算哈希不一致，评分直接失败（fail closed），比现在更严。
- **对已发布版本的影响**：门禁保证非 `atomic-v1` 的已发布版本里没有驳回细则，过滤前后集合相同，**哈希逐字节不变**。上线前在生产执行一次只读核对（§11），确认已发布版本里没有非 `approved` 的细则。
- 被排除的细则连同它的模板映射、来源映射一起不进入哈希；来源文件和来源规则（`artifacts`）不变。

### 3.3 评分执行

- 正式版本（批次锁定 `rubric_version_id`）一律走 Core：`score_paper` → `_score_paper_core` → 快照。快照里没有已排除的细则，执行计划、规则决策账本、互斥组合并判断、报告都看不到它们。不需要改执行器本身。
- `RubricCriterion.deduction_rules_structured`（评分项上的扣分规则投影）**不改**：它只给未版本化的兼容路径用，正式版本不读它；`rule_origin` 还按下标从它取显示信息（严重度、触发条件），删掉其中一条会让后面的细则错位。代价：评分项的这份投影里仍有已排除细则的条目，读它的人要知道它不是执行输入。ARCHITECTURE 写明。

### 3.4 互斥组

执行器对“同组只剩 1 条”本来就是空操作：`eligible_rule_groups` 跳过不足 2 条的组，互斥冲突要求同组 ≥2 条同时命中。所以门禁对“因排除而只剩 1 条”的组放行；整组都没被排除、本来就只有 1 条的组仍按现在的规则报错（那是定义写错了）。

## 4. 每个评分项至少保留 1 条非驳回细则

两道检查：

1. **排除时**（`lifecycle.reject_atomic_rule`，页面接口和 CLI 共用）：排除后该评分项参与评分的细则为 0 条，则拒绝，提示“每个评分项至少保留 1 条细则；要换掉这条，请先补充新细则再排除”。
2. **发布时**：门禁按参与评分的细则做完整性检查（3.1）。只剩复核类细则、没有可计分细则的，照现在的 `criterion_numeric_scoring_missing` 报。

只拦“0 条”、不拦“没有可计分细则”，原因：`review_only` 评分项本来就只有复核细则；拦“可计分”要在排除时重复一遍门禁的分档/复核规则判断，两处容易不一致。代价：老师可能排除掉最后一条扣分细则，到发布时才看到阻断——提示里会指到具体评分项（Q2）。

## 5. 草稿能不能直接排除

现在 `reject` 只收 `review` 状态，而页面上待确认的细则几乎都是 `draft`（“确认”接口在一次调用里做了 draft→review→approved）。

**推荐：新增与“确认”对称的组合接口，状态机不改。**

| 接口 | 做什么 | 幂等 |
|---|---|---|
| `POST /rubrics/{id}/rules/{code}/exclude` | `draft` 先提交审核再驳回（两条审计：`submit_review`、`reject`），`review` 直接驳回 | 已是 `rejected` 时直接返回，不重复写审计 |
| `POST /rubrics/{id}/rules/{code}/restore` | `rejected` → `draft`（调用现有 `reopen_atomic_rule`，写 `reopen` 审计） | 已是 `draft` 时直接返回 |

两个接口的请求体与 `/confirm` 相同（`compilation_id`、`rule_id`、`content_token`、`reason`），同样先锁评分标准、核对“老师看到的就是库里的这条”，内容变了返回 409 让页面刷新。权限同 `/confirm`（`org_admin`、`teacher`）。实现放在 `review_workspace.py`，与 `confirm_rule` 并排。

现有 `/reject`、`/reopen` 与 CLI 不变，仍只收 `review` / `rejected`。

放弃的做法：
- **放宽 `reject` 直接收 `draft`**：改了已冻结的状态机，CLI 与历史接口的语义随之变化；而且没有 `content_token` 核对，老师排除的可能是别人刚改过的那一版。
- **前端先调 `submit-review` 再调 `reject`**：两次请求不是一个事务，中间失败会留下一条“审核中”的细则；也没有内容核对。

## 6. 审计

- 排除记两条事件（与确认对称）：`submit_review`（draft→review）、`reject`（review→rejected），`actor_id` 为操作人，`reason` 为固定文案：评分标准页“用户核对条款后排除，不参与评分”，评分助手“在评分助手里核对后排除，不参与评分”。
- 恢复记 `reopen`，`before` 带原来的 `status` / `reviewed_by` / `reviewed_at`（现有实现）。
- 事件都追加进当前编译的 `human_changes`（只追加、不改写），与确认相同。`reviewed_by` / `reviewed_at` 写在细则上。
- 门禁核对已排除细则的 `reject` 事件与细则上的 `reviewed_by` / `reviewed_at` 一致（3.1）。原因：排除决定了“这条不算分”，权重和确认一样，不能允许绕过接口直接改库。

## 7. 排除结论的沿用

| 场景 | 现在 | 改后 |
|---|---|---|
| 保存修改、重新校验（重新编译，`review_carry`） | 只沿用内容与评分上下文都没变的**已确认**细则；其余回到草稿 | 已排除的同样沿用：签名相同的细则在新编译里重放 `submit_review` + `reject`，原因写“复用内容与评分上下文均未改变的既有排除；前序编译 …” |
| 重新上传前的差异预估（`calculate_carry_diff`） | 只数已确认 | 已确认与已排除合计为“保留的核对结论” |
| 克隆已发布版本（`clone_published_rubric`） | 全部细则回到草稿 | 原版本里已排除的细则在克隆里保持已排除（克隆人重放 `submit_review` + `reject`，原因写“克隆自已发布版本 {版本号}，沿用原版本的排除”）；其余仍回到草稿 |

克隆为什么不让排除的细则回到草稿：克隆后老师通常会点“统一确认最终规则”，回到草稿的已排除细则会被一并确认，悄悄重新参与评分——这正是本方案要防住的。代价：克隆不再是“签核字段全部清空”，克隆出来的草稿带着新写的驳回审计（Q4）。

## 10. QWK 基线与 `PROMPT_VERSION`

- **`PROMPT_VERSION` 不动。** 没改任何 prompt 模板或输入构造。互斥组合并判断的输入里成员少了一条，属于输入内容变化，已经被组身份哈希（`_group_identity` 含成员）和 L0 缓存键覆盖，不会命中旧缓存。
- **QWK 不需要重新锚定。** 评分逻辑没变：没有排除细则的评分标准，快照与哈希逐字节不变（有测试钉住）。有排除的评分标准是老师授权改了评分内容，和老师改一条细则的扣分值同类，不是评分算法变化。
- 回归测试钉住：同一个评分标准在“无排除”时的版本哈希与快照哈希与改动前一致。

## 11. 发布与回滚

- 上线前在生产只读核对（应为 0）：

  ```sql
  begin read only;
  select count(*)
    from atomic_rules r
    join rubric_versions v on v.id = r.rubric_version_id
    join rubric_compilations c on c.id = v.compilation_id
   where c.published_at is not null and r.status <> 'approved';
  rollback;
  ```

  不为 0 时不发布：这些版本的哈希重算会变化，评分会 fail closed。
- 无迁移，回滚即回到上一版镜像。回滚后，已排除细则的草稿重新被旧门禁挡住发布（`rule_not_approved`），已用新版发布的、含排除的版本在旧代码下重算哈希不一致，评分失败——回滚前要先确认这期间没有发布过含排除的版本，或接受这些版本需要克隆重发（RUNBOOK 写明）。

## 12. 测试与门禁

- 后端：门禁各条（排除后可发布、依赖已排除被挡、互斥组只剩 1 条放行、驳回审计缺失被挡、全部排除被挡）；排除/恢复接口（草稿与审核中、幂等、内容变化 409、最后 1 条被拒、权限）；快照不含已排除、评分不调用已排除细则（Mock LLM 计数）；无排除时哈希不变；重新编译与克隆沿用排除；覆盖率计数。
- 前端：`RuleCard`、`RuleReviewPanel`、`ReviewStep` 单测；`rubric-workflow` 单测；`rubric-review.spec.js` 增加“排除 → 刷新仍为已排除 → 恢复 → 确认 → 发布”。
- 门禁：`pytest`、`npm run test:unit`、`typecheck`、`api:dump && api:check`、`playwright test`。

## 14. 本期不做
