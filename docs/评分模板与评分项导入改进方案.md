# 评分模板与评分项导入改进方案及实施计划

日期：2026-09-17，2026-09-20 更新。状态：临时导入会话及数据合同已实施，见 §6 历史验证记录；本轮统一工作区、来源投影、分步交互、响应式复制和确认重试修复已完成，后端全量 2197、前端 238、受影响 E2E 96 通过（3 项不适用跳过），本地实际构建及桌面/窄屏截图已核对。范围见 [评分标准原型差异与改造执行计划](评分标准原型差异与改造执行计划.md)，不是全项目 E2E 全量，不含生产发布。

关联：后端解析内核（单元台账、覆盖率、LLM 兜底与规则审查）见 [评分规则解析模块重构方案](评分规则解析模块重构方案.md)。本方案负责页面与交互；两者重叠的 `pipeline.py`、`parser.py`、Word 抽取以该方案的内核结构为准，本方案阶段 2、3 与其阶段 4、7 合并执行。

## 1. 当前实现与目标

方案制定时，代码已支持仅 Word、仅 Excel 或双文件解析，但工作台仍走 `POST /rubrics/import-files`，解析后立即创建 Rubric。2026-09-20 的会话改造已将工作台首次解析切换为 `POST /rubrics/import-sessions`，确认前不创建 Rubric；兼容导入接口仍保留。同日的原型整改进一步将初始/会话/正式/只读状态统一为同一工作区，新增 `source-workspace` 读取正式来源，将规则归属放在第二步、完整校验放在第三步。最终视觉与完整流程验收记录见补充执行计划。

目标将三步统一为“导入评分模板与评分项 → 评分规则 → 校验与发布”，第一步按用户提供的参考图片重组。图片是布局参考，其中示例名称、示例类型、自动合并和取值文案不作为业务规则。上传和确定性解析只创建数据库中的临时导入会话，不创建 Rubric；只有用户确认评分项后才在事务中创建正式 Rubric、评分项、来源图与首个执行草稿。

## 2. 已确认的页面方案

前端固定提供上下两个上传框：上方“评分标准文档（Word，.docx）”，下方“评分表（Excel，.xlsx / .xlsm）”。不提供“仅 Word / 仅 Excel / Word＋Excel”模式选择，不展示文件组合处理逻辑。后端根据收到的文件决定处理路径；至少上传一份文件。Word 单文件入口需等后端能力实现后开放，不能只取消前端必填校验。

采用双栏布局：左侧依次为 Word 上传卡片、Excel 上传卡片、解析出的评分项表格；右侧为基本信息、待确认问题、主操作。窄屏按顺序堆叠。文件卡片展示上传框或文件名、解析状态、重新上传操作；Word 提供受权限控制的原文预览。

基本信息包含标准名称、版本、满分和标准说明。评分标准不区分适用类型，不新增 Profile 选择器；图片中的“课程报告”仅是用户给评分标准填写的示例名称，“学位论文”“编程作业”等按钮不进入实现。

评分项表格包含编号、名称、满分、文档出处、解析状态、操作，并展示项数和分值合计。支持编辑名称、整数分值、说明、查看出处以及在临时导入草稿内新增或删除评分项；继续遵守 D-026，不提供空白新建评分标准入口。评分项与满分均以正整数进入正式数据：导入源出现小数时采用十进制 `ROUND_HALF_UP` 四舍五入到最近整数（例如 10.4→10、10.5→11），保留原始值与换算结果，并在待确认问题和对应表格行明确告知用户。编号必须唯一，评分项合计必须等于满分，否则阻断确认。

待确认问题面板汇总名称、分值、匹配等冲突，点击定位评分项。系统只能提出合并和取值建议，用户确认前不得静默合并或覆盖。主操作为“确认评分项，下一步”：保存评分项、处理阻断问题后进入第二步，失败时保留编辑内容并说明原因。

第一步默认不调用 LLM。Word/Excel 的结构读取、评分项抽取、高确定性编号/名称匹配、小数换算、冲突和总分检查均由确定性代码完成。LLM 集中用于第二步的模板内容归属、评分规则和扣分细则建议；第一步未来如增加不规则 Word 的 AI 辅助识别，也必须由用户主动触发、只形成带原文证据的候选，不能直接持久化或覆盖用户选择，本期不作为第一步完成条件。

### 2.1 临时导入会话合同

- 新增数据库持久化的 `RubricImportSession`（最终表名以迁移为准），记录组织、创建人、状态、`state_version`、文件元数据/安全存储引用、解析草稿、来源定位、冲突、人工编辑、换算提示和重新上传差异。临时会话不是 Rubric，不得被评分、审核或发布流程读取。
- 会话状态至少区分 `draft`、`confirmed`、`expired`、`cancelled`；过期策略通过服务配置统一管理，确认、替换和编辑均使用 `state_version` 做乐观并发控制。
- 上传接口只返回 `import_session_id`、当前版本和待确认草稿，不返回新建的 `rubric.id`。重复确认使用幂等键；成功后返回同一个 Rubric，失败回滚整个确认事务并保留会话与用户编辑。
- 原文预览沿用既有评分标准的组织可见性和编辑权限，不另建一套角色规则；服务端仍必须校验会话所属组织和创建/编辑权限，前端不得凭按钮可见性代替授权。

## 3. 后端处理与后续联动

- Word：提取正文和表格中的评分项、分值及说明，保留原文出处，形成待确认草稿；复用现有批注能力但区分来源。
- Excel：兼容当前导入；同时上传时，结构化评分项与分值以 Excel 为候选，Word 提供原文依据，差异必须交由用户确认。
- 匹配：优先使用明确编号，名称匹配不能自动消除歧义；保留双方来源及确认记录。无法可靠提取时提示核对，不编造评分项。
- 重新上传：先生成差异预览，经确认后替换；保存失败不覆盖原草稿。编号相同且名称/分值未变时保留人工修改和已确认规则；名称或分值变化时保留内容但标记失效并要求重新确认；删除项软删除并保留历史；新增项标记规则不完整。已持久化 Rubric 的重新上传生成新 compilation，不覆盖已发布版本。
- 解析成功留在第一步且只更新临时导入会话。用户解决阻断并点击“确认评分项，下一步”后才创建 Rubric 并进入第二步。第二步保留逐项规则导航、原文规则、AI 补缺与人工确认，并提供返回第一步入口。
- 评分项或分值变化后重新编译和校验受影响规则，标记需要再次确认的内容；第三步检查未解决冲突、分值/权重策略、规则完整度及校验是否对应最新草稿。
- 复用既有权限、组织隔离、草稿生命周期及发布审核，不新增绕过审核的发布路径。
