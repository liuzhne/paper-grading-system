# 评分证据与理由改造方案

> 状态：已实现（2026-11-04，维护者确认后编码）；G1–G4 部署即生效，G5 开关默认关闭，等统一评测。
> 起因：维护者在评分页看到 Core 评分的评分表：每项置信度都是“未提供”，未扣分项没有理由，扣分理由是英文 “Authorized Core rule deduction”，所有证据都是“无锚点”。
> 范围：只改 Core 评分的**结果怎么保存、怎么展示**，以及一个默认关闭的提示词开关。不改扣分规则、不改分数计算。

## 1. 结论

| 现象 | 原因 | 分期 |
|---|---|---|
| 证据全是“无锚点” | 论文走 Core 评分时运行没有 `submission_id`，证据视图被分到旧路径的分支，找不到 `chunk_id`。冻结正文一直存在 `document_snapshot_ref`，没被读出来 | G1，修好后旧评分也生效 |
| 扣分理由是英文固定句 | 落库时写死 `"Authorized Core rule deduction"` | G2 |
| 未扣分项没有理由 | 落库只写分数和扣分，没写逐条规则的判定 | G2 |
| 扣分没有原文引文 | 模型逐字引用了原文、代码也核对过，但只存了哈希，引文丢了 | G3 |
| 置信度“未提供” | Core 从来不产置信度 | G4：改为代码算的“证据充分度” |
| 未扣分项没有原文出处 | 提示词要求“未触发”时不引原文、不写解释 | G5：新开关，默认关，进统一评测 |

G1–G4 不调模型、不改分、部署即生效。G5 改提示词，开关默认关闭，和第二阶段的 B、C 一起做真实模型评测后再决定是否打开。

## 2. 决定（维护者 2026-11-04 选定）

- **置信度改为“证据充分度”**：由代码按证据情况给出 高 / 中 / 低，不编造百分比，也不让模型自报。旧评分路径的数值置信度照常显示。
- **未扣分项也要原文出处**：改提示词，让模型在每条规则的判定里都给出依据引文和一句理由。因为会改判定身份、可能改分，放在开关后面，评测通过后再打开。

## 3. 现状（核对过代码）

- `evidence_view.build_evidence_view` 用 `run.submission_id` 区分 Core 与旧路径；论文的 Core 运行 `paper_id` 有值、`submission_id` 为空，所以走 `_legacy_view`，Core 证据没有 `chunk_id`，全部 `no_anchor`。`document_view.build_document_view` 同样按 `submission_id` 分支，论文 Core 运行显示的是当前解析的 `PaperChunk`，不是判分时的冻结正文。
- 论文 Core 运行的冻结正文：`ScoringRun.document_snapshot_ref`（`document-snapshot:sha256:…`），由 `LocalDocumentSnapshotStore` 存取，内容含 `sections` 与 `evidence_units`（单元文本、章节路径），没有页码。
- `rule_executor._evidence_ref` 把模型的 `{type, evidence_unit_id, quote}` 核对为原文子串后只留 `payload_hash`；`results._normalize_evidence_ref` 是封闭字段，存不下 `quote`。
- `persistence._score_items`：`reason=f"Core criterion outcome: {status}"`，`deduction_items[].reason` 固定英文，`confidence=None`。逐条规则的判定在 `ScoreItem.rule_results` 里有（状态、出现、扣分），只是没展示。
- 决策账本 `rule_decision_ledger.response` 存的是归一化后的模型回复，含引文；复用判定时引文一并复用。
- 提示词 `core_view._COMMON_INSTRUCTIONS`：“not_triggered 表示……；不得输出分值、扣分、解释文字”。未触发时 `occurrences` 必须为空数组，所以没有任何证据。
- 结果版本号（`rule-results@*`、`scoring-outcome@*`）在数据库里没有 CHECK 约束，存在 JSON 列里，**本方案不需要迁移**。

## 4. G1：证据回到冻结正文

- 证据视图与正文视图的分支条件从“有没有 `submission_id`”改为“这次运行有没有冻结正文”：v2 提交读 `run.document_snapshot`，论文 Core 运行按 `document_snapshot_ref` 从快照存储读取。两者都没有（旧评分路径）才走 `PaperChunk`。
- 论文 Core 运行的正文栏改为显示冻结正文（D-019：正式 Core 查看运行绑定的冻结正文），证据可以点击定位到对应段落。快照里没有页码，页码留空、显示章节路径，不编造。
- 快照读不到（文件丢失）时证据显示“冻结正文不可用”并说明原因，不退回最新解析文本。
- 只读改动，**已有评分立即生效**。

## 5. G2：逐条规则的判定说明

评分接口在返回证据视图的同时，为每个 Core 评分项返回**判定视图**（读取时从 `rule_results` 与执行计划里的规则快照算出，新旧评分都适用）：

| 规则状态 | 显示 |
|---|---|
| 扣分 | 规则「名称」：扣 X 分 + 引文（G3 之后）或证据所在段落 |
| 选档（band） | 规则「名称」：选「档位」 |
| 未触发 | 规则「名称」：未发现问题（G5 打开后附依据与理由） |
| 不适用 | 规则「名称」：不适用于本文 |
| 证据不足 / 无效 | 规则「名称」：+ 已有的复核原因 |

- 评分页每个评分项都有这张清单，未扣分项不再是空白。
- 落库时 `deduction_items[].reason` 改为中文“规则「名称」扣 X 分”，给评分助手用；旧行读取时换算，不改库里已有数据。

## 6. G3：保留模型的原文引文

- 结果合同**只加可选字段、不升版本号**：证据引用多一个 `quote`，只有通过“原文子串”核对的引文才会写入；规则判定可带 `evidence_selection` 与 `basis`。旧结果没有这些字段，照常读取。（原方案写的是升到 `scoring-outcome@3`，实现时改为可选字段：新字段只用于展示，升版本要改六处版本判断和金样，见 DECISIONS 2026-11-04。）
- 判定身份、出现编号（occurrence）与分数都不变：引文本来就参与了 `payload_hash`，现在只是不再丢掉原文。
- 评分页的扣分项显示引文（论文原文，语言与论文一致），点击定位并高亮；已有评分没有引文，显示所在段落并标“上下文”，不冒充引文。

## 7. G4：证据充分度（取代 Core 的“置信度”）

每个评分项一档，由代码按以下顺序判定，取最差的一条，并列出原因：

| 档位 | 条件 |
|---|---|
| 低 | 有规则判定无效或被阻断；有规则判“证据不足”；有扣分没有核对通过的引文；有规则一条证据都没看到 |
| 中 | 有规则的证据因预算被裁掉（实际放下的段数小于排序后要取的段数）；G5 打开时有未触发 / 不适用判定没给出任何引文 |
| 高 | 以上都没有 |

- 选证据的结果现在只进了观测日志，改为写进每条规则的结果（`evidence_selection`：`candidate_count` 候选段数、`requested_count` 排序后要取的段数、`selected_count` 实际放下的段数），不进判定身份。已有评分没有这项记录，只按其余条件判定，并注明“旧评分未记录选证情况”。
- 页面上 Core 评分项的“置信度”一行改为“证据充分度：高 / 中 / 低”，悬停看原因；旧评分路径仍显示数值置信度。
- 证据充分度只用于展示和排查，**不改分、不决定是否复核**；复核仍由现有规则决定。

## 8. G5：每条判定都给依据（开关 `SCORING_DECISION_BASIS_MODE`）

- 取值 `off`（默认）| `cite`。`off` 时提示词、输出结构与现在逐字相同。
- `cite` 时每条规则的回复多一个 `basis`：
  - `evidence`：0–2 条依据引文（`evidence_ref` + 逐字 `quote`），与扣分引文同样核对；
  - `rationale`：一句话理由，不超过 80 字，**用论文的语言**写，纯文本。
  - 扣分时 `basis.evidence` 可以复用出现里的引文；未触发时引用能说明“没有该缺陷”的段落；问“有没有”的规则若找不到可引的段落，允许不给引文，但必须写理由，证据充分度记为“中”。
- 依据引文核对失败时只丢掉这条引文、证据充分度记为“低”，**不把判定判为无效**：依据只用来解释，扣分仍只看 `occurrences`。理由由模型写，只展示、不参与算分。
- `cite` 是要求不是保证：模型漏写依据不判失败，确定性规则没有依据；互斥组一次调用只有一个依据，页面只在被选中的那一档显示，其余档注明“依据见同组”。
- 提示词版本加后缀 `+basis@1`，进入判定身份：打开后已有判定不复用，分数可能变化。
- 输出长度：每条规则约多 60–150 个 token。当前输出上限 2048，评测时同时记录截断次数（`truncated_count`）。
- 与第二阶段的开关一起接进生产部署（`scripts/production_env.py` 与 `ci.yml` 仓库变量）。

## 9. 评测（需要授权预算，本轮不做）

与第二阶段 B、C 的统一评测合并：同一批论文分别在 G5 关闭和打开时评分，比较 QWK、复核比例、输出 token、截断次数，并抽样人工核对理由是否与引文相符。G1–G4 不改分，不需要评测。

## 10. 不做的事

- 不让模型自报置信度：校准差，还会拉长输出。
- 不从决策账本反查已有评分的引文：账本是缓存、可能已被删除，按哈希匹配成本高；已有评分显示所在段落。
- 不给 Core 评分项回填数值 `confidence`：这一列保留给旧路径的模型置信度。
- 不改分数计算、复核规则和扣分规则。
- 复核队列（`ReviewView`）的置信度列本轮不改：队列接口逐行解析冻结正文开销大，只改评分页。

## 11. 兼容与回滚

- G1、G4 与 G2 的判定视图都是读取时的展示，回滚代码即恢复。G2 落库写的中文扣分理由与评分项说明（`deduction_items[].reason`、`reason`）已经存进评分项，回滚代码不会把它们改回英文；旧代码照常显示这些文字。
- G3 只增加可选字段；回滚后旧代码读 `rule_results` 不经结果合同校验，分数照常显示，只是不显示引文。
- G5 关掉开关即回到原提示词；开过期间的判定留在账本里，不影响关闭后的复用。
- 无迁移，head 仍为 `0041_assistant_agent_state`。

## 12. 验收

- 论文 Core 评分的证据显示章节与段落，可以点击定位；冻结正文读不到时如实提示。
- 每个 Core 评分项都有逐条规则清单；扣分理由是中文且带规则名。
- 新评分的扣分项显示核对过的原文引文。
- 置信度一行换成证据充分度，原因可见。
- `SCORING_DECISION_BASIS_MODE=off` 时提示词与输出结构逐字不变（测试守住）；`cite` 时未触发判定带理由与依据引文，核对失败不改判定。
- 后端、前端测试与 OpenAPI 合同检查通过；三份文档同步。
