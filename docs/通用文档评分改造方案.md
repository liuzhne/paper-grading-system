# 通用文档评分改造方案

状态：**已实施**（2026-10-11，分支 `claude/general-document`）。方案与页面原型经维护者确认，决定记录见第 6 节；实施中的补充与出入见第 9 节。

---

## 1. 目标与原则

让工作台和评分助手除了毕业论文，也能评任意类型的文档（方案、报告、作业等）。

- **改动最小**：不迁移数据库，不把工作台换到 v2 接口，不改表名和列名。
- **操作习惯不变**：用户的流程仍是 导入评分标准 → 新建任务 → 上传 → 评分 → 复核 → 导出。**唯一新增的操作是导入评分标准时选择“文档类型”**，之后每一步都由系统按评分标准推出类型，不再询问。
- **论文的评分结果不变**：论文的代码路径一行不改，现有评分一致性基线继续有效。

## 2. 现状

评分内核已经通用（v2 Submission、AtomicRule Core、Profile 隔离，Core 的提示词写的是“通用材料评分内核”），但用户能接触到的部分仍按论文设计：

| 位置 | 现状 |
|---|---|
| 导入评分标准 | 文档类型写死为 `"thesis"`（`api/routes/rubrics.py` `_file_import_command`），界面无处选择 |
| 工作台走 Core 时 | `scoring/engine.py` `_core_request_context` 写死 `ThesisProfile()`；技术方案版本在这里会因类型不符被拒 |
| 旧评分路径 | 提示词“你是毕业论文评阅助手”；确定性检查按名称调度，字数下限 3000 |
| 语义一致性 | Core 路径每次评分都调用一次“论文篇章一致性核验助手” |
| 身份字段 | Paper 只有学号、姓名、导师、学院、专业；导出列与 HTML 报告照此写 |
| 用词 | 工作台已有 66 处称“材料”，剩 5 个文件写“论文”；评分助手后端有若干“论文”文案 |

可以直接复用的基础：

- `rubric_versions.business_profile_key` 已存在，且数据库不限制取值——类型沿“评分标准版本 → 批次 → 评分”传下去**不需要迁移**；
- 评分标准导入流水线已经按 `business_profile_key` 取领域词汇与表头别名，本身是通用的；
- 论文类型注册的检查器（必备章节、字数范围、图表引用、引用与参考文献、格式约束）读的都是正文、章节和格式事实，对任何文档都适用；
- `papers.file_name` 已存原始文件名。

# 第一部分：业务方案

## 3. 页面变化

原型已在对话中确认。下表“毕业论文”一列即现状，保持不变。

| 页面 | 毕业论文 | 通用文档 |
|---|---|---|
| ① 导入评分标准 | 基本信息新增“文档类型”二选一 | 同左 |
| ② 新建评分任务 | 评分标准后显示类型标签；下方一行说明本任务的处理方式 | 同左 |
| ③ 评分工作台 | 材料列表与顶栏：学号 / 题目或姓名 | 文件名 / 标题 |
| ④ 复核页“材料”列 | 学号 | 文件名 |
| ⑤ 导出 Excel | 原有列（学号、姓名、学院、专业、论文题目） | 文件名、标题、归属单位、类别 |
| ⑥ HTML 评分报告 | “毕业论文智能评分报告”、论文题目、学生 | “材料评分报告”、标题、文件名 |
| ⑦ 评分助手 | 确认开始时说明标准的文档类型 | 同左 |

不变的部分：上传区、评分项核对、评分规则、校验与发布；批次信息、AI 连接、上传与预检；正文、评分项、扣分证据、复核操作；分数、等级、扣分点、复核列。

### 3.1 导入时选择文档类型

- 两个选项：**毕业论文**（学号、姓名、学院）、**通用文档**（文件名、标题、类别）。
- 默认值：记住本浏览器上次的选择；第一次使用默认“毕业论文”，老用户感觉不到变化。
- **上传前选择，上传后只读**。类型会影响评分标准文件的识别（领域词汇），并写进版本内容的哈希；上传后要换类型，取消本次导入重新导入即可。原型里写的“发布前可改”据此收紧，见第 9 节。
- 评分助手里导入评分标准的卡片同样加这一项。

### 3.2 新建任务

- 类型跟随所选评分标准，不需要再选。
- 技术方案类型的评分标准（只能通过 v2 接口创建）不出现在可选列表里；直接调接口建批次会被拒绝，提示原因。

### 3.3 用词

- 工作台与评分助手统一称“材料 / 份”。
- 评分助手同时听得懂“第 N 篇”“第 N 份”。

# 第二部分：技术方案

## 4. 实现

### 4.1 类型如何流转

```
导入表单 business_profile_key
  → prepared graph（rubric / version）→ rubric_versions.business_profile_key（进内容哈希）
  → 建批次锁定版本 grading_batches.rubric_version_id
  → 评分：engine 按锁定版本取 Profile
  → 解析落库 / 导出 / 报告 / 接口响应：按批次锁定版本取类型
```

- 统一入口：`profiles/registry.py` 新增 `profile_key_for_batch(batch)`——有锁定版本取版本的类型，没有（未版本化的旧批次）一律视为 `thesis`。
- 工作台支持的类型集合 `WORKBENCH_PROFILE_KEYS = ("thesis", "general_document")`。

### 4.2 通用文档 Profile

新增 `scoring/profiles/general_document.py`，`GeneralDocumentProfile` 继承 `ThesisProfile`，复用全部机制：解析适配、证据切块、检查器实现、分组调用、单篇输入上限、用量计量、v4 证据信封。只替换：

| 项 | 论文 | 通用文档 |
|---|---|---|
| `profile_key` / `profile_version` | `thesis` / `thesis-legacy-profile@1` | `general_document` / `general-document-profile@1` |
| `prompt_version`（进缓存键） | `2026-09-03-10` | `general-document-2026-10-11` |
| 提示词扩展 `instructions.domain` | `thesis` | `document` |
| 送入提示词的元数据 | 学号、姓名、题目、学院、专业、导师 | 只有标题 |
| 检查器 | 7 个 | 去掉 `thesis.coherence.research_conclusion.v1`（研究问题与结论呼应是论文专属），其余 6 个复用，注册的 `supported_profiles` 为 `general_document` |
| 语义一致性（模型调用） | 运行 | **不运行**；确定性的图表、引用、术语一致性照常 |
| 表格与报告投影 | 学号、姓名、学院、专业、题目 | 文件名、标题、归属单位、类别 |

论文检查器的注册函数加一个可选的 `supported_profiles` 参数，默认仍是 `("thesis",)`——论文的注册内容逐字节不变。

### 4.3 评分链路

- `_core_request_context`：先解析锁定的正式版本，再按版本的 `business_profile_key` 从注册表取 Profile；没有正式版本的旧批次仍用论文 Profile。
- 通用文档**只走 Core**：建批次时必须锁定已发布版本（工作台本来只列已发布标准），旧路径的论文提示词、按名称调度的检查器、3000 字下限都不会经过。
- `_score_paper_core`：Profile 声明 `semantic_coherence = False` 时跳过 `analyze_semantic_coherence`。
- 论文路径：取到的仍是 `ThesisProfile`，计划、请求、幂等键、缓存键都不变。

### 4.4 导入与发布

- `POST /api/rubrics/import-sessions` 增加表单字段 `business_profile_key`（默认 `thesis`，只接受工作台支持的两种），传给 `_file_import_command`。
- 导入会话响应增加 `business_profile_key`（取自 prepared graph）。
- 发布校验：`DEFAULT_BUSINESS_PROFILE_REGISTRY` 登记 `general_document`；`DefaultPublicationCheckerRegistry` 里复用的 6 个论文检查器与 `thesis.legacy_required_fields.v1` 的 `supported_profiles` 加入 `general_document`。

### 4.5 建批次守卫

`actions.create_batch` 在解析版本后检查类型：不在 `WORKBENCH_PROFILE_KEYS` 内的返回 400“该评分标准的文档类型（…）不能在工作台评分”。页面与评分助手共用这一个函数。

### 4.6 解析落库

`papers/ingestion.parse_and_store`：通用文档不从封面填学号、姓名、学院、专业、导师（避免张冠李戴）；标题取解析出的标题，没有就取文件名去掉扩展名。论文不变。

### 4.7 接口字段（全部追加、可空，不改已有字段）

| 响应 | 新字段 |
|---|---|
| `RubricRead`（列表与详情） | `business_profile_key`：最新版本的类型；未版本化为 `null` |
| `RubricImportSessionRead` | `business_profile_key` |
| `BatchRead`（列表、详情、新建） | `business_profile_key`：按 4.1 推出，旧批次为 `thesis` |
| 复核队列条目 | `file_name`、`title` |

OpenAPI 合同（`schema.d.ts`）随之更新；契约版本守卫 `X-PGS-Contract` 只覆盖 AI 任务接口，不受影响。

### 4.8 导出与报告

- Excel：身份列由类型决定，其余列不变；列宽、换行、数字格式改为按表头名称配置，论文导出的列、顺序、宽度与现在一致。
- 在线表格写入器（`spreadsheet/writer.py`）同样按类型取表头。
- HTML 报告：标题与身份行按 `run.business_profile_key` 选择文案。
- JSON 导出不变。

### 4.9 前端

- `lib/document-types.js`：类型名称、身份字段显示规则、上次选择的读写（`localStorage`，读写失败时退回默认值）。
- `RubricImportWorkspace` 基本信息：初始步骤为二选一，上传后只读显示；`RubricsView`、`stores/rubrics.js` 把它带进创建请求。
- `NewTaskView`：类型标签、处理说明，不支持的类型不可选。
- `GradeView`：顶栏与材料列表按批次类型显示（`stores/grading.js` 打开批次时读取批次）。
- `ReviewView`：“材料”列按批次类型显示学号或文件名。
- 用词：`AuthLayout`、`AssistantView`、`AssistantCard` 中的“论文”改为“材料”或通用说法。

### 4.10 评分助手

- 导入卡片加文档类型二选一，前端带进同一个创建导入会话的请求。
- 确认开始时说明标准的文档类型。
- 定位与回复里的“第 N 份《…》”：通用文档用标题或文件名，论文仍用姓名。
- 意图识别提示词“论文评分系统”改为“文档评分系统”，`ASSISTANT_PROMPT_VERSION` 升到 `assistant-intent@2`。
- 其余“论文”文案改为“材料”。

## 5. 放弃了什么

| 放弃的做法 | 为什么不选 | 代价 |
|---|---|---|
| 工作台整体迁到 v2 Submission 接口 | 批量评分、任务队列、评分助手、导出、复核都建在 v1 批次上，迁移是数倍工作量 | 数据库列名仍叫 `student_*`，只能靠显示名称遮住 |
| 新建批次表的类型列 | 版本表已有类型且进了内容哈希；再存一份会出现两处不一致 | 批次的类型要经锁定版本推出，多一次关联查询 |
| 通用文档也支持旧路径 | 旧路径的提示词、检查器、字数下限都按论文写，要重写一遍 | 通用文档必须先发布评分标准（工作台本来如此） |
| 通用文档复用论文的语义一致性 | 提示词按“绪论、结论”写，对方案和报告会误报，还多一次模型调用 | 通用文档没有“前后呼应”类发现，需要的话写进评分标准 |
| 上传后允许改类型 | 类型影响识别并进入内容哈希；改了要重新识别，会丢掉已核对的评分项 | 选错了要取消重导 |
| 技术方案类型进入工作台 | 它没有工作台评分路径需要的论文适配方法，还有自己的厂商、项目字段 | 技术方案继续只能通过 v2 接口评 |
| 在界面里配置新文档类型（M9） | 需要 schema 驱动的 Profile，超出本次范围 | 再加一种类型仍要写代码 |
| 用真实模型验证效果 | 未获授权与预算（见维护者约定） | 通用文档的真实效果要另行抽样比对 |

## 6. 决定记录

| 编号 | 决定 |
|---|---|
| G1 | 文档类型挂在评分标准版本上，批次、评分、解析、导出、报告都由它推出；不迁移 |
| G2 | 新增 `general_document`，继承论文 Profile，只替换领域说明、元数据、身份字段、提示词版本、检查器集合，并关闭语义一致性 |
| G3 | 通用文档只走 Core；论文路径不变 |
| G4 | 导入时选择，记住上次选择，首次默认毕业论文；上传后只读 |
| G5 | 技术方案不进入工作台，建批次时拒绝 |
| G6 | 通用文档身份显示为文件名 + 标题；导出身份列为文件名、标题、归属单位、类别；数据库列不改名 |

## 9. 实施记录（2026-10-11）

与原型和第 4 节的出入：

- 原型写“发布前可改”，实施为“上传前选择、上传后只读”，原因见 3.1 与第 5 节。
- `RubricRead.business_profile_key` 实现为 `Rubric` 上的只读关联子查询（`column_property`，默认延迟加载，列表接口 `undefer` 一次带回），而不是在列表路由里另查一次——这样发布、确认导入、克隆等所有返回评分标准的接口都带同一个值。
- `BatchRead.business_profile_key` 实现为 `GradingBatch` 上的只读属性；列表接口用外连接一次带回。
- 类型守卫抽成 `actions.require_workbench_version`：建批次、修改批次的评分标准（上传材料前）、评分助手建批次都经过它。
- 评分助手里列出的候选评分标准同样过滤掉技术方案；确认卡片多了一行“文档类型”。
- 重新上传（导入草稿内、已确认草稿）沿用原来的类型；旧的 `POST /rubrics/import-files` 也接受可选的 `business_profile_key`。
- 论文 Profile 把领域说明、元数据白名单、排除的检查器、语义一致性开关、身份列与报告文案改成类属性，取值与改造前相同；检查器注册的 `supported_profiles` 改为取自 `profile_key`，论文仍是 `["thesis"]`。导出列宽、换行、数字格式改为按表头名称配置，论文导出逐列核对与改造前一致。

验证（全部离线，Mock 模型）：后端新增 `test_general_document.py` 10 项（类型注册、发布校验、导入、通用文档全链路、论文不变、建批次守卫、助手定位）；前端新增文档类型、导入工作区、新建任务页、评分 store、导入会话 store、助手候选的单元测试，以及“导入时选择文档类型”的浏览器用例。
