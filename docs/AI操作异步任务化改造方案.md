# AI 操作异步任务化与统一执行模型改造方案

状态：**A1、A2、B、C 已全部实施（2026-10-10，迁移 0035、0036、0037）**。C 的实施补充：导入前的结构识别还没有评分标准，迁移 0037 让这类任务的 `rubric_id` 为空、按用户去重；估算拆成独立接口（见 DECISIONS 2026-10-10 “AI 任务 C”）。对应待办清单 P1 第 5 项，并包含 P0 第 4 项（批量评分卡住恢复）。决定记录见第 13 节；第 13.2 节列出实施前仍需确认的数值。

## 1. 背景

**评分标准侧的 AI 操作仍是同步请求**：浏览器发请求，后端在这个请求里调用模型，等结果回来再返回。

| 接口 | 现状 | 问题 |
|---|---|---|
| 起草扣分细则 `POST /rubrics/{id}/draft-deduction-rules` | 一个评分项一个请求，内部 3–6 批，按连接并发上限并行或串行 | 并发为 1 时串行，可能超过 Vercel 300 秒上限（PR #13 先用 260 秒总预算止血）；刷新或关页面后结果丢失；已完成的批次随失败一起作废 |
| AI 归类 `POST /rubrics/{id}/unit-classifications` | 前端调度器每批 3 条、按连接并发上限并发 | 并发由前端控制，多个标签页会超限；关页面后剩余批次不再发出 |
| 规则审查 `POST /rubrics/{id}/rule-review` | 同步，按评分项逐个调用模型 | 评分项多时同样可能超时 |
| 结构识别 `POST …/structure-suggestions`（两处） | 同步，一次调用 | 慢模型可能超时 |

这些问题的共同根源是“用户的请求在等模型”。

**批量评分已是异步任务，但按部署环境走两套不同的实现**。`vercel_queue.vercel_queue_enabled()` 只看 `BATCH_SCORING_DISPATCH` 或 `VERCEL` 环境变量：Vercel 生产走队列；内网 compose 与本地 `start-web-pg.sh` 走 worker。worker 在先；2026-09-15 为了绕过 Vercel 的 300 秒上限，又加了队列路径（DECISIONS“持久化后台评分”），之后明确不在本地模拟 Vercel 队列。两条路径的差异（2026-10-10 核对代码）：

| | Vercel（`_claim_queue_item`） | worker（`run_worker_cycle` → `run_batch_scoring_job`） |
|---|---|---|
| 领取单位 | 一篇（一条消息一篇） | 整个任务，由一个 worker 用线程池跑完 |
| 领取方式 | 消息到达后锁任务行（阻塞等锁） | 先不加锁查最早的任务，再锁；抢输了下一轮重试 |
| 租约与心跳 | 每篇租约 330 秒，心跳记在任务上 | 任务租约 120 秒，每 15 秒心跳 |
| 名额检查 | 跨任务：锁连接行 + 三表 `COUNT`；满了延迟 30–300 秒重投 | 只在建任务时按单个任务限制线程数，任务之间不检查 |
| 执行次数上限 | 只有 Vercel 的 12 次；用完后消息被丢弃，条目卡在“运行中”（P0 第 4 项） | 没有：同一篇每次都把进程弄崩，会无限重跑 |
| 卡住后的恢复 | 靠 Vercel 重投 | 取下一个任务时顺带取回租约过期的任务 |
| 公平性 | 先来先评 | 按任务先来后到，大任务挡住后面所有人 |

后果：一边修了另一边漏掉（例如 #13/#14 的跨任务名额检查只在 Vercel 路径）；本地和 CI 冒烟测的是 worker 路径，不是生产实际运行的逻辑。另外，积压时 Vercel 路径的名额满条目每 30–300 秒重新排队一次，数据库开销与积压量成正比，并且全部争抢同一行锁（没绑私有连接的批次共用平台模型那一行）。全仓库没有一处使用 `SKIP LOCKED`。

做对的部分保留：每篇的结果都有检查点，重跑时续评而不重复；worker 的取任务查询已经包含租约过期的任务。

## 2. 目标与不做的事

目标：
1. **数据库即队列，全系统一套执行逻辑**。批量评分与 AI 任务都由同一个领取函数取活，Vercel、内网、本地三种部署行为一致。平台相关的只剩“谁来叫醒”：Vercel 上是一条不带任务信息的叫醒消息，内网和本地是 worker 循环。
2. AI 操作提交后立即返回任务 ID；刷新或关页面不影响任务继续执行。
3. **一次执行只处理一个条目**：AI 任务的一个条目是一批，只调用一次模型，最长约 120 秒；批量评分的一个条目是一篇，超过 300 秒的靠检查点跨多次执行续评。
4. **不原地等**：遇到 429 或名额已满，条目带上“最早可执行时间”回到待处理，函数正常退出。
5. 两层任务表（任务 / 条目）。每个条目的结果先落库；失败时只重试失败的条目。
6. 用内容指纹去重：重复提交（双击、多个标签页、刷新后重点）拿到同一个任务。
7. 采用 AI 结果时，在规则上写明“来自 AI”和生成模型名，用于对比新旧模型在评分与规则精细度上的差别。
8. 按几百人同时在线规划（第 9 节）。

不做的事（理由见第 12 节）：后端改成 async/await；依赖厂商回调（Webhook）；SSE、WebSocket 或 Supabase Realtime 推送；引入 Redis、自建或第三方 MQ；定时任务作为恢复手段。

## 3. 总体架构

```
浏览器 ──POST──▶ 后端：校验 → 指纹去重 → 写任务和条目 → 按空闲名额叫醒 → 返回任务（202）
   ▲                                                        │
   │ 每 2–5 秒 GET 进度（页面隐藏时暂停）                       ▼
   │                         ┌──────────── 叫醒（平台相关，只有这一层）────────────┐
   │                         │ Vercel：叫醒消息 {source_key}，不带任务信息           │
   │                         │ 内网/本地：worker 循环                                │
   │                         └──────────────────────┬──────────────────────────────┘
   │                                                ▼
   │                  claim_next_item(source_key)：SKIP LOCKED 取下一个条目
   │                    · 名额：锁来源行，统计该来源在跑条目（部分索引，只读几行）
   │                    · 顺序：AI 条目优先；同类按用户轮转
   │                    · 条目各自的租约与心跳；连续无进展计数
   │                                                ▼
   │                  执行：AI 条目一次模型调用 / 评分条目评一篇（检查点续评）
   │                  落库：条目结果；任务计数增量更新；最后一个条目完成时合并
   │                  接力：还有待处理的条目且有空位 → 再叫醒一次
   │                                                │
   └──────────────── 任务状态、进度、结果 ◀──────────────┘

巡检（同一个函数）：Vercel 上 2 分钟一次的自续期消息；页面读取时只对本任务；worker 每一轮
```

数据库是唯一的事实来源。叫醒消息重复无害（取不到条目就退出），丢失由巡检补发，因此 Vercel 队列的重试次数与条目状态无关。

## 4. 数据模型

### 4.1 `ai_tasks`（任务，迁移 0036）

| 字段 | 说明 |
|---|---|
| `id`、`organization_id`、`owner_id` | 组织隔离与归属；`owner_id` 用于按用户轮转 |
| `kind` | `rule_draft`、`unit_classification`、`rule_review`、`structure_suggestion` |
| `rubric_id`、`scope` | 作用对象。例如起草时 `scope` 为评分项编号；归类时为排序后的单元 ID 列表 |
| `input_snapshot` | 建任务时冻结的输入（评分项、规则原文、归入的原文单元等），各条目据此拆分，保证可复现 |
| `fingerprint` | 内容指纹（第 7 节） |
| `ai_connection_id`、`ai_connection_key_version`、`ai_connection_snapshot` | 和批量评分一样锁定连接；执行时连接或密钥变了，就以明确错误失败 |
| `model_name` | 生成模型名，采用结果时写进规则（第 4.4 节） |
| `status` | `queued` / `running` / `succeeded` / `failed` / `canceled` / `superseded` |
| `total_items`、`succeeded_count`、`failed_count`、`pending_count` | 进度，条目结束时增量更新 |
| `result` | 合并后的结果（例如完整的起草草稿），只在 `succeeded` 时有值 |
| `error_code`、`error_message` | 根因错误码和可读提示（复用批量评分取根因码的逻辑） |
| `state_version` | 乐观锁 |
| `created_at`、`started_at`、`finished_at` | |

生命周期：评分标准**发布时**删除它名下的全部 AI 任务与条目；评分标准被删除时级联删除。不设时间期限，弃置不管的任务随发布一起清理。

索引：`(organization_id, fingerprint)` 上建部分唯一索引，条件为 `status in ('queued','running','succeeded')`，作为去重锁（第 7 节）。

### 4.2 `ai_task_items`（条目，一批一条，迁移 0036）

| 字段 | 说明 |
|---|---|
| `id`、`task_id`、`ordinal` | 批次序号，合并时按序；同时是轮转用的“任务内序号” |
| `source_key` | 模型来源键（私有连接 ID，或平台模型），从任务冗余而来，供名额统计与领取走部分索引 |
| `owner_id` | 从任务冗余，供按用户轮转 |
| `input` | 本批输入（起草的批次分析，或归类的 3 个单元） |
| `status` | `pending` / `running` / `succeeded` / `failed` / `canceled` |
| `not_before` | 最早可执行时间（429 或名额已满后延后） |
| `started_at`、`heartbeat_at` | 租约：心跳超过租约时长未更新即视为这次执行已死 |
| `attempt_count`、`stall_count`、`deferral_count` | 总执行次数；连续无进展次数（第 6.4 节）；因 429 延后的次数 |
| `attempt_history` | 每次执行的错误码与耗时（不存厂商正文） |
| `output` | 本批模型结果（已校验） |
| `error_code`、`error_message` | 最终失败原因 |

### 4.3 `batch_scoring_items` 的变化（迁移 0035）

新增 `source_key`、`owner_id`、`ordinal`（任务内序号）、`heartbeat_at`、`stall_count`、`not_before`。建任务时写入；存量条目在迁移里按所属任务回填。任务行上已有的各状态计数列沿用，改为条目结束时增量更新，不再每次加载全部条目重算。

### 4.4 规则来源字段（迁移 0036）

- `AtomicRule` 新增 `ai_origin`（布尔，非空，默认否）与 `ai_model`（可空）。评分项的结构化规则条目（`deduction_rules_structured` 的每一项）同样带上这两项。
- 采用 AI 结果时直接写入，`rule_origin.is_ai_rule` 改为读字段，不再按 `rule_code` 或位置反查。
- 存量回填：迁移时用现有 `is_ai_rule` 推断一次 `ai_origin`；`ai_model` 留空，表示历史未记录。
- 评分结果一侧已经记录模型（`ScoringRun.model_name` 与连接快照），两侧合起来即可按模型对比。

### 4.5 部分索引（两张条目表各一组）

- 领取：`(source_key, ordinal, created_at) WHERE status = 'pending'`。
- 名额统计与巡检：`(source_key, heartbeat_at) WHERE status = 'running'`。

索引里只有待处理或在跑的少量行，已结束的历史条目不在其中，领取、名额统计和巡检的开销都与表的总行数无关。实测（SQLite，230 万行，其中 5 行卡住）：只有现有 `(job_id, status)` 索引时全系统查询每次 47 ms，执行计划为全表扫描；加部分索引后每次 0.002 ms。Postgres 的绝对数值不同，但量级关系相同。

### 4.6 迁移要求

- 按 CLAUDE.md：新表必须在迁移里给 `pgs_app` 授权并建 RLS（照 0023 的做法）。漏了不会让迁移失败，只会让上线后的应用报 permission denied。
- 0035 降级：存在 `queued`、`running` 或 `cancel_requested` 的批量评分任务时拒绝。
- 0036 降级：`ai_tasks` 有数据，或任何规则的 `ai_model` 非空时拒绝。
- `test_migrations.py` 补 0035 与 0036；CI 的 Postgres 逐版本迁移会自动覆盖；`postgres_verifier` 检查新增的部分索引存在。

## 5. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/rubrics/{rubric_id}/ai-tasks` | 体：`kind`、`params`（评分项编号或单元 ID 等）、`ai_connection_id`、`regenerate`。新建返回 202；命中去重返回 200 和已有任务（第 7 节） |
| GET | `/api/ai-tasks/{id}` | 状态、进度、各条目状态；成功时附结果。对本任务做一次限频巡检（第 6.5 节） |
| GET | `/api/rubrics/{rubric_id}/ai-tasks?kind=&active=1` | 刷新页面后找回进行中的任务 |
| POST | `/api/ai-tasks/{id}/cancel` | 取消：未开始的条目直接取消，进行中的条目跑完后不再继续 |
| POST | `/api/ai-tasks/{id}/retry` | 只重试失败的条目，已成功的保留 |

批量评分的现有接口不变；进度接口同样对本任务做限频巡检。

**旧同步接口**：哪个操作迁到任务，就在同一个 PR 里停用它的旧接口（返回 410），不等其它阶段；对历史数据的影响忽略。

**版本守卫**（与第一个停用旧接口的阶段一起上线）：后端每个响应带构建号响应头；前端记下自己的构建号，发现不一致时，在下一次写操作或路由切换之前静默刷新页面。已经打开的旧页面因此不会调用已停用的接口，也不会报错或写入数据。

权限：沿用 `_visible_rubric` 加 `require_organization_role("org_admin", "teacher")`；任务只对同组织可见。

## 6. 执行

### 6.1 领取：`claim_next_item(source_key)`

在一个短事务里完成：
1. 锁来源行（私有连接行或平台模型配置行，与现在相同），用部分索引统计该来源在跑且租约有效的条目数，满了就返回“无空位”。领取次数与评分速度相当，这把锁不再是热点。
2. 用 `SELECT … FOR UPDATE SKIP LOCKED LIMIT 1` 取下一个条目，条件为 `status = 'pending' AND not_before <= now()`。顺序：AI 条目优先（用户在页面上等），同类内按 `ordinal` 轮转（所有任务的第 1 个条目先执行，再执行各自的第 2 个），再按创建时间。
3. 置为 `running`，写 `started_at`、`heartbeat_at`，`attempt_count + 1`。

批量评分条目与 AI 条目共用连接名额。

### 6.2 叫醒

- **Vercel**：一个订阅 `pgs-work`，消息体 `{source_key}`，不带任务或条目 ID。函数被叫醒后调用 `claim_next_item`，取到就执行，取不到就退出；执行结束后，如果该来源还有待处理条目且有空位，再发一条叫醒。建任务时按空闲名额发对应条数。条目因 429 延后时，按 `not_before` 发一条延迟叫醒。订阅的 `max_concurrency` 即全局并发上限，沿用 `BATCH_SCORING_QUEUE_CONCURRENCY`（默认 8）。
- **内网与本地**：worker 循环调用同一个 `claim_next_item`，线程数即并发，默认 8。compose 不新增服务。
- **切换期**：部署时队列里可能还有旧格式消息 `{job_id, item_id}`，处理函数兼容旧格式，按“叫醒该条目所属来源”处理。

### 6.3 一次执行

- **AI 条目**：只调用一次模型（`attempts_limit=1`、`rate_limit_retries=0`），超时、429 都不在原地等。起草的“输出不合格后修正一次”作为该条目的下一次执行，带修正提示重新入队，而不是在同一次执行里连做两次。
- **评分条目**：评一篇，沿用现有的规则检查点；超过 300 秒的由下一次执行续评。
- 执行期间每 15 秒更新该条目的 `heartbeat_at`。

### 6.4 结果处理与执行次数

| 结果 | 处理 |
|---|---|
| 成功 | 写结果，条目 `succeeded`，任务计数增量更新；AI 任务的所有条目都已成功时，锁任务行，按 `ordinal` 合并（复用 `draft_deduction_rules` 里的合并与 `validate_ai_rule_draft`），任务 `succeeded` |
| 429（限流，可重试） | 条目回到 `pending`，`not_before = 现在 + Retry-After`（没有就 30 秒），`deferral_count + 1`，发延迟叫醒；超过 5 次才判失败 |
| 名额已满 | 不领取，不计数 |
| 输出不合格（可修正） | 再执行 1 次（带修正提示），仍失败才判失败 |
| 超时、5xx | 最多再执行 1 次 |
| 额度耗尽、鉴权失败、请求被拒（400 / 401 / 403 / 404） | 立即判失败 |
| 模型、材料错误（评分条目） | 照旧逐篇记为失败 |
| 有条目永久失败 | AI 任务 `failed`，取根因码；已成功的条目保留，可以“重试失败的条目” |

**连续无进展上限**：每次执行结束或被发现已死时，如果这次执行没有写入新的检查点或结果，`stall_count + 1`，否则清零。达到上限（默认 3）时标为失败，原因写“多次执行都没能推进（超过运行时间上限或进程中止）”，并收敛任务状态，页面的“重试失败项”随之可用。按“无进展”而不按总次数计算，是因为超过 300 秒的单篇本来就要靠多次执行续评完成。

归类任务的结果合并：每个条目成功后，就用现有 `run_unit_classification` 里的“锁行 + 指纹校验 + 合并”逻辑写进 `unit_classifications`，页面可以边跑边看到建议；任务完成只是汇总计数。

### 6.5 巡检：找回卡住的条目（同时解决 P0 第 4 项）

同一个巡检函数 `sweep_stale_items(scope=全系统|某任务)`：
- 用部分索引找出 `running` 且心跳超过租约的条目，`SKIP LOCKED` 取行，每次最多 200 条：计入无进展次数；未达上限的重置为 `pending` 并叫醒，达到上限的标为失败。
- 有待处理条目、有空位、但没有在跑的来源：补发叫醒。
- 收敛已全部结束的任务状态。

调用方：
- **Vercel**：一条自续期的延迟消息，每 2 分钟一次，幂等键按时间槽生成（`sweep-<槽号>`），不会出现两条链。数据库记录最近一次巡检时间；任何进度查询发现超过两个周期没巡检，就补投一条。全系统每月约 6.5 万次队列操作，与用户数无关；免费额度为 100 万。
- **页面读取**：进度接口只对本任务执行，原子条件更新，每个任务 30 秒最多一次；用户刷新后几秒内看到结果。
- **内网与本地**：worker 每一轮执行。
- 以后如果升级到 Vercel Pro：改用 Vercel Cron 每 2 分钟调用，取代消息链；接口须校验 `CRON_SECRET`。

租约过期的含义是“这次执行已死”，不是“这个条目失败了”：现有逻辑遇到租约过期的条目会重置后续评（RUNBOOK 验收项“强制终止后消息重投、330 秒后恢复且不重复有效结果”），这一点保留。

## 7. 去重与幂等

**内容指纹** = sha256（规范 JSON）：
- `kind`、`rubric_id`、当前编译版本；
- `scope`：评分项编号，或排序后的单元 ID；
- 冻结输入的哈希：规则原文、归入的原文单元；
- 连接 ID、密钥版本、模型名；
- 提示词版本（`AI_RULE_DRAFT_PROMPT_VERSION`、`CLASSIFIER_PROMPT_VERSION` 等）。

不包含时间戳和客户端生成的键。

建任务时：
1. 同一评分标准下已有同指纹的任务（进行中，或已成功、尚未随发布清理），直接返回它（200），不按时间判断。并发的两次提交靠部分唯一索引兜底：插入冲突的一方回查后返回胜出者。
2. `regenerate=true`（点“重新生成”）：把旧任务标为 `superseded`（进行中的先取消），再建新任务。模型每次输出不同，用户可能确实想换一版。
3. 归类按单元去重：新任务要处理的单元里，已在其它进行中归类任务里的那些单元会被剔除；全部被占用时，返回那些进行中的任务。

前端在发起函数开头加重入保护（`if (busy) return`），作为最便宜的第一道防线。

## 8. 前端

- **起草**：点“AI 根据规则来源起草”后显示任务进度（“第 2/4 批”）、取消按钮；完成后进入现有的草稿确认面板，交互不变。失败时显示根因提示和“重试失败的批次”。“生成全部缺失细则”为每个评分项建一个任务，由后端按名额调度。
- **归类**：去掉前端调度器 `classifyInBatches`，改为一个任务；进度和“本轮已获得 N/M 条建议”由任务计数给出。PR #11 的“续跑跳过已有建议”由后端建任务时剔除已有有效建议的单元。
- **规则审查、结构识别**：同样改为“提交 → 进度 → 结果”。
- **规则来源展示**：规则上显示“AI”标记与生成模型名。
- **轮询**：AI 任务前 30 秒每 2 秒一次，之后每 5 秒一次；批量评分页面保持现有 3–5 秒。所有轮询在页面隐藏时暂停（`visibilitychange`），回到前台立即刷新一次。进入评分标准页时调用 `GET /rubrics/{id}/ai-tasks?active=1` 找回进行中的任务。
- **版本守卫**：见第 5 节。

## 9. 并发、限流与规模

- **连接的“同时请求数”**由用户在账户页配置（已有），在领取时统一执行，同时计入批量评分和 AI 条目；前端和多个标签页都绕不过去。平台默认模型也可以声明（PR #14）。
- **全局并发**保持默认 8，不做界面配置：Vercel 上是叫醒订阅的 `max_concurrency`，worker 上是线程数。
- **出错与拥塞提示**：模型调用失败目前只写日志（`llm/call_log`），不落库。按连接记录最近的调用结果；最近 20 次里限流、超时或厂商过载超过 30% 时，在账户页和任务页提示调低“同时请求数”，建议值取当前值的一半（至少 1）。额度耗尽（`quota_exhausted`）不提示调低，因为调低解决不了。
- **规模（按几百人同时在线规划）**：轮询约每秒几十到一百多次，加上页面隐藏时暂停即可，不做退避拉长。吞吐的瓶颈是模型：全局并发 8、每篇 1–2 分钟时约 240–480 篇/小时。几百人同时各提交一批时，排队会达到小时级；需要更快时，按 Bedrock 配额同时调高全局并发与连接的“同时请求数”。到上万人的规模，需要提高并发与厂商配额、升级 Vercel 与 Supabase 付费档，并加上轮询退避，超出本方案范围。

## 12. 放弃了什么（实施时写进 DECISIONS）

- **保留两条执行路径**：行为不一致，一边修了另一边漏掉，本地和 CI 测的不是生产实际运行的逻辑。
- **完全去掉 Vercel 队列**：Vercel 上没有常驻进程；免费套餐的定时任务每天只能 1 次；靠浏览器反复触发，关页面就停了；另找平台跑 worker 要多一个部署平台。叫醒这一层在免费套餐上只能用队列。
- **一条消息一个条目（现状）**：积压时名额满的条目反复重新排队，数据库开销与积压量成正比，并且争抢同一行锁。
- **（推翻）10-08 放弃的“只投一部分、做完一篇再投下一篇”**：当时放弃的理由是“消费函数在投下一篇之前崩溃，剩余论文就再没人投递；在任务卡死的自动恢复（P0 第 4 项）做好之前，会引入新的卡死点”。本方案的接力叫醒与巡检（第 6.5 节）在同一阶段 A1 交付，巡检会给“有待处理、有空位、没人在跑”的来源补发叫醒，前提已经满足。约束：接力叫醒不得先于巡检上线。
- **每个条目各投一条延迟核查消息**：消耗随在途条目线性增长，按 1 万人各 30 篇估算约 830 次/秒的函数调用，每月约 65 亿次队列操作。
- **按 Vercel `delivery_count` 标记“消息重投用尽”**：统一后消息不代表任务，丢一条叫醒消息不影响任何条目；改由数据库计数，所有平台都生效。Vercel 队列也没有托管的死信队列或重试告警。
- **租约一过期就标为失败**：会让本来能续评完成的长论文变成失败。
- **定时任务作为恢复手段**：免费套餐每天最多 1 次，写成更高频率会导致部署失败；升级到 Pro 后才改用 Cron。
- **第三方 MQ（RabbitMQ、SQS、QStash 等）**：数据库与队列会成为两份状态，需要事务发件箱和对账；这个规模用不上它的吞吐；内网部署也用不了外部服务。
- **把后端改成 async/await + `httpx.AsyncClient`**：解决不了 300 秒上限和刷新问题；整条链路都是同步的，改动面大、收益小；厂商按 Key 限并发，线程不是瓶颈。
- **一条消息处理一个任务的多批**：单次调用时长又会逼近 300 秒，一批失败会连累其它批。
- **消费函数里原地重试 429**：会把函数挂在 `sleep` 上，占着实例和时长额度。
- **依赖厂商回调（Webhook）**：用户可以自带任意兼容接口，不能依赖。
- **SSE / WebSocket / Supabase Realtime 推送**：SSE 受函数时长限制要断线重连，Serverless 不适合 WebSocket；Realtime 的权限依赖 Supabase Auth 的 JWT，而本系统用自己的会话，内网部署也没有 Supabase。
- **单独的幂等键回执表**：内容指纹加部分唯一索引已经覆盖。
- **结果复用窗口（30 分钟）与保留期（7 天）**：改为保留到评分标准发布，同指纹直接复用，避免同一份内容反复计费。
- **全局并发做成界面配置**：多组织共用，谁改都会影响别人；用户只调自己连接的“同时请求数”。
- **旧接口保留到全部迁完再停用**：维护两套入口；改为每阶段停用，旧页面由版本守卫处理。
