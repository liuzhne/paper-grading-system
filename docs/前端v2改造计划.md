## 1. 结论摘要

产品由按对象浏览转向按任务推进：工作台 → 批次 → 评分工作区 → 复核 → 导出。改造的关键依赖是正式评分能被正确查看、人工处理和审计，其次才是页面重排。

- 评分工作区需要冻结正文投影、Core/legacy 证据适配、非引用证据展示；增加页码不能单独完成定位。
- 复核队列同时包含普通确认与阻塞人工任务。`confidence=None` 不代表无需复核；未解决的阻塞任务必须保持总分和等级为空。
- 状态机需统一上传、解析、批任务、单篇重评、复核和归档的写入口；枚举约束仅是最后一道数据校验。
- 直传恢复、现有 Excel 日志、组织隔离和本地/Docker/Vercel 三种部署均属于必须保留的能力。
- 后端变更覆盖投影、状态、权限、复核并发和导出审计；不能再按“除原因字段外后端零改动”估算。

执行顺序：先完成部署与权限基础、状态及证据合同，再交付复核闭环和完整工作区，最后切换上传/模板/输出页面。每个阶段按 §12 验收后才能替代旧入口；双评/仲裁不计入首版。

门禁阈值仍由获授权用户提供，禁止预填生产阈值；运维页面只做观察与授权配置录入，**不授予 GATE-03 发布权限**。

## 3. 当前实现事实

- Web 是 `frontend/web/` 原生 HTML/JS/CSS；Vercel 由 `scripts/build_web_static.py` 生成 `public/`。本地 FastAPI 和 Docker 使用 `frontend/web`，尚无 Vite/浏览器测试流水线。
- 论文链路为 `GradingBatch → Paper → PaperChunk`；评分链路为 `ScoringRun → ScoreItem → ReviewLog`，Core 另有 `DocumentSnapshot / RuleScoringTask / ManualReviewTask`。
- 未版本化 compatibility 可能返回 `{quote, location, chunk_id}`；正式 Core 保存 `{evidence_unit_id, evidence_type, locator, payload_hash}`。`LegacyPaperAdapter.adapt()` 不把 chunk 行 ID/边界当作不可变身份，Core 持久化当前设 `confidence=None`。
- DOCX 和文字 PDF 都是输入；PDF chunk 可能含页码，DOCX 无真实分页。Core 快照不能假定有 PDF 页码或与 chunk 一一对应。
- 默认大小配置为 50 MB，TUS 阈值 6 MB；UI 读取部署能力中的实际限制，服务端最终校验。不能把默认值写成所有部署的固定上限。
- 现有 Web 已有逐文件直传/TUS/归档确认/解析及失败重试；`/papers/bulk-upload` 是另外的同步入口。
- 已有 `/api/v2/manual-review-tasks` 的查询、领取、释放、解决端点；解决依赖 version、领取者及冻结证据。普通 `PATCH /score-items/{id}` 与整体 review 不可绕过阻塞。
- `SpreadsheetWriteLog` 已记录 `mock_sheet / google_sheets / excel / excel_v2`；v1 批次 Excel 按 run 逐条落日志。缺全通道事件身份和操作人，HTML/JSON 尚未统一落日志。
- `/system/integrations` 已包含离线与 Sheets 可用性线索，无须另建意义重复的 deployment-mode 端点；在 §2.1 的能力投影内整合。
- `grading_batches.status` 无 CheckConstraint；业务编排主要写 draft/scoring/scored/scored_with_errors，Create/Patch 还允许客户端传 status。不能把“内置写入四种值”当作存量值全集。

评分标准的 AtomicRule、RuleLevel、SourceRule、审核与发布基础继续复用；UI 重组不修改用户授权规则、分值、冻结版本和评分政策。

### A. 冻结正文与证据定位

新增按 run 读取的正文投影服务，放在 API/adapter 层；不改 Core 的不可变快照、已有证据或评分计算。

| 来源 | 正文与身份 | 定位策略 |
|---|---|---|
| 正式 Core | `run.document_snapshot`，返回 snapshot hash、section 与 evidence unit 的稳定顺序 | 用 `evidence_unit_id + locator` 在同一快照定位；不关联当前 chunk 猜测身份 |
| legacy compatibility | 经组织校验的 PaperChunk，按文档顺序和 ID 稳定排序 | 已验证 `chunk_id` 内匹配 quote；显示“当前解析文本”，不伪称历史冻结快照 |
| 历史缺失/非引用证据 | 显式返回不可定位原因或结构/格式 finding | 展示检查事实与审计定位信息，不伪造引用、页码或空字符串高亮 |

计划 DTO：正文 `source_kind / run_id / document_snapshot_hash / blocks / next_cursor`；block 包含稳定 `block_id`、`evidence_unit_id` 或 `chunk_id`、章节、正文、可空页码。采用有界分页，支持指定锚点读取其所在页，避免整篇大文档一次返回或依赖当前已加载页。

评分项新增独立 `evidence_view` 展示投影，保留原始 evidence 的审计语义及旧默认响应。展示项包含 `source_kind / snapshot_hash / anchor_id / evidence_type / quote / section_title / page_start / page_end / location_status`。`quote` 只有在留存的审计内容可验证时才作为引文显示；仅有 unit locator/payload hash 时显示对应证据单元上下文，标注“证据上下文”，不能从 hash 反推出模型原句。页面不把上下文自动当成人工确认的证据。

Core 页码只有存在可验证的来源映射时才提供；首版允许 Core 页码为空，优先保证冻结正文定位。legacy 文本匹配保留空白归一化到原始字符区间的映射，多处命中时不任意选一句；找不到就显示无法精确高亮，仍可查看块上下文。正文和模型文字按纯文本渲染，禁止拼接不可信 HTML。

`GET /scoring-runs/{id}/document-view` 与评分项展示投影使用同一快照身份，按当前组织授权且 `Cache-Control: private, no-store`。查不到冻结快照时不静默退回最新解析文本；正常评分不因新增显示逻辑改变身份或重算。非论文页面如纳入范围，通过同一投影服务加 `/api/v2` 入口，不让 v1 Paper 路由接受 Submission。

### B. 普通确认、阻塞任务与原因

**统一队列**按当前有效结果集合选择 run，输出材料、评分项、队列类型、可空分数/置信度、原因列表、task id/version、是否可采纳和分页游标。默认显示普通 `need_manual_review` 项及 open/claimed 阻塞任务；阻塞优先。Core `confidence=None` 显示“未提供”，不得转为 0、满置信度或排除出队列。`review-sample` 是确定性抽样监控，继续独立保留。

**当前结果选择器**由队列、KPI、复核统计、分布图、导出预检共享：优先使用当前批任务 generation 的材料范围和选中 run；新 generation 尚未完成的材料标待评，不能用旧 run 冒充新结果。无批任务的历史/单篇评分采用确定的 `(created_at, id)` 排序，并让单篇重评进入相同失效流程。响应返回选择集合的 revision/hash。旧 run 仍可审计查看，不能从默认队列修改；本轮不删除其未关闭任务或改写历史。

**普通操作与阻塞操作**：

- 普通改分保留 `reason` 必填，服务端验证 frozen policy、分值范围、当前结果身份和 review revision。采纳写 ReviewLog 并重算；整体提交复核仍是单独动作，不因清空几行队列自动完成。
- 阻塞复核复用 `/api/v2/manual-review-tasks/{id}/claim|release|resolve` 和现有服务；显示领取者、version、trigger code/message。解决必须由领取者提交匹配版本、分数、理由及从冻结正文选择的证据。多任务关联同一评分项时显示关联关系，全部阻塞解决前不得出现完整总分/等级。
- task 解决记录与 ReviewLog 在时间线中关联展示，避免重复计数。采纳数/调整数以当前评分项最后有效确认计算；重复修改保留在时间线，不能增加“已确认项数”。平均调整幅度只纳入有 AI 分数的人工调整项，并公开分母。

**批量采纳合同**：保留计划路径 `accept-all`，但明确作用于用户预览并提交的有限集合，按钮显示“采纳本页可采纳项”。请求包含 batch/结果集合 revision、明确的 run/item ID 与各自 review revision、理由和 idempotency key；每次最多 100 项，跨页操作需要重新选择，不在服务端无限扫描全批次。

服务端先校验组织及 reviewer 能力，再以短事务锁定/校验整个集合：只接受有有效 AI 分、仍待普通确认、无未解决阻塞、未被人工修改、属于当前结果的项。任一项过期或不合格返回 409 和刷新指引，整次不写入；禁止覆盖已改分数。幂等键按组织、操作人和动作限定，同键同载荷返回原结果，同键不同载荷 409；持久化命令回执与 ReviewLog 同事务提交。普通单项修改、批量采纳、整体提交、任务解决及重评须共享 run/item 的并发锁顺序和 revision 更新，不能只有新端点防冲突而旧写入口仍可覆盖。实现应提取不自行 commit 的服务，禁止循环调用现有每项自行 commit 的 API。

**需要确认的原因**为结构化 `review_reasons[]`（source、code、message、可选 rule_code）与派生展示文本 `review_reason`，优先排列 blocking/确定性原因，再列模型补充。原因不能改变触发依据或自动清除复核标记。

| 路径/来源 | 实施要求 |
|---|---|
| legacy LLM | 修改对应 prompt、validator 的 required keys 与 Mock；保留 evidence_failed/注入检测的确定性原因 |
| Core semantic/compatibility | 分别修改 Core provider 输出 schema、Mock 与运行适配；保留解释至运行审计元数据，再投影到评分项，明确 rule→criterion 的稳定合并和去重规则 |
| deterministic/hybrid/policy | 从检查结果和 policy issue 构造原因；不要求无 LLM 的路径虚构模型解释 |
| Provider/预算失败、Core invalid/block | 从已有错误码、review issue、ManualReviewTask trigger 构造；LLM 无返回时仍有明确原因 |
| 历史 run | 新列可空，按已有 issue/任务数据提供显示回退；不为补文案重评历史 |

改变受封闭 schema 管理的输出时同步版本化，列出 legacy/Core 两条完整链路，不能认为 `REQUIRED_SCORE_KEYS` 是所有 Core 输出的共同入口。同步 bump `cache/llm_cache.PROMPT_VERSION`、Core 镜像及实际受影响 provider/profile prompt identity，更新缓存与运行身份测试；在 `论文打分系统设计方案.md` §15 对应真实留出集重锚 QWK。未取得基线证据前，LLM 原因变更不得进入生产；确定性展示回退保留原 prompt 合同，不改变默认 legacy 或 GATE-03 权限。

### C. 批次状态机与守卫

保留设计的七种**业务阶段** `draft / parsing / scoring / scored / scored_with_errors / reviewed / archived`；并行返回 `job_status`、未完成/失败计数与可执行操作，不能靠阶段字段表达全部任务故障。创建只允许 draft；Patch 不再允许客户端设置阶段或终态。兼容期对携带未变化 status 的旧请求可作 no-op，改变 status 必须走动作服务。

| 事件 | 条件与转移 | 故障/并发规则 |
|---|---|---|
| 新建、保存草稿、上传 | draft；记录已归档材料，但保存草稿不启动评分 | 字段编辑沿用已有 rubric/version/BYOK 冻结约束 |
| 开始/恢复解析 | 有归档文件且无活动评分任务，进入 parsing | 单文件租约负责恢复；失败项独立保留 |
| 解析全部结束 | 回 draft，返回 ready/failed 等计数 | 有失败不能启动全批评分，不把解析失败写成 scored |
| 启动/恢复评分 | 全部目标材料已解析，已绑定标准/连接且有授权观察策略；进入 scoring | 创建新 generation 即撤销该批次 reviewed；服务端锁定批次，禁止同时上传/改标准/归档 |
| 评分结束 | 当前范围全部有有效结果为 scored；有失败/缺结果为 scored_with_errors | 即使全部失败也显示错误阶段与零完成数，不伪造总分 |
| 取消/中断 | 活动执行停止后，依当前结果回 draft/scored/scored_with_errors；另示 job canceled/failed | cancel_requested 期间仍属活动；租约失效显示待恢复，不自动宣称完成 |
| 失败项重试、单篇/全批重评 | 显式动作进入 parsing/scoring，撤销 reviewed，更新结果集合 revision | 原 run、ReviewLog 和任务保留审计，新结果未产出时不能沿用旧确认 |
| 完成复核 | 当前结果齐全、普通待确认数为 0、blocking open/claimed 为 0，且集合 revision 未变，转 reviewed | 锁定检查并提交；服务端重算与校验，禁止直接改状态 |
| 归档/重新打开 | 仅 reviewed 且无活动任务可归档；重开后重新计算稳定阶段 | archived 下拒绝上传/解析/评分/改分/取消重试等写动作；重开走显式授权动作，历史导出仍可读 |

新增批次 `state_version` 支持乐观并发；所有触发都经同一服务，包括同步 `/score`、`/start`、单篇评分、jobs 回调、解析恢复、复核和归档。服务在数据库事务中校验预期状态/版本及资源租约，并更新投影；客户端轮询不能写状态。阶段是材料与当前结果的投影，job 终态不直接等于业务 reviewed。

存量先普查全部值及材料/run/task 状态；用明确规则计算迁移值，未知或无法判定数据输出脱敏 ID/计数并终止，不统一改成 draft。CheckConstraint 仅限制合法阶段，API/服务测试另验证合法与非法转移及并发。

### D. 进度与统计

已有 `/batches/{id}/summary` 的材料和最新 run 摘要可复用，但不能将历史 run 总数当作完成材料数。各页面使用 §5-B 的选择器，分别返回上传、解析、评分、复核数量，分母为当前目标集合；空批次显示 0 项而非伪造百分比。

进度条在失败/取消时展示失败/待恢复计数；只有成功完成相应阶段才显示完成。分布图只包含有效且非空终分，另报未评/阻塞数量；分桶、跨批次比较和耗时冷启动见 §11。耗时是估计值，不能用于评分租约或超时判定。

### E. 多文件上传、解析预检与草稿

**保留能力属于 P0；预检摘要和耗时优化可后置。**

- Supabase：逐文件创建 `direct-upload-intents` → 标准签名上传或 TUS → `complete-upload` 校验归档 → 单文件 `/parse`。沿用 6 MB 默认阈值及标准上传网络故障时先确认归档、再按需恢复 TUS 的逻辑，避免重复对象。
- local：能力投影声明本地上传入口，逐文件 `/papers/upload` 上传解析，保持文件级结果与重试。`bulk-upload` 保留给兼容客户端，不作为 Vercel 多文件上传默认路径；直传配置失败必须报错，不能偷偷回落到函数转发大文件。
- 统一逐文件状态、有限并发、取消调度、归档确认失败/解析失败重试。进度指明上传与解析分别完成多少；一个失败不撤销其它成功文件。刷新后重新加载服务端文件状态；未完成传输需重新选择原文件再按 fingerprint 恢复，已归档的文件不重传。
- 浏览器预检扩展名/大小，服务端依配置复核；扫描件明确拒绝并提示提供文字版 PDF 或 DOCX。预检端点接收已归档 paper ID，仅汇总解析诊断，不重新传文件或额外执行一次全文解析。
- 存为草稿表示保存批次和已完成归档的文件，不创建评分 job；未完成传输不能显示已保存成功。恢复时继续上传/解析；首版不自动删除用户材料，遗留 uploading 预留清理沿用明确的单文件丢弃入口。
- “开始解析与评分”先确认解析全部成功、标准/BYOK 可用与授权观察策略，随后创建并运行持久化 score-job。没有策略时引导录入，不改用同步 `/start` 绕开恢复能力。

### F. 导出审计与检查

保留已有 `SpreadsheetWriteLog` 表名、通道值和写入口，先扩展而不是重命名/重标历史。增加事件级 `ExportEvent` 及 run 关联记录，供新输出中心读取；旧 `/export-logs` 默认合同保持兼容。

| 旧 `target_type` | 新事件展示通道 | 必须保留的信息 |
|---|---|---|
| mock_sheet | mock_sheet | Mock 身份，不显示为真实 Sheets 写入 |
| google_sheets | sheets | 原类型、目标、状态、错误、原日志 ID |
| excel | xlsx | v1 导出与关联 run |
| excel_v2 | xlsx | v2 导出与 schema/profile 身份 |

HTML/JSON 从新增事件链路记录；历史不存在的日志不补造。无法可靠确定的操作人置空并显示“历史记录未记录”，不能把 run.owner 当作导出操作者。一份 v1 批次 xlsx 当前可能有多条 run 日志，禁止仅凭相同文件路径/相近时间强行合并为一次历史事件；按一条旧日志一条可追溯的历史记录导入并标 `legacy_run_log`，历史次数单独显示。

新导出一次请求创建一个 event，记录组织、真实操作人、请求范围、选中的 run 集合/版本、format、schema、状态及受控产物引用；多 run 通过关联表表达。状态区分生成中/生成成功/失败；客户端断开不能证明文件已下载。批次预检与真正导出复用同一选择器，生成前重查 revision，期间状态变化返回冲突而不输出混合结果。

预检区分阻塞和告警：未解决 blocking、缺有效结果时禁止“完成复核并导出正式成绩”；原有允许检查中间状态的报告/结构化审计导出仍可用，保持空总分并标注未完成，不用新 UI 放宽旧服务限制。明确导出目的和结果集合，避免所有通道一律“不阻断”。Sheets 可用性从鉴权能力投影读取，离线时禁用。

### G. 独立里程碑：双评/仲裁

首版 `POST /batches` 只接受省略或 `single`，拒绝其它模式；不持久化没有变化语义的 review_mode 字段。双评/仲裁以后另行设计评次、终分聚合、分歧与仲裁审计、导出合同及迁移。

## 7. 数据模型与迁移

当前 head 是 `0023_rule_scoring_review_tasks`，以下编号是计划顺序，实施时按实际 head 串联。增加了并发和审计合同后，撤销原“固定三个迁移即可完成”的估算。

| 计划迁移 | 内容 | 阶段/兼容与验收 |
|---|---|---|
| `0024_batch_status_machine` | 七态约束、`state_version`；存量阶段普查与可解释回填 | 1；先更新所有应用写入口，再收紧约束；未知数据 fail-closed |
| `0025_review_contract` | `review_reasons` JSON、可空展示文本、run/item review revision；命令回执表的组织/操作人/幂等键唯一约束 | 2；历史原因不重评，任务继续使用 0023 表；幂等与日志同事务，Postgres 并发测试 |
| `0026_export_event_expand` | 新增 ExportEvent 与 run 关联、旧日志 ID 唯一映射；旧表仅增可空 event 关联 | 6A；保留原表、列与 target_type，新写端原子双写旧表支持的通道及新事件 |
| `0027_export_event_backfill` | 幂等迁移四种旧通道，保留操作者未知与 legacy_run_log 粒度 | 6B；逐通道计数/状态/来源 ID 核对，不按路径猜合并；未知通道终止 |
| 后续独立迁移 | 双评/仲裁模型或旧日志结构的最终清理 | 不计首版，兼容窗口结束且另行审核后再安排 |

首版不物理删除/重命名旧日志表，不移除恢复所需审计字段。新增 HTML/JSON 事件无须伪造旧 SpreadsheetWriteLog。旧应用回退期会只写旧表，重新前进时必须重新执行幂等补录；0027 调用可重入的补录服务，并配套独立运维入口，因为再次执行 `alembic upgrade head` 不会重跑已完成的迁移。该入口随 6B 实现并记录到 RUNBOOK；切换前验证读取一致性并保留来源标记。

正文只读投影不迁移快照、不更改 hash；预检首版复用已有解析诊断，不新增未经使用的 JSON 列。新增表明确组织外键、索引、唯一性；按生产既有 `pgs_app` 的最小权限/RLS 基线配套，通用 CI 不创建部署专属角色。

每个迁移要有独立 `test_migrations.py` 验证与 PostgreSQL 16 artifact，包括升级、四类旧日志样本、非法状态、并发约束和有数据时拒绝 lossy downgrade。更新 CI 中显式的 head/逐版本 verifier，不能假定新增文件就已覆盖全部门禁。回滚默认保留 schema 和审计数据，使用经验证兼容的应用版本；不能回退到绕过状态/复核守卫的旧版本。

## 8. 前端技术、部署与并存

Vite + Vue 3 + JavaScript，Vue Router + Pinia；OpenAPI 生成 `.d.ts` 并通过 JSDoc 引用，保留 JS 源码。生成步骤不依赖生产 API：本地测试配置导出 schema，CI 检查生成结果差异和类型使用；只为本次使用的接口补强 schema，不要求先改完所有历史端点。

字体为自托管 IBM Plex Mono，随原始字体附许可证；具体字体文件/子集工具在阶段 0 校验许可证后锁定，不在本次计划修改中下载。accent/density/logo 用 CSS token；界面保留键盘焦点、错误提示、加载/空状态和窄屏折叠，不将桌面三栏固定宽度作为唯一布局。

### 8.1 查看器边界

查看器对外暴露 `locate({ source_kind, snapshot_hash, anchor_id, locator, quote, page })`，`page/quote` 可空；返回精确定位、上下文定位或无法定位结果。评分表不跨组件操作 DOM、不依赖 chunk 结构。Core 与 legacy 适配器共用显示 DTO，但保留不同来源及可信度。

未来原文渲染仍需独立解决页码映射、DOCX 转换、读取授权和定位精度，不宣称现在内联页码已完成迁移准备，也不提前估计只替换几百行代码即可切换。

### 8.2 构建与三种部署

阶段 0 建立 `frontend/workbench/` 源码、package.json 与单一 package-lock；Node 22 与现有部署 job 对齐，在依赖接入时验证 Vite/测试工具兼容并锁版本。提供以下**待实现**脚本：`build`、`test:unit`、`test:e2e`、`typecheck`、`api:generate`、`api:check`。使用 `npm ci`，不依赖运行时联网安装。

保留 `scripts/build_web_static.py` 为统一组装入口：调用已安装依赖的前端 build 并组合新旧产物；失败即阻止发布。`pyproject.toml` 的 Vercel build 配置和 workflow 同步适配安装/构建顺序。

| 部署 | 实施目标 | 必验行为 |
|---|---|---|
| Vercel | `public/` 含新旧页面、各自 hash 资源；Node/npm 构建发生在 prebuilt deploy 前 | SPA 路由刷新、登录/邀请/重置、API 不被 fallback 吞掉、资源及许可证可用 |
| 本地 FastAPI | 从统一组装产物托管新页，同时保留开发时旧入口与非默认 API_PREFIX 注入 | 静态目录配置、深链接返回 HTML、未知 API 返回 API 错误；开发代理保持同源 Cookie 语义 |
| Docker/Compose | 增加 Node 构建阶段，将同一静态产物复制到 Python runtime；运行镜像不安装 Node/npm | 容器启动与页面/字体/动态模块可用，离线运行不访问 CDN |

资源分配：旧资源保留 `/assets/*`，新 hash 资源独立 `/workbench/assets/*`，只有 hash 资源使用 immutable；HTML/运行配置不使用长期不可变缓存。字体采用同一 hash 规则并附许可证。更新 `vercel.json` 的资源头和精确 SPA rewrite，先匹配 `/api` 与静态文件，再处理允许的页面路由；缺失 JS 文件必须 404，不能回 HTML。FastAPI 的托管根、`system.static_web_ready` 检查、Docker COPY、`.vercelignore` 的字体/图标打包与离线部署文档均一并核对。

### 8.3 新旧页面并存与回退

初始 `/` 继续旧 SPA，新页统一在 `/workbench/*`，新页面由导航能力表逐页启用；未交付页跳旧页时携带经服务端校验的 batch/run ID，不传原文或凭据。使用 Vue Router history 模式，显式实现两个宿主的路由回退；邀请/重置现有 URL 和 fragment token 语义保持，认证流程单独测试。

旧页保留到对应新页 §12 验收通过；旧 SPA 在并存期同步适配 capabilities、review revision 和状态错误，不成为绕过新服务守卫的入口。切换组织/离开未保存工作区有提示，切换页不丢失服务端任务。

阶段 6 通过门禁后才把 `/` 指向新入口，并保留 `/legacy/` 兼容入口及其独立资源，至少一个可回退发布窗口。回退使用受门禁验证的旧 UI 兼容应用产物，数据库保留；Streamlit/旧源码是否最终删除见 §11，不将物理删除列入首版必要步骤。每次发布归档对应静态产物，避免回退 HTML 找不到旧 hash 资源。

### 实施中发现并修正的既有缺陷

这些不在原计划的预期内，是写测试或实机走查时暴露出来的：

1. **持久化批任务从不把批次标记为 `scoring`**，直接由 `draft` 跳到终态。计划只提到
   `parsing` / `reviewed` / `archived` 缺失。
2. **`GET /papers` 缺少稳定排序**，同一时刻上传的材料在两次请求间顺序可能不同，
   评分工作区的「下一份」会跳错行。
3. **测试会打到生产库**：`alembic/env.py` 无条件用 `settings.DATABASE_URL` 覆盖调用方
   传入的 URL，而 settings 加载 `.env.local`。已加 conftest 防线。
4. **旧 SPA 的「测试模型连接」按钮无角色门控**，`/system/llm-check` 收紧后非平台
   管理员点击只会拿到 403。上线准备时发现并修复。
5. **CI 的前端 job 从不安装后端依赖**，而浏览器验收的 webServer 是真实 FastAPI。
   接入验收那一版会因 `ModuleNotFoundError` 起不来，Playwright 只报 webServer 超时，
   把真正的原因盖掉。已补 `uv sync --locked`。
6. **`playwright.config.js` 的解释器路径按配置文件目录写**，但 `cwd` 已切到仓库根，
   `../../.venv` 指到了仓库外；本地跑同样静默超时。已改为相对仓库根。
7. **`archived` 是一个无法到达的状态**：`PATCH /batches/{id}` 明确拒绝改 status 并
   让调用方去用「对应的阶段动作端点」，而 `archive` / `reopen` 端点从未建过；评分
   任务页的状态图例又把 `archived` 列了出来——看得见、走不到。补端点时还发现
   `BatchArchived` 无人捕获，写归档批次会返回 500，前端会把「需要先重新打开」显示
   成「服务器出错」；已挂应用级处理器映射为 409。
8. **`GET /batches/{id}/score-distribution` 从未实现**，§6 列在阶段 1/6。按 §11 未决
   项的处理办法只交付原始有效终分与缺结果计数，`bucketing` 显式返回 null，让前端
   能区分「还没定」和「算出来是空」。
9. **验收种子的 run 从没设过总分**，分布图因此恒为空。已按逐项分数求和回填。
10. **`GET /batches` 没有 status 过滤**（§6 列了）。前端一直在客户端筛：为了看一个
   阶段要下载全部，且分页一旦加上会把「这一页里没有该阶段」显示成「没有该阶段的
   批次」。改到服务端后阶段计数要单独保留未过滤的那一次，否则筛选时图例会把其它
   阶段显示成 0。
11. **归档漏了「无活动任务」这一条**（§5-C 明写）。阶段判断挡不住：任务刚拉起、
   阶段投影还没跟上时，`reviewed` 与一个仍在跑的任务可以并存，归档会把批次转成
   只读而那个任务继续往里写。
12. **人工复核任务列表只能按 status 过滤**（§6 要求补 run/batch 范围与分页）。取一个
   批次的阻塞任务此前要把全组织的任务都拉回来。批次过滤经 run→paper 连接实现并叠加
   批次自身的组织归属，因为任务行上的 `organization_id` 在批次换归属后仍是旧值。
13. **`Cache-Control: private, no-store` 只设在 document-view 上**，而 §5-A 要求
   「正文投影**与评分项展示投影**」都设。`GET /scoring-runs/{id}/items` 的两种形状
   都带学生原文的逐字引文，换个端点就能把同样的内容缓存出去。顺带给复核队列也
   补上（计划外加固：它带学生姓名学号与分数，属同一类数据）。
14. **历史 run 的原因显示回退没做**（§5-B 表格里明写「历史 run | 新列可空，按已有
   issue/任务数据提供显示回退」）。`review_reasons` 是 0025 才加的列，在它之前完成
   的评分这一列为空，队列会显示一行标着「需要确认」却不给任何原因。回退只用评分项
   上已有的数据推导（置信度、证据充分性、旧管线追加进 `deduction_items` 的确定性
   文案），推不出来时说「原因未记录」——编一个原因比不给原因更糟，复核者会照着那个
   不存在的线索去核对原文。不重评历史。
15. **上传没有取消入口**，§5-E 明写「有限并发、**取消调度**」。上传 50 份材料后
   无法中止。取消停的是「还没开始的那些」，已发出去的那一个仍走完并记下结果——
   文件在服务端已经归档，谎称没传成功只会让用户再传一次，产生重复对象。
16. **刷新后不按服务端文件状态恢复**（§5-E「已归档的文件不重传」）。新建页挂载时
   直接 `reset()`，刷新会把已归档材料全丢掉；用户只能重建一个批次再传一遍。补了
   `restoreFromServer` 与评分任务页的「继续上传」入口，草稿批次可回到上传流程。
17. **`POST /batches` 从不校验 `review_mode`**，而 §5-G 明写「首版只接受省略或
   `single`，拒绝其它模式」。Pydantic 默认忽略未知字段，发 `review_mode: "dual"`
   会拿到 200——调用方据此认为系统在做双评，实际每份材料只评了一次，这个错误结论
   会一直被当成双评结果用。只校验、不持久化（存一个不影响行为的值同样误导）。
18. **导出事件只会写 `generated`**，而 §5-F 要求「状态区分生成中/生成成功/失败」。
   一次失败的 Sheets 写入不留任何痕迹，历史只显示成功——按遗漏说谎和按内容说谎
   一样糟。失败必须带原因、成功不许带；已定案的事件不能改写。
19. **组织切换只清了 session store**（§2.1 要求「切换前处理未保存改分并停止旧组织
   上传调度；切换后清空 Pinia/查询缓存/选中资源」）。批次、工作区、复核、上传四个
   store 都留着上一个组织的数据——旧组织的学生姓名留在界面上就是一次跨组织泄露，
   而上传循环还会继续往旧组织的批次里写。
20. **分布没报阻塞数量**（§5-D「另报未评/阻塞数量」）。阻塞项的总分尚不成立，不说
   出来读者会把曲线当成这批的最终形态。
21. **预计耗时完全没做**（决策 12）。按 §11 的未决处理办法实现：样本够（≥3 次已结束
   任务）给区间，不够就明说暂无估计——不编造分钟数。区间而非精确值，因为精确数字
   会被当成承诺；`display_only` 把 §5-D 的「不用于租约与超时判定」写进合同。
22. **Docker 镜像从不 COPY `public/`**，而 FastAPI 从 `public/workbench` 托管新页。
   容器里 `/workbench/*` 全是 404，legacy 入口走 `frontend/web` 反而正常——故障看
   起来像「新页面没部署上」而不是「镜像少了一层」。compose 冒烟只 curl 了
   `/api/system/integrations`，完全看不见这件事；已补工作台、字体许可证、hash 资源
   与「缺失资源必须 404」四项检查。
23. **字体许可证没随产物发布**。SIL OFL 1.1 要求许可证随字体分发；字体文件进了产物、
   许可证没进，是一个安静的合规缺口——没有任何东西会报错。组装脚本现在复制它，
   入口页用 `<link rel="license">` 指过去（放进产物却没人找得到等于没放）。
24. **生成的 `.d.ts` 没有任何人引用**，而 §8 要求「OpenAPI 生成 `.d.ts` 并**通过
   JSDoc 引用**」。它照样进合同门禁、照样产生 diff，但没有一处代码会因为后端改了
   字段而报错——门禁看起来在工作，实际什么都没保护。`jsconfig` 的 `checkJs` 是
   false，所以 JSDoc 根本不被校验。补了 `src/api/types.js`（类型从端点路径取，不
   手抄形状）与 `// @ts-check`，按接口逐步接入。已做变异验证：把读取的字段改名，
   `typecheck` 立即报 TS2551 并指出正确字段名。
25. **字体许可证在产物里但 HTTP 取不到**。静态 mount 只挂了 `assets/`，许可证交给
   SPA 回退取到的是一份 HTML——合规上等于没发布，入口页的 `<link rel="license">`
   也指向一个假 URL。这条是新加的 V13 离线验收先于 CI 抓到的。修法只认一层文件名，
   带分隔符的路径一律走回退，拼不出 `../` 读到产物之外。
26. **0025–0028 没有「有数据时拒绝 lossy downgrade」守卫**，而 §7 对每个迁移都写了
   这条。0024 做了，后四个没有：降级会**静默删掉**复核原因、批量采纳的幂等回执与
   导出审计事件——这些不是缓存，删掉重建不回来，丢了幂等回执还会让一次重放变成
   二次写入。空库降级仍然允许，回滚一个刚上线还没产生数据的版本是正常操作。CI 的
   PostgreSQL job 也补了对应验证。
27. **旧写入口绕过新守卫**，而 §8.3 明写「旧 SPA 不成为绕过新服务守卫的入口」、
   §5-B 写「不能只有新端点防冲突而旧写入口仍可覆盖」。`PATCH /score-items/{id}` 与
   `POST /scoring-runs/{id}/review` 两条都没接：归档批次仍可改分与置为已复核——那样
   归档只是一个标签而不是写保护；改分也不 bump `review_revision`，批量采纳会以为
   这一项没变过，把人工刚改的结果按「采纳 AI 分」静默覆盖。
28. **`api:generate` / `api:check` 是空转脚本**：它们读的 `storage/openapi.json`
   从来没有人生成，`schema.d.ts` 也不存在，§12.2 要求的类型/schema 差异检查因此
   一直没有门禁。补了 `dump_openapi` 导出入口与前端调用路径的静态契约测试
   （`test_frontend_api_contract.py`）——前端是纯 JS，调错路径只在浏览器里表现为
   一个 404，而 404 常被页面当成「暂无数据」渲染掉。

## 10. 风险与控制

| 风险 | 控制与回退 |
|---|---|
| Core 引用不能直接映射 chunk | 用冻结快照投影，无法恢复原 quote 则显示上下文；不修改历史身份 |
| 阻塞任务被遗漏、批量覆盖人工结果 | 双类型队列、共用 revision/锁、明确集合与幂等；阻塞总分始终为空 |
| prompt 扰动评分和缓存命中 | 两条管线版本检查、真实 QWK；失败保留旧 prompt 与确定性原因展示，不删除旧缓存或改写历史 |
| 状态收敛错误/客户端绕过 | 所有写入口共用守卫；未知历史值 fail-closed；重评撤销 reviewed，取消有独立 job 状态 |
| 直传/恢复退化 | 抽取旧上传逻辑为独立服务，保留标准/TUS/归档/解析错误合同，浏览器注入各阶段失败 |
| 历史导出误标或双写重复 | 保留旧值、来源唯一约束、逐通道对账；两次发布 expand/backfill，不在首版删表 |
| 运维泄露跨组织信息 | 平台/组织接口拆分、先过滤再聚合；测试直接调用而非只看导航 |
| 构建只适配 Vercel、深链接 404 | 阶段 0 完成三宿主产物/路由合同；归档静态产物并验证兼容回退 |
| 全站重写缺行为证据 | 每页先过 browser gate 再替换入口；不能用静态字符串断言替代 |
| 设计范围继续扩张 | 非论文完整页面、双评/仲裁、原文渲染独立决策，不阻断必需的 Core 论文能力 |

### 12.2 CI 与证据

每个阶段需要 PR 附上涉及 V 编号的结果、API/组件测试和合成浏览器证据。CI 增加独立前端 job 执行锁文件安装、类型/schema 差异检查、组件测试、生产 build、浏览器测试；现有 pytest 静态源码契约按功能迁移，不能简单删除使门禁变绿。生产 deploy 的 `needs` 必须包括前端 job，保留 PostgreSQL、Docker 和全量 Python 门禁。

**当前可执行的基础核验命令**（不等于新前端验收已完成）：

```bash
.venv/bin/python -m pytest -q backend/app/tests/test_m8_documentation_contract.py
.venv/bin/python -m pytest -q backend/app/tests/test_p3_manual_review_tasks.py backend/app/tests/test_paper_direct_upload.py backend/app/tests/test_api_core_flow.py backend/app/tests/test_m4_rule_executor.py::test_authorized_quote_is_bound_to_validated_unit_and_canonical_locator
.venv/bin/python -m pytest -q backend/app/tests/test_migrations.py
.venv/bin/python -m pytest -q
```

前端脚本在阶段 0 实现后，由 README/RUNBOOK 记录实际目录与运行命令；现在不得把未存在的 `npm run` 结果记为通过。迁移测试的 SQLite 结果不能替代真实 PostgreSQL 16 artifact；QWK 的 Mock/合成演练不能替代真实留出集。

### 12.3 发布与回退

完成 `docs/上线清单.md` 与三文档同步；生产数据库操作前先备份并 verify，restore 仅针对明确批准的数据库和空 storage。发布只由 main 的 GitHub Actions 全部门禁通过后，经 production Environment 使用当前固定 Vercel CLI `58.4.0` 执行；不得为前端预览绕过生产流程。

在预览环境完成路由/恢复/导出回退演练并关联 commit、前端产物、PG migration/restore artifact；生产上线后执行不含真实敏感内容的已授权冒烟。失败时回退兼容应用与静态产物，保留新增 schema 和审计状态；不执行 lossy downgrade，不切换默认 Core，不覆盖历史评分。
