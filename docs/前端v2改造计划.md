## 1. 结论摘要

设计稿不是一次皮肤改版。它把产品从**「按对象浏览」**（选批次 → 选论文 → 选评分记录 → 看结果）改成**「按任务推进」**（工作台看待办 → 进入评分工作区逐份确认 → 复核队列清零 → 导出）。这个转向带来四类后果：

1. **新增一个当前完全不存在的核心界面**：三栏评分工作区（正文渲染 + 证据高亮 + 右侧评分表）。按决策 7，正文从已有的 `PaperChunk` 渲染，后端新增能力仅剩「evidence 内联页码」一项。
2. **复核从「单条记录」升级为「批次级队列」**：现有 `PATCH /score-items/{id}` 逐项改分仍可用，但队列查询、批量采纳、复核统计、复核时间线四类端点都不存在。
3. **多组织能力需要补画**：设计稿按单租户绘制（页脚「v2.4 · 单租户部署」，登录页无组织切换，「账户与连接」导航项存在但从未绘制）。按决策 2，这部分要用设计稿的视觉语言补齐——**后端零改动**，纯前端工作。
4. **评审方式（单评/双评取均/双评+仲裁）是全新业务概念**：后端从模型到编排到导出全链路都没有多评次概念。按决策 4 拆为独立里程碑，v2 首版置灰。

其余部分（评分标准生命周期、规则审核、扣分细则来源溯源、导出通道）后端基础相当扎实，主要是前端重组 + 少量聚合端点。

**工作量重心排序**：复核队列 > 评分工作区 > 多组织界面补画 > 上传预检 > 统计端点 > 评分标准页重组 > 导出增强。（评审方式独立立项，不计入 v2。）

## 3. 现状盘点

**前端**：`frontend/web/` 原生 HTML+JS，无框架无构建（`index.html` 377 行 / `app.js` 2965 行 / `styles.css` 1952 行）。`scripts/build_web_static.py` 产出带 hash 的 `public/`，Vercel 静态托管 + `api/index.py` Python Serverless 挂 `/api`。另有遗留 `frontend/streamlit_app.py`（731 行）。**仓库内无任何 TypeScript，也无任何 webfont**（全系统字体栈）。

**后端**：FastAPI，14 个 router 约 100 个端点（`/api` 前缀）。核心模型链路：
`GradingBatch → Paper → PaperChunk` / `ScoringRun → ScoreItem → ReviewLog`，评分标准侧 `Rubric → RubricVersion → AtomicRule → RuleLevel`，来源侧 `SourceArtifact → SourceRule`。

**输入格式**：DOCX 与**文字版 PDF 都是一等输入**（依赖 `pymupdf>=1.24.0`；`extractor.py:42-54` 按后缀分发）。`PaperChunk.page_start/page_end` 的页码来自 PDF 的 block——DOCX 无真实页码，该字段可能为空，前端需容错。

**已具备、可直接支撑设计稿的能力**（重要，避免重复造）：

- `ScoreItem.confidence`、`need_manual_review` — 置信度与待确认标记已落库
- `ScoreItem.evidence` = `[{quote, location, chunk_id}]`，`PaperChunk` 带 `page_start/page_end/section_title/text` — **决策 7 的正文渲染与证据锚定全部由此供给**
- `ReviewLog` 带 `reviewer_id / before_score / after_score / reason` — 复核留痕完整
- `AtomicRule` 带 `mutex_group`（互斥）、`cap_points`（累计上限）、`creation_method`（来源）、`reviewed_by/reviewed_at`、`status`；`RuleLevel` 承载严重程度分档；`SourceRule` 精确溯源到 Excel 工作表/行/单元格 — **设计稿规则表的每一列都有对应字段**
- 规则逐条审核流程端点齐全（submit-review / approve / reject / reopen / template-links review）
- `_compiler_identity()` 已预留 `model_provider / model_name / sampling_params / prompt_version` 信封 — 生成指纹有位置
- 批任务检查点恢复 / 取消 / 定向重试（`BatchScoringJob`、`BatchScoringItem`）
- **多组织全链路**：组织、成员、邀请、角色、BYOK 连接、模板可见范围 — 决策 2 所需的后端能力全部就绪

## 5. 能力缺口清单

### P0 — 阻断设计稿落地，必须做

**A. 证据定位与正文渲染**（评分工作区前提）

按决策 7，中间栏从 `PaperChunk` 渲染结构化正文流（章节标题 + 页码标记 + 正文段落），DOCX 与 PDF 走同一条路径。

- **需要新增**：`GET /scoring-runs/{id}/items` 的 evidence 内联 `page_start` / `section_title`。用途有二——渲染证据 chip「第 12 页 · 3.2」，以及为将来切换原文渲染留下唯一可用的桥（见 §8.1）。当前前端是二次拉 `/chunks` 再按 `chunk_id` join（`app.js:1661`），内联后可省掉这次往返。
- **不需要**：`/papers/{id}/file` 原文下发端点、签名 URL、PDF.js、bbox。原文件仍保留在 `Paper.file_path`，只是 v2 不下发。
- **精度说明**：`evidence.chunk_id` 是硬锚点，定位确定；这比在 PDF 文本层里模糊搜索 `quote` 字符串**更可靠**（引文跨行截断、文本抽取乱序、同句重复出现都会让文本搜索失败）。
- **容错**：DOCX 无真实页码，`page_start` 可能为空，证据 chip 需降级为只显示章节。

**B. 复核队列**
- 现状：`/batches/{id}/review-sample` 是**随机抽样**（带 ratio/seed），不是低置信度队列，语义不同不可复用。
- 现状：`need_manual_review` 是布尔，**没有「需要确认的原因」文本字段**——设计稿这一列（如「方法描述跨 3.2 与 4.1 两节，证据定位不唯一」）无数据来源。
- 现状：无批量采纳端点；无复核统计（采纳数/调整数/平均调整幅度）；无跨 run 的复核时间线聚合。

**C. 批次状态机**
- 设计稿声明 7 态：`draft / parsing / scoring / scored / scored_with_errors / reviewed / archived`。
- 现状：代码只向 `grading_batches.status` 写入 **4 个值**——`draft`、`scoring`、`scored`、`scored_with_errors`（`engine.py:1273/1312/1314/1316`、`jobs.py:920/922`）。`reviewed` 只写在 `ScoringRun` 和 `Paper` 上，`parsing` 和 `archived` **从未赋值给批次**。
- 现状：`grading_batches.status` **没有 CheckConstraint**（对比 `evaluation_batches` 有 `ck_evaluation_batches_status`）。

### P1 — 设计稿明确画出，但可分期

**D. 进度与统计**
- 无进度百分比字段或计算；无分数分布直方图端点；无「与上一批次均分对比」；无「预计耗时」（需要历史吞吐量样本）。
- `/batches/{id}/summary` 已返回 `paper_stats` / `run_stats` 计数，是直方图与进度的现成输入。

**E. 上传与解析预检**
- 只接受 `.docx` / `.pdf`（`papers.py:50-56`；其中 `application/zip` 是 docx 的 mimetype 别名，**不是压缩包支持**）。设计稿要求支持压缩包 → 需实现解包入库。
- **扫描件**：`document_parser/parser.py:74` 直接抛错。**按决策 1 保留该行为**，仅改造两处文案：
  - 预检报告中给出明确提示「该文件为扫描件，系统不支持 OCR，请提供文字版 PDF 或 DOCX」
  - 设计稿「将走 OCR 流程」的措辞需在实现时替换
- 无「上传后、评分前」的预检报告端点（缺章节、扫描件、体积异常）。
- 单份上限需核对现值是否为设计稿标注的 60 MB。

**F. 导出增强**
- `/export-logs` 实际查的是 `SpreadsheetWriteLog`，**只记录 Google Sheets 写入**；HTML 报告、Excel、JSON 三个通道**不落日志**。
- 该表**无操作人字段**，设计稿导出历史表要求「操作人」列。
- 无导出前检查端点。
- 无部署模式标志端点（设计稿据此禁用 Sheets 卡片）。

**G. 盲审**
- 设计稿把 `blindReview` 做成前端 prop，但真盲审必须后端不下发姓名——现状 `PaperRead` 直接返回 `student_name`。前端开关只是遮眼法。

### P2 — 独立里程碑，不计入 v2

**H. 评审方式：单评 / 双评取均 / 双评+仲裁**
- 现状：**完全不存在**。`GradingBatch` 无 `review_mode`；一份材料产生多个独立 `ScoringRun` 再聚合终分的编排不存在；分歧检测、仲裁人指派、仲裁记录均无。
- 影响面：模型（批次配置 + 评次聚合 + 仲裁记录）、编排（`batch_scoring/jobs` 需按评次×材料展开）、复核（分歧优先级）、导出（终分口径从「最新 run」改为「聚合结果」）、报告模板。
- **按决策 4**：v2 首版 UI 保留三选一但置灰，仅「单评」可选，`POST /batches` 固定 `review_mode='single'`。双评/仲裁拆为独立分支与里程碑。

## 8. 前端技术选型（已定）

**Vite + Vue 3 + JavaScript**，配 Vue Router + Pinia。不引入 TypeScript。

理由与取舍：
- 设计稿是表单/表格密集型，Vue 的模板 + 响应式写这类界面代码量最小
- 单人维护，JS 心智负担低于 TS，无类型构建步骤
- 仓库现无任何 TS，不存在既有约定需要延续

**类型安全的折中方案**：后端 FastAPI 已自动产出 `/openapi.json`。用 `openapi-typescript` 生成 `.d.ts`，配 `jsconfig.json` + JSDoc 注解引用——**不写一行 TS**，编辑器仍可对 ~100 个端点的嵌套载荷提供字段补全与错拼提示。本次改造要动 4 处以上接口契约（evidence 内联页码、导出日志泛化、批次状态机、review-queue 新增），这层投入回报明确。生成步骤挂在 `package.json` script，不进构建关键路径。

**正文渲染**：按决策 7，中间栏消费 `GET /papers/{id}/chunks`，渲染为带章节标题与页码标记的正文流。**不引入 PDF.js**。证据高亮按 `evidence.chunk_id` 定位到 chunk，再在其 `text` 内高亮 `quote` 子串。

**字体**：IBM Plex Mono 用于全部数字（分数、页码、状态编码、时间戳），中文正文走系统字体栈。许可为 **SIL Open Font License 1.1**（`Copyright © 2017 IBM Corp. with Reserved Font Name "Plex"`），允许商用、嵌入、随产品分发与自托管；分发时须附 `OFL.txt`，不得单独售卖字体，修改后不得沿用「Plex」名称。**必须自托管**（`docs/本地模型与离线部署.md` 要求资源可完全本地化），不走 Google Fonts CDN；只需 Latin + 数字子集，subset 后体积在几十 KB 量级。

**设计 token 落地**：`accent`（默认 `#175c50`）、`density` 三档行高、`logoMark` 三选一、`blindReview` 全部落为 CSS 变量 + 运行时配置。

**构建产物**：替换 `scripts/build_web_static.py`，Vite 输出到 `public/`，保持带 hash 的资源名与 `vercel.json` 现有缓存头约定不变。

### 8.1 三处接缝（为将来切换原文渲染保留）

决策 7 绕开了原文渲染，但不封死这条路。将来若要改为真正的原文渲染，被丢弃的只有中间栏的 chunk 渲染器本身（约 200–400 行）；三栏布局壳、材料列表、评分表、篇章结构 tab、格式发现 tab 全部不受影响。前提是现在留好三处接缝：

1. **查看器接口固定**。中间栏封成独立组件，对外只暴露 `locate({ chunk_id, page, quote })`。评分表点击证据 chip 时调用该方法，**不得直接操作 chunk DOM 或依赖 chunk 结构**。换实现时只换组件内部。
2. **evidence 内联页码照做**。即使 (a) 主要靠 `chunk_id` 定位，`page_start` 仍必须内联返回——切换到 PDF 渲染时，页码是唯一可用的桥。
3. **`/papers/{id}/file` 端点占位不实现**。原文件本就一直保留在 `Paper.file_path`，不会丢失；端点在 §6 中列为规划占位。

**切换时需要重新评估的两件事**（不是理由不做决策 7，但届时会重新浮现）：

- **精度会下降**。`chunk_id` 是硬锚点，PDF.js 只能在文本层模糊搜索 `quote`；引文跨行截断、文本抽取乱序、同句重复出现都会导致定位失败。要恢复到 chunk 级精度就得引入 bbox——即决策 6 明确不做的那件事。
- **DOCX 依然无法在浏览器渲染**。这个问题不是决策 7 造成的，它现在就存在；决策 7 只是绕开它。届时仍需在「只对 PDF 渲原文、DOCX 降级」与「服务端 LibreOffice 转换（离线部署需打包，很重）」之间选择。

## 9. 实施路线

> 每阶段独立可交付、可回滚。阶段 1～6 不触碰评分内核（`services/scoring/engine`），不影响 GATE-03 与 `SCORING_ENGINE_MODE` 现状。

**阶段 0 · 地基（不改功能）**
Vite + Vue 3 脚手架；OpenAPI → JSDoc 类型生成链路；设计 token → CSS 变量层；`blindReview` / `density` / `accent` 运行时配置；IBM Plex Mono 子集化并自托管（附 `OFL.txt`）；**侧边栏含组织切换器**（组织上下文影响所有列表请求，必须最先就位）；品牌更名为「有据智评」。后端零改动。

**阶段 1 · 状态机与统计（纯新增端点 + 1 个迁移）**
批次状态机补全 + 约束 + 回填（`0024`）；progress / score-distribution / export-precheck / deployment-mode 端点；前端交付**登录、工作台、评分任务、输出中心**四页。风险最低，先跑通新旧前端并存。

**阶段 2 · 复核队列（1 个迁移）**
`review_reason` 落库（`0025`）；review-queue / accept-all / review-stats / review-timeline 四个端点；前端交付**结果复核**页。

**阶段 3 · 评分工作区**
后端仅两项：evidence 内联 `page_start` / `section_title`；`/papers/{id}/neighbors`。前端交付**评分工作区**——三栏布局、chunk 正文流渲染、按 `chunk_id` 锚定的证据高亮、±0.5 步进评分表、键盘导航。查看器须按 §8.1 接缝 1 封装。

**阶段 4 · 上传与预检**
压缩包解包入库；`upload-precheck` 端点（含扫描件识别与明确拒绝提示）；预计耗时（基于历史吞吐量）；前端交付**新建评分任务**页，评审方式三选一置灰。

**阶段 5 · 评分标准页 + 账户与连接页**
`rule-coverage` 端点；前端把模板中心重组为单模板 3 步详情页，补模板范围选择器；**按 §2.1 补画账户与连接页**（成员、邀请、角色、BYOK 连接）。后端零改动。

**阶段 6 · 收尾**
盲审后端脱敏；导出日志泛化（`0026`）+ 全通道落日志；下线 Streamlit 与旧 SPA；全站文案更名核验；`docs/上线清单.md` 全项过一遍。

**独立里程碑 · 评审方式（P2）**
双评/仲裁全链路。在 v2 上线并稳定后单独立项。

## 10. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 批次状态回填 | `0024` 给存量数据加约束，历史值可能越界 | 先写普查脚本统计现有值分布，再定回填映射；按约定有真实状态数据时降级 fail-closed |
| 导出日志表重命名 | `0026` 涉及表改名 + 回填 | 分两步：先建新表双写，验证后再切读、下线旧表 |
| 正文渲染观感落差 | 中间栏是结构化正文流，非「一页纸」外观，与设计稿灰条占位的观感预期可能有出入 | 保留章节标题层级与页码标记，尽量贴近阅读体验；上线前用真实材料走查 |
| 接缝被侵蚀 | 后续迭代若让评分表直接依赖 chunk 结构，§8.1 接缝 1 失效，将来切换成本剧增 | 查看器组件接口写进代码评审清单；禁止评分表跨组件访问 chunk |
| DOCX 无页码 | 证据 chip「第 12 页」对 DOCX 无值 | 前端降级为只显示章节；后端明确 `page_start` 可空 |
| 补画界面与设计稿脱节 | §2.1 的多组织界面无设计稿参照，容易做成两种风格 | 先补一份 token 与组件规范（按钮/表格/表单/标签的既定样式），补画界面只允许组合既有组件 |
| 前端重写期间的双轨维护 | 新旧 SPA 并存 | 阶段 1 起按页切换，旧页保留直到对应新页上线 |
| 评分内核回归 | 阶段 1～6 不改 `scoring/engine`，但 evidence 结构调整会碰到 validator | 改 prompt/输入构造需 bump `cache/llm_cache.PROMPT_VERSION`；改评分逻辑后按 §15 用 QWK 留出集重新锚定 |
| 更名遗漏 | 「衡鉴」散落在文案、报告模板、邮件、README | 阶段 6 全仓 grep 核验，报告模板与邮件模板单独过 |
