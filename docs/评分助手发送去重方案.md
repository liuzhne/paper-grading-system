# 评分助手发送去重方案（请求编号）

> 状态：维护者 2026-11-06 确认，第 9 节五个问题都按推荐（B 新增列与部分唯一索引、回放那一轮、同一编号自动重发一次、撤掉 #79 的两个绕开办法、UUID 格式）。已在分支 `claude/assistant-send-dedupe`（基于 #79）实现，#79 合并后开 PR。
>
> 前置：PR #79（老师的话先显示、过程流式、说不准有没有发出去时先核对会话）合并之后实施，本方案改的正是 #79 里的发送与核对逻辑。

## 1. 背景

老师发一句话，请求可能遇到 5xx 或断线。这时前端说不准这句话有没有被后端收下：

- 后端是先提交消息、再释放运行锁和返回的，返回前出错也会是 5xx，但消息已经存下了；
- 代理或网关的 502、504，以及断线时，回合可能还在跑；断线时请求也可能还在路上，还没拿到运行锁。

#79 的做法是回头读会话，按文字找这句话（附件按“评分这 N 份文件”找）。CodeRabbit 连续几轮指出，按文字始终对应不准：另一个标签页同时说了一样的话、发了同样份数的文件，就会认错。为此 #79 加了两个绕开的办法：

- 一个新状态“还不确定有没有发出去”，这种状态不给重发；
- 附件只要是核对会话得来的结果，就不归档文件，请老师重新选择。

根本原因只有一个：前端没有办法把会话里的消息和这一次请求对上号，而“重新发送”也可能多出一条。

## 2. 目标

- 每次发送带一个请求编号。后端按编号去重：同一个编号重复收到时，不再新建消息、不再跑一遍，直接返回第一次的结果。
- 有了去重，“重新发送”和“自动重试”就都是安全的，前端不用再猜。
- 核对按编号精确对应，另一个标签页的消息不会被认错，附件也能准确归档。

不做的事：

- 卡片上的“确定”“选择”（`resume`、`select`）不加编号。它们本来就靠卡片状态防重复，同一张卡片第二次操作会返回 `ASSISTANT_CARD_STALE`。
- 编号不跨会话。

## 3. 后端

### 3.1 请求与存储

- `AssistantRunCreate` 加一个可选字段 `client_id`：8 到 64 个字符，只能是字母、数字和连字符。只对 `type = "message"` 有意义。旧页面不带这个字段，行为不变。
- 存储有两种选法，见第 9 节 Q1。推荐 B：
  - **A. 存进 `assistant_messages.meta`**：不用迁移，同一会话里的去重靠运行锁串行保证。缺点是运行锁过期、而第一次还在跑的极端情况下（实际不会发生，因为模型请求受 60 秒截止时间约束）可能重复。另外，Agent 降级时现在是整个覆盖写入 `message.meta`，要先改成合并写入。
  - **B. 新增一列加唯一索引**（推荐）：迁移 0042 给 `assistant_messages` 加 `client_id`，可以为空；再在 `(conversation_id, client_id)` 上建部分唯一索引，只约束 `client_id` 不为空的行。由数据库保证不重复，做法和 `review_command_receipts` 的幂等回执一样。这是给已有表加列，不用另外给 `pgs_app` 授权，RLS 也照旧生效。降级规则：列里有数据就拒绝降级。
- `AssistantMessageRead` 加一个可选字段 `client_id`，老师的消息带上它，前端靠它精确对应。

### 3.2 去重放在哪

在 `runner.run` 抢到运行锁之后、`_handle_message` 新建消息之前：

1. 请求带了 `client_id`、而且本会话里已经有这个编号的老师消息：不再新建，直接回放第一次的结果（见 3.3），日志记一行 `assistant_run_replayed`。
2. 没有：照常处理，新建老师消息时写上 `client_id`。
3. 选 B 时，即使极端情况下两次请求都走到了插入这一步，唯一索引也会让后插入的那次失败。捕获这个冲突后回滚，改为回放第一次的结果。

编号相同但文字不同时（前端出错或被篡改），照样按编号回放第一次的结果，不采用新文字，日志记一条警告。

### 3.3 回放什么

回放的返回体和 `/runs` 一样：`messages` 是那一轮的消息，也就是那条老师消息，加上它之后、下一条老师消息之前的助手消息（和 `context.turn_groups` 的分组口径一致）；`pending` 和 `conversation` 取当前的。见第 9 节 Q2。

流式接口 `/runs/stream` 遇到回放时，没有进度事件，直接推 `accepted` 和 `done`。

### 3.4 第一次还在跑时

如果第一次请求还在跑，它的消息还没提交，第二次请求看不到，会在抢运行锁这一步拿到 409。有了编号以后，409 不再等于“后端没收下”。前端的处理见 4.2。

## 4. 前端

### 4.1 编号怎么来

- `store.send` 每发一句话，用 `crypto.randomUUID()` 生成一个编号，写进本地消息和请求体。浏览器在非安全上下文里没有这个函数，就退回用 `crypto.getRandomValues` 拼一个。
- “重新发送”用原来的编号，不生成新的。
- 附件同样生成编号。

### 4.2 说不准时怎么办

替换 #79 的 `recoverRun`：

| 情况 | 做法 |
|---|---|
| 成功 | 按 `client_id` 找到后端存下的那条，换掉本地消息 |
| 4xx（409 以外） | 后端确实没收下，标“没有发出去”。重发安全（同一个编号） |
| 409（运行锁被占） | 可能是自己第一次的请求还在跑。等会话的 `running` 变成 false（最多 70 秒），再用同一个编号自动重发一次 |
| 5xx、`error` 事件、断线 | 等 `running` 变成 false（最多 70 秒），再用同一个编号自动重发一次：后端收到过就回放，没收到就照常处理 |
| 自动重发也失败 | 标“没有发出去”，给“重新发送”（同一个编号，安全） |

这样“还不确定有没有发出去”这个状态就不需要了（见第 9 节 Q4）。

### 4.3 附件

回放或重发返回的结果里，按 `client_id` 找到这一轮的老师消息。如果当前等待的卡片属于这一轮的消息，就把文件归到它的流程；否则不归档，提示重新添加。#79 里“核对会话得来的一律不归档”的绕开办法就可以撤掉。

## 5. 接口契约

- 只新增可选字段，旧接口的行为不变，`API_CONTRACT_VERSION` 不改。
- OpenAPI 里会新增 `client_id`，用 `api:dump && api:check` 重新生成 `schema.d.ts`。
- 前后端在同一个镜像里，一起发布。没刷新的旧页面不带编号，后端按现在的方式处理。

## 6. 测试

后端：

- 同一个编号发两次：只有一条老师消息，模型只调用一次，第二次的返回体和第一次是同一轮的消息；
- 编号在不同会话里互不影响；
- 第一次还在跑时第二次拿到 409；
- 编号相同、文字不同：回放第一次的结果并记警告；
- 选 B 时：唯一索引冲突后回放；迁移的升级、降级、有数据时拒绝降级；
- 流式接口的回放只推 `accepted` 和 `done`。

前端：

- 编号写进请求体，“重新发送”沿用同一个编号；
- 5xx 和断线之后用同一个编号自动重发一次，拿到回放就换掉本地消息；
- 409 时等运行结束再重发；
- 跨标签页：另一个标签页一模一样的话不会被认成这次的；
- 附件按编号归档。

浏览器验收：用 Mock 后端拦截第一次请求返回 502，确认对话里最终只有一条老师消息。
