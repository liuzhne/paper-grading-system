# 评分输出预算与截断恢复改造方案

状态：**已确认**（2026-10-19，Q1–Q8 均按推荐）。P1 已实施（见第 14 节），P2、P3 待实施。

起因：评分任务 `31df7ef2`（运行 `b40fecc1`，2026-10-16，Vertex `google/gemini-2.5-flash`）因输出截断整篇失败，6 个评分项里 5 个无效。PR #34 对这一个型号补发了关闭思考的参数并把输出上限调到 2048，PR #41 修了「无效项还显示改分」的界面问题。本方案处理这件事背后的设计缺口。

---

# 第一部分：问题与根因

## 1. 事故经过（生产数据，只读查询）

| 层面 | 事实 |
|---|---|
| 调用 | 48 次模型调用，其中 13 次 `finish_reason=length`（截断） |
| 用量 | 输入 58,330，可见输出 3,304，计费总量 98,552：约 3.7 万是看不见的推理 token，平均每次约 770；当时输出上限 1200 |
| 规则 | 132 条规则判定，105 条成功（都在 3 条一组的分组调用里），26 条 `PROVIDER_OUTPUT_TRUNCATED`，1 条待复核；**每条只尝试 1 次** |
| 结果 | 20% 的规则失败 → 5 个评分项无效（一项里任一规则缺结论就算不出分）→ 整篇失败，总分为空 |

## 2. 根因分层

**表层**：模型输出被截断。

**直接原因**：Gemini 2.5 Flash 默认会思考，推理 token 计入输出上限。运行身份写着「思考关闭」（`OPENAI_COMPATIBLE_THINKING_TYPE=disabled`），但适配器从没把关闭思考的参数发给 Google，思考吃掉了大部分额度。#34 已对 `gemini-2.5-flash*` 补发 `reasoning_effort: none`。

**设计缺口**（代码位置均为 2026-10-19 的 `main`）：

| # | 缺口 | 代码事实 |
|---|---|---|
| G1 | **身份是声明，不是观测** | `core_adapter.core_runtime_provider_contract` 按配置推出 `thinking.enabled`；没有任何适配器解析推理 token（全仓库无 `reasoning_tokens`），身份与真实行为不符时无人察觉 |
| G2 | **输入有预算，输出没有** | 输入：`SCORING_CONTEXT_WINDOW_TOKENS − 输出上限 − SCORING_CONTEXT_SAFETY_MARGIN_TOKENS`，有确定性预检（D-015）。输出：`OPENAI_COMPATIBLE_MAX_TOKENS` 一个全局常数，与这次请求要输出多少无关 |
| G3 | **输出结构没有上界，预算无从计算** | `core_response_json_schema`：`occurrences`、`evidence` 无 `maxItems`，`quote` 无 `maxLength`；OpenAI 兼容路径用 `json_object`，厂商侧也不约束 |
| G4 | **截断被当成判断失败，不自动恢复** | `rule_executor._semantic_group_decisions`：分组调用抛错 → 整组规则判无效，不重试；任务汇总提示运维「调大上限或关闭思考后重试」。AI 任务侧已有「输出不合格修正 1 次」，评分路径没有对应 |
| G5 | **补救动作让复用失效，提示没说代价** | 判定身份 = 整个提示信封的哈希（`decision_identity.rule_decision_identity`），信封含 `provider.sampling.max_tokens`、`provider.thinking` 与 `profile.prompt_version`。照截断提示（`batch_scoring/jobs.py`）调大上限后，105 条已成功的判定一条也复用不了，重试等于整篇重评；提示没说这一点 |
| G6 | **发现得太晚** | `ai_connections.verify_connection_runtime` 是 8 token 的连通性测试；能否关思考靠 `llm/thinking_params` 的型号名单（只有 `gemini-2.5-flash*`），名单会随厂商变化过时 |
| G7 | **规则任务的尝试记录不真实** | `scoring/adapters/persistence.py` 写规则任务时 `attempt_count=1`、`max_attempts=3` 是写死的，事后看不出到底试了几次 |

## 3. 对照设计原则

| 原则 | 现状违背在哪 | 本方案的对应 |
|---|---|---|
| 无状态、可缓存、可复现 | 冻结的身份与真实行为不符（G1）；容量参数混进语义身份，调容量就丢复用（G5） | P1 观测核对身份；P2 把身份拆成语义与容量 |
| 确定性优先（代码做判定题） | 输出预算是拍脑袋的常数，没有由代码按结构算出（G2、G3） | P2 有界输出契约 + 确定性输出预算，发送前拆组 |
| 结构化优先 | 输出结构没有上界（G3） | P2 契约上界写进提示与校验 |
| 人在回路、宁缺不编（D-016） | 补救全靠人改配置、重跑整篇（G4） | P2 有限次自动恢复；**一项缺结论就不出分的底线不变** |
| 早失败、少花钱 | 48 次调用之后才暴露（G6） | P3 连接能力探测与开评门禁；P1 发现不一致立即停 |

# 第二部分：方案

## 4. 总体

```
P3 测试连接：结构化探测 → 连接能力（能否关思考、推理开销、是否截断）
        │（建任务时随快照冻结）
        ▼
P2 每次调用前：按有界输出契约算出输出预算（+ 关不掉思考时的推理预留）
        ├─ 超过天花板 → 发送前拆组
        ▼
   调用模型 ──► P1 记录 finish_reason / 推理 token；声称不思考却在思考 → 停任务
        │
        └─ 截断 → P2 升一档重发 1 次 → 仍不够 → 拆成单条 → 仍失败 → 无效（底线不变）
```

## 5. P1：观测与身份一致性守卫

**5.1 每次调用记录四个数**：`finish_reason`、输入、可见输出、推理 token。
- 推理 token 取法：OpenAI Chat 兼容用 `usage.completion_tokens_details.reasoning_tokens`；OpenAI Responses 用 `usage.output_tokens_details.reasoning_tokens`；Claude 用响应里思考块的计量。
- 厂商不给时用「总量 − 输入 − 可见输出」推算，并标记为推算值。（本次事故是手算看出来的；Vertex 其实在 `completion_tokens_details.reasoning_tokens` 里报告，2026-10-19 生产核实。）
- 不记录任何模型输出内容。

**5.2 落在哪**：
- 每篇论文汇总进批量评分条目已有的 `telemetry` JSON：截断次数、推理 token 合计、各结束原因的计数。
- 运行级汇总进 `ai_usage_ledger`（新增 `reasoning_tokens`、`truncated_count` 两列，见 Q2）。
- 规则任务写实际尝试次数，修掉 G7。

**5.3 一致性守卫**：运行身份为 `thinking.enabled=false`，但一篇论文内累计观测到推理 token 大于 0（推算值要连续 2 次以上），就判定「身份与行为不符」：
- 当前论文失败，错误码 `PROVIDER_THINKING_NOT_DISABLED`，提示「这个模型没有按请求关闭思考：换模型，或在连接里改为允许思考并调大上限」；
- 同一任务里还没开始的论文**一并取消**，不再花钱（见 Q1）。

**5.4 可见性**：日志行 `llm_call_finished finish_reason=… reasoning_tokens=…`（不含内容）；运维页按连接显示近 24 小时的推理 token 占比与截断次数；RUNBOOK 加排错。

## 6. P2：输出预算、截断恢复与身份拆分

**6.1 有界输出契约**（G3）：每条规则最多 5 处发现、每处最多 3 条证据、每条引文最多 120 字（数值见 Q3）。
- 上界写进提示词，由我们的校验器（`normalize_core_provider_response`）强制，超界按「输出不合格」处理。
- **不写进厂商的严格 Schema**：2026-10-16 起草路径已证明，过细的有界 Schema 会被 Gemini 以「状态太多」拒绝；OpenAI 兼容路径本来也只用 `json_object`。
- 输出结构版本保持 `semantic-rule-response@2`：上界只收紧取值、不改形状，而且这个版本号还被已保存的结果、技术方案 Profile 与 `contracts.py` 的回放校验共用。上界检查只作用于新收到的模型响应，不回头校验已保存的判定。
- 提示词变了，升 `PROMPT_VERSION`。

**6.2 确定性输出预算**（G2）：
- `输出预算 = Σ规则(单条固定开销 + 发现上限 × (发现码 + 证据上限 × (证据编号 + 引文上限的 token 数))) + 外层结构开销`，再加 15% 余量。token 数用证据压缩已有的保守估算器（`retrieval/selection`）。
- 关不掉思考的连接再加推理预留，取值来自 P3 的探测结果。
- 实发上限 = `min(输出预算, 天花板, 上下文窗口 − 本次实际输入 − 安全余量)`。`OPENAI_COMPATIBLE_MAX_TOKENS`（及 Claude、OpenAI 的同类设置）改为**天花板**，不再是每次请求的值。
- 分组的预算超过天花板时，**发送前**就拆成单条调用（复用现有「分组判不了就逐条」的回退路径），不浪费那一次调用。
- 输入预算的计算改为「窗口 − 本条规则的输出预算 − 余量」，不再固定扣掉天花板；单条规则的证据预算因此通常会变大。

**6.3 截断的有限次自动恢复**（G4）：
- 截断属于「容量不足」，不是判断失败。第一次截断后，**升一档重发 1 次**：上限 ×2，同样受 6.2 的三个约束封顶。
- 升档后仍不够或仍被截断的分组，拆成单条调用；每条单条调用也最多升档 1 次。
- 关不掉思考、且推理 token 占了上限的大半时，不再升档，记为 `PROVIDER_REASONING_BUDGET_EXHAUSTED`，提示换模型。
- 花费上限：每篇论文因恢复而多出的调用，不超过原调用数的一半（见 Q4），超出的直接判无效。
- 每次升档、拆组都记进规则任务的尝试记录：原上限、新上限、各次结束原因，事后可查、可复现。
- **底线不变**：恢复失败的规则仍判无效，评分项照旧不出分、总分为空（D-016）。

**6.4 判定身份拆成语义与容量**（G5）：
- 思考关闭时，输出上限只决定答案装不装得下，不改变答案本身，所以不该进判定身份。判定身份去掉 `provider.sampling.max_tokens`，升到 `rule-decision-identity@2`；L0 缓存键做同样拆分。
- 思考开着或关不掉时，上限会影响思考深度，`max_tokens` 仍留在身份里。
- 运行记录仍保存每次实际发出的上限，用于审计，只是不参与复用判断。
- 代价：身份版本升级后，现有判定账本条目一次性不能复用（账本本来就是 30 天过期的缓存）。
- 截断的失败提示改为按身份是否变化如实说明：思考关闭时「调大上限后重试，已成功的规则会直接复用」；思考开着时注明「调大上限会让本篇全部规则重新判定」。

**6.5 上线方式**：开关 `SCORING_OUTPUT_BUDGET_MODE=legacy|computed`，默认 `legacy`。有界契约与拆组可能改变判定，按约定用 §15 的 QWK 留出集重新锚定基线，通过后再切成 `computed`（见 Q6）。

## 7. P3：连接能力探测与开评门禁

**7.1 结构化探测**：「测试连接」在现有连通性测试之外，多做一次真实的结构化调用。
- 用合成内容（固定文本，不含任何学生材料），按 3 条规则一组的输出结构、显式请求关闭思考。
- 记录：结束原因、推理 token、可见输出 token、耗时。
- 得出连接能力：`thinking_control = honored | ignored | unsupported`，以及观测到的推理开销、探测时间、探测版本。
- 平台默认模型在运维页的「测试」同样做一次。

**7.2 能力怎么存**：
- 存在连接记录上（新增 JSON 列，见第 8 节），**不放进连接快照**：否则重测一次，正在跑的任务都会因为快照变化报 `AI_CONNECTION_CONFIG_CHANGED`。
- 建评分任务时，把当时的能力随任务冻结，任务内的预算只按冻结值计算。
- 用探测结果取代 `thinking_params` 的型号名单；名单只作「还没探测过」时的默认值（见 Q8）。

**7.3 开评门禁**：开始评分任务前，连接必须有 30 天内的探测结果；改过连接配置后要重新探测（见 Q7）。
- `thinking_control=ignored` 且推理预留放不进天花板 → 不允许开评，提示「这个模型关不掉思考，推理开销超过输出上限：换模型或调大上限」。
- 探测本身失败（截断、输出不合格）→ 不允许开评，并给出原因。

## 11. 放弃了什么（实施时写进 DECISIONS）

- **只把全局上限调得很大**：推理模型额度越多往往想得越多，不保证不截断，每次调用更贵；问题被藏起来了。
- **对同一请求原样重试**：截断是确定性的，同上限重发必然再截断。
- **靠「允许老师直接给无效项打分」兜底**：把系统性的模型问题转嫁成老师的手工活，并绕过 D-016。
- **部分规则失败时给部分总分**：违背「每个分数都有出处」。
- **继续维护按型号的思考名单**：#34 就是这种做法，模型和厂商一变名单就过时；改为探测与观测。
- **把输出上界写进厂商的严格 Schema**：Gemini 已因 Schema 状态过多拒绝过起草请求；上界放在提示与我们的校验里。
- **把探测到的能力放进连接快照**：重测一次就会让在跑的任务全部报「连接配置已变更」。

## 14. 实施记录

### P1（2026-10-19）

按第 5 节实施，与原文不同的几处：

| 原文 | 实际 | 原因 |
|---|---|---|
